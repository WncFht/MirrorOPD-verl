# W&B 重复上传与超时分析

## 现象与证据

2026-10-29 的 Mac 输出显示，日志包接收、Git 提交及推送在 15.4 秒内完成，随后 W&B 的第一批 E49/E50 上传达到 900 秒上限。超时后旧程序继续启动 E51/E52，队列等待时间随批次数累积。以下时间直接沿用原日志的 UTC；例如 03:11 对应北京时间 11:11。

| 日志证据                                                   | 可以确认的事实                                                                            |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 03:10:04–03:10:20：解包、入队、推送成功，HEAD 到 `31775eb` | 原始日志已到日志 Git 仓库；这不代表 W&B 已收到                                            |
| 03:11:11：SDK 0.31.0、core sync、从 Mac `.netrc` 认证      | 并非旧 Python 同步器；不能把这次超时归给 legacy 引擎                                      |
| E49 显示 history `4353–5440`；E50 显示 `4352–5953`         | core 选择了云端已有历史之后的追加偏移，存在整份重放风险；该输出本身不证明这批已经上传完成 |
| E51 后续显示 history `8653–10216`                          | 该 run 的云端已存在更多历史，重新传整份快照会继续扩大重复                                 |
| 03:11:21 后重复 WAIT，03:26:11 超时                        | 上层只能确认没有进一步显示进展，不能定位为 DNS、TLS、代理、文件流或对象上传中的某一项     |

`Queued 0 new run snapshot(s)` 表示没有新建本机队列任务；旧 pending/failed 任务仍会执行。它不表示“云端没有要上传的内容”。`WAIT wandb.batch; total elapsed ...` 也是操作总耗时，不是网络吞吐量或单个 run 的有效进展。

日志里的 `forge.coreweave.com/wandb/...` 是 SDK 展示的 run 链接，仅凭该链接不能认定 API 主机配置错误。需要结合实际 `WANDB_BASE_URL`、SDK 诊断和网络错误判断。

## 重复上传的原因

旧队列以 run 路径、Git tree 和目标区分任务，本机成功快照可以跳过。但队列、`.wandb.synced` 和 `.wandb.syncstate` 位于 `.git` 下，不会随普通 Git push/pull 传到另一台机器。分析机手工 sync 也不会更新 Mac 队列。新快照还使用不同缓存目录，不能依靠上一份快照的 SDK 状态接续。

core sync 接收到同 ID 的完整文件时可以追加所有 history，而不是按文件原来的 `_step` 覆盖。云端的最后 `_step` 仍可能与本地一致，但行数已经翻倍。因此仅看最后一步、summary 数值、finished 状态或进程退出码，会漏掉重复。此前 Linux 会话也在 E51 上触发了这种追加；另建的 `6vv5o9b8-clean1029` 是独立副本，不会自动修复原 ID 或 Mac 队列。

900 秒超时和重复上传是两件事。重复上传增加了无效工作量，但现有 Mac 输出不足以证明它就是网络停滞的直接原因。没有原 Mac 的 SDK debug 日志，也没有在该网络上复测，不报告确定的网络根因或加速倍数。

## 当前行为与取舍

[操作入口](../README.md#队列重试和状态)维护完整用法。`wandb_preflight.py` 在独立上传环境中只读解析事务日志并查询云端；`log_sync.py` 只把允许上传的任务交给 core。

- 已有相同且无重复的 history：逐行比较本地字段和值，记录 covered 并跳过。covered 证明指标覆盖，不补证旧 system、console 或附件的完整性。
- 已有计数不一致、重复、缺行或冲突：停止该 run 的整份重传，保留证据；当前入口不裁剪云端历史、不删除原 run、不自动创建替代 ID。
- 新 run：完整记录且有退出记录才上传，完成标记和上传后云端核验都通过才记为 succeeded。非零退出码仍可以对应完整的失败训练日志。
- 中途快照：不联网，默认本地分析并等待新的完成快照。该限制替代旧的“先传完整前缀、下次再传整份文件”行为，避免制造无法安全撤回的追加。
- 网络/鉴权核验失败：停止当前轮次；不把查询错误当作 run 不存在，不尝试后续批次来消耗相同超时。

云端没有提供此工具可用的原子“检查并创建”锁；两台机器仍应避免同时 upload 同一 run。本机 worker 锁只保护本机。读取其他机器已经完成的数据后再跳过，解决的是顺序接管问题，不能宣称跨机器并发 exactly-once。

默认总时限仍为 900 秒，增加 120 秒无新 SDK 输出时限；重复进度行不重置计时。超时保留最后输出和 SDK 日志位置，可匹配时报告 DNS、TLS、代理、认证、限流等类别。无新输出是停止等待的策略，不是网络无传输的证明；静默大文件传输可以显式提高时限。

显式 `WANDB_NETRC` 覆盖环境 API key，entity/project 固定传入 SDK。本机曾有环境 API key 优先于预期 netrc 的情况，因此日志现在记录凭据来源，但不打印密钥。

## Mac 升级与恢复

取得这组源码修改后，保留旧队列与缓存，先做只读检查：

```bash
make sync-log-audit RUN=7rwc1ioz WANDB_NETRC="$HOME/.netrc"
make sync-log-upload RUN=7rwc1ioz RETRY=1 WANDB_NETRC="$HOME/.netrc"
make sync-log-status
```

audit 不上传、不修改任务结果、不同步 Git，但会产生本地核验报告。旧失败任务可能处于冷却或达到次数限制，`RETRY=1` 只让它重新核验，不允许跳过云端保护。E49/E50/E51 如果报告重复、缺行或值冲突，会保持失败并报告原因；无重复且所有本地行均被覆盖，才会接管为 covered。先单个 run 验证，再处理整个队列。

```bash
make sync-log-upload RETRY=1 WANDB_UPLOAD_JOBS=1 WANDB_NETRC="$HOME/.netrc"
```

不要删除 `.git/mirroropd-upload` 或 SDK 状态来解决重复；这只会丢失本机证据。已重复的云端历史应单独评估修复方案，当前科学分析继续以只读本地解码为依据。

## 验证范围

69 项自动测试通过，Ruff lint/format 与两篇维护文档的格式、链接检查通过。测试覆盖跨机器 history 接管、已有部分 run 阻止重放、冲突与重复计数、鉴权失败不写云端、完成标记后的再次核验、显式 netrc 优先级、静默及重复输出超时、原始文件不变，以及旧队列和 Git 操作。测试使用本地 Git bare 仓库、假的上传 CLI 与可控云端响应；不以模拟测试代替 Mac 网络验收。

真实云端检查只读比较已有实验，既不重新上传也不删除 run。宽评测 schema 单独限定实际 step 窗口；普通训练 schema 批量读取。这样避免把两千多个评测字段展开到每一条训练记录，也避免小分页在稀疏评测之间发出大量空请求。实测结果见 [结构化验证摘要](../benchmarks/2026-10-29-wandb-sync-guard.json)；历史新 run 上传性能仍保留在 [2026-10-23 验证记录](2026-10-24-W&B上传重构与本机验证.md)。
