# LiveCodeBench 判分内存故障、隔离实验与实施方案

更新日期：2026-10-22。范围是 MirrorOPD 的 TACO / LiveCodeBench（LCB）本地代码判分。结论依据用户提供的 code run 日志、当前与固定上游源码、独立 CPU 实验和本地 LCBv6 的 175 道题；以下数据保留实现前的实验快照；隔离判分器现已接入，使用方式和验收见[实现与使用](2026-10-22-隔离判分器使用与验收.md)。未启动 GPU 训练，也未重放导致开发机故障的未知答案。

## 1. 方案选择

推荐将判题规则与执行环境分开：**保留现有 LCB 的代码提取、输入解释和答案比较，在不导入 verl/Torch/Ray 的独立 Python 进程中执行；由外部监督者控制每个任务的内存、总时限、输出容量和全节点并发。**

有可委派 cgroup v2 的开发机优先采用每任务 cgroup 内存限制；没有权限时采用轻量进程、地址空间兜底、进程树 RSS 监控和进程组清理。仅把 `reliability_guard()` 改为 `reliability_guard(4 GiB)` 不适合作为当前 spawn 路径的默认补丁：实验中完整导入 verl 后，虚拟地址空间已超过 5 GiB，设置 4 GiB 会让简单程序因 pandas 动态库无法映射而失败。

这里选择的是资源故障隔离方案。它没有提供文件系统、网络和系统调用的完整安全隔离；对更强的安全要求，应另行采用受限制的原生执行账户、namespace/seccomp 或受管执行服务，不把 Python guard 或 cgroup 单独称为完整安全沙箱。

## 2. 故障证据与因果边界

用户日志对应 `code-full-sampled-20261021-232239-2568`：TACO 训练、LCBv6 验证、DeepCoder teacher、共享八卡、每批一次更新、current advantage + vanilla。正常训练已记录到 step 39；随后在第 40 步验证时点附近处理窗口时退出。

| --- | --- |

| 进程内存榜 | PID 91804 为 Python 进程，日志报告 218.48 GB；完整命令被截断 |

## 3. 上游调研和源码继承

### 3.1 最直接的上游报告

LiveCodeBench PR #103 提议修复评测内存持续增长，作者报告 1 TB 主机也会受影响。修改包括传入 4 GiB 限制和加强进程终止。维护者担心固定内存限制改变判分结果；该 PR 查询时仍 open、未合并。它直接支持“内存上限缺失值得修复”，不证明 4 GiB 是所有运行环境和题目的正确默认值。[^lcb-103]

Issue #76 报告评测卡在尾部少量样本，关闭后仍有人反馈；讨论没有给出充分的具体触发程序，不能把它当作本次事故的根因证明。[^lcb-76]

Issue #160 讨论 binary stdin/stdout mock 的判分差异。它说明资源层重构后仍须保持或单独审计判题语义；不能把升级 runner、修 binary I/O 和修改资源预算混成一个“等价的性能修复”。[^lcb-160]

### 3.2 三层代码保留了同一个空参数调用

引用链是 LiveCodeBench `998c52d394b836f15fff3b9a29866191108ff81b` → One-Shot-OPD `6b6b1782cc3f04749dd077de19353f839f6bc048` → 本仓 `verl/utils/reward_score/one_shot_opd/code_eval_v2/_lcb_runner.py`。上游及本地均在注释声称限制 4 GB 的位置调用 `reliability_guard()`；函数默认 `maximum_memory_bytes=None`，只有传入数值才设置 `RLIMIT_AS/RLIMIT_DATA`。[^lcb-source][^oneshot-source]

[本地 runner](../../../../verl/utils/reward_score/one_shot_opd/code_eval_v2/_lcb_runner.py)的 guard 与固定 One-Shot-OPD 版本经 AST 对比一致。迁入提交为 `a752bc196`。调研只读现有源码；开发机仍需确认实际部署版本。

[包装器](../../../../verl/utils/reward_score/one_shot_opd/code_eval_v2/__init__.py)改造前每个 completion 建立一个 spawn Manager 和一个 spawn 执行进程；父进程等待 `(timeout+1)×n_cases+5` 秒，并在 finally 中执行 kill/join/close。已有清理逻辑应保留和测试，不机械复制上游 PR 的裸 PID kill。

改造前包装器丢弃了 runner 的 metadata，最终 reward 又丢弃 `_lcb_eval_single` 的细节，因此 WA、RE、超时、执行环境故障难以从现有日志精确区分。修复时应保留状态和关联 ID。

### 3.3 超时、内存和进程生命周期是不同约束

`SIGALRM` 处理依赖 Python 主线程的信号检查点，不能限制内存；部分长时间 C 操作还可能推迟 handler 执行。外部监督者必须能直接终止执行进程。[^python-signal]

`RLIMIT_AS` 限制虚拟地址空间，不等于实际常驻内存（RSS）；共享库映射、预留但未触页的 mmap 都消耗地址空间。它适合作为轻量执行器的兜底，不能用相同数字替代 RSS 或 cgroup 内存预算。[^python-resource]

Ray 负责它管理的 worker；调用者仍须管理自行创建的子进程。Ray 默认退出清理机制的适用条件与递归范围有限；不能把“父 actor 死亡”视为所有执行子进程必然已回收。[^ray-child]

## 4. 实验设计和资源边界

主脚本为 [benchmark_isolation.py](scripts/benchmark_isolation.py)，执行器对照为 [benchmark_transport.py](scripts/benchmark_transport.py)。两者均为报告配套探针，未注册为 reward backend。

运行环境为 Linux 5.15、Python 3.12.11、NumPy 2.3.5、pandas 3.0.6、PyArrow 26.0.0、psutil 7.2.2。主实验只从文件目录导入现有 runner 和 import prelude，避免训练依赖；执行器对照另测真实 `_lcb_eval_single`。BLAS/OMP 等线程数固定为 1，GPU 对探针不可见；同机其他 CPU 负载没有被隔离，耗时只作局部工程证据。

| 策略标签 | 研究干预 | 实验保护 |
| --- | --- | --- |
| baseline | 保持 runner 的默认 guard 和输出捕获 | 外部 1 GiB 地址空间、CPU/墙钟时限、独立进程组 |
| as256 | 显式传入 256 MiB 地址空间限制 | 同上；此限制发生在导入与 fixture 载入之后 |
| rss256_output | 5 ms 轮询进程树 RSS，超过 256 MiB 时 kill；限制输出 | 同样保留外部 1 GiB 地址空间保护 |
| cgroup256_output | 单任务 `memory.max=256 MiB`、swap=0、oom.group=1、pids=32；限制输出 | 仅创建自己的临时子 cgroup，结束后回收；一核 CPU 配额 |

“baseline”只指不施加候选限制；为避免复现危险的大内存事故，所有压力实验仍有独立上限。因此这些实验不测 218 GB 分配过程，也不能预测无上限程序最终会分配多少。

压力用例覆盖快/慢增长到 384 MiB、64 MiB 输出、普通死循环、主动忽略 alarm、512 MiB 虚拟地址预留及正常 NumPy/pandas 程序。兼容性用例包含预期 WA/RE/语法错误和 binary stdin；后者用于暴露原判分器已有的接口限制。

真实数据校验使用本地 175 题 LCBv6，选取索引 0、2、3、4 的四个手写正确参考程序，覆盖乘法表、平方和、数位计数和区间事件累计，共 173 个测试 case。程序只实现题意，没有读取预期答案或按测试输入查表。该子集不是模型生成答案分布，不能用通过率推出整个 benchmark 的无误判保证。

主矩阵每个配置/用例执行一次；吞吐实验固定 12 个相同的简单任务，分别限制并发为 1、2、4，每种两轮。真实包装器在导入后连续调用三次。实验数据保留逐次记录，不把这些少量重复当作统计显著性证明。

内存同时区分进程 RSS、虚拟地址空间和 cgroup charge。当前内核没有 `memory.peak` 文件，cgroup 峰值来自 `memory.current` 采样，真正的 OOM 判定来自 `memory.events`；采样峰值可能漏掉瞬时峰值。`ru_maxrss` 在这条派生进程路径观察到继承高水位影响，保留原始值但不拿它作为当前解释器实际峰值，采用 `/proc` VmHWM 和监督者采样。

## 5. 实验结果

### 5.1 资源策略矩阵

[isolation-results.json](data/isolation-results.json)记录 17 个用例 × 4 种策略，共 68 次执行。表中的“失败”保留 runner 的原始返回，不将所有失败都重新解释为 MLE。

| 用例 | baseline | AS 256 MiB | RSS 256 MiB + 输出限额 | cgroup 256 MiB + 输出限额 |
| --- | --- | --- | --- | --- |
| 加法、NumPy、pandas 三个正常程序 | 全部 PASS | 全部 PASS | 全部 PASS | 全部 PASS |
| 四道真实题的手写参考程序，173 个 case | 4/4 PASS | 3/4 PASS；第 4 题 MemoryError | 4/4 PASS | 4/4 PASS |
| 分配并持有 384 MiB，快/慢两种 | 完成分配并返回 PASS | 失败，但缺少稳定的 MLE 分类 | 外部 RSS_LIMIT | 内核 CGROUP_OOM |
| 输出约 64 MiB 无效文本 | 收集后判错 | 失败 | OUTPUT_LIMIT | OUTPUT_LIMIT |
| 普通死循环 | case timeout | case timeout | case timeout | case timeout |
| 忽略 alarm 后死循环 | 外部 WALL_TIMEOUT | 外部 WALL_TIMEOUT | 外部 WALL_TIMEOUT | 外部 WALL_TIMEOUT |
| 预留 512 MiB 虚拟地址、另申请 8 MiB | PASS | 失败 | PASS | PASS |
| 正确的 binary stdin 加法程序 | 失败 | 失败 | 失败 | 失败 |

忽略 alarm 的程序在四组都由研究脚本的外部 3 秒时限终止；这验证外部 watchdog 能工作，不表示原生产包装器已有 3 秒总限制。正常死循环仍由原 runner 的单 case alarm 处理。

第 4 道真实题在 baseline 的进程 RSS 采样峰值约 234.17 MiB，低于 256 MiB；AS 256 MiB 却失败，因为运行时地址空间还包含其他映射。它证明 AS 和 RSS 预算不可互换，不证明生产应该只给 256 MiB。

Binary stdin 的失败是原 runner 缺少 `.buffer` 支持的既有行为。推荐资源方案保留了这个失败，说明“判分与原版一致”不等于“原判分器没有 bug”；完整协议修复要另做对照。

### 5.2 真实内存、采样超调与输出峰值

| 观测 | 数值 | 解释 |
| --- | ---: | --- |
| baseline 快速分配的进程 RSS 采样峰值 | 496.48 MiB | 包含解释器、依赖和 384 MiB 工作负载 |
| RSS 监督触发时的已观测峰值 | 272.08 MiB | 超过 256 MiB 约 16.08 MiB；5 ms 轮询存在超调 |
| cgroup 快速分配的 memory.current 采样峰值 | 255.46 MiB | 内核记录 oom/oom_kill；文件峰值接口不可用 |
| 同一次 cgroup 运行的进程 RSS 采样峰值 | 315.58 MiB | RSS 与 cgroup charge 不同，不能据此声称内核约束失效 |
| baseline 大量输出的 VmHWM | 300.88 MiB | StringIO 和后处理将输出转为实际内存占用 |
| 输出限额下的 VmHWM，RSS / cgroup 两组 | 127.06 / 128.41 MiB | 限额在累计输出超过预算时立即终止 |

共享库等共享页的 RSS 与 cgroup charge 归属不同，因此 cgroup=256 MiB 不意味着 `/proc` RSS 必然小于 256 MiB。这里依靠独立组的事件计数和终止事实确认保护；对整棵任务树的节点预算，仍要测量其实际 charge 和共享数据生命周期。

同样地，轮询峰值可能漏掉瞬时增长；RSS 监督得到的 272.08 MiB 只是已观测值，不是保证的最高超调。

### 5.3 改造前 spawn 包装器的成本与 4 GiB 误判

[transport-results.json](data/transport-results.json)使用同一原生环境直接调用改造前的 `_lcb_eval_single`。输入只是两个加法 case，parent 首次导入之后连续执行三次：11.217、11.542、11.140 秒，均通过，平均 **11.300 秒/答案**。观察到最多四个进程，包括 parent、执行子进程及 multiprocessing 辅助进程。

完整导入后 RSS 约 **734 MiB**，VMS 约 **5249 MiB**。这并非申请了 5 GiB 实体内存；它解释了直接设置 AS 4 GiB 的风险。独立对照保留完整导入、仅给 guard 加 4 GiB，随后正常的加法/小缓冲程序返回 `failed to map segment from shared object`，失败发生在 pandas 导入阶段。

轻量路径使用同一 runner，但不导入训练包。简单任务的单次端到端为 baseline **1.299 秒**、RSS 方案 **1.307 秒**、cgroup 方案 **1.306 秒**。任务包含新解释器启动和依赖导入；这三个值各为一次主矩阵测量，重复吞吐证据见下一节。

耗时差支持优先移除重复训练依赖导入和 Manager 协议开销。两条路径的启动/资源配置并非完全相同，尚未用 profiler 分拆每个组件；不能把观察到的约 8.6 倍差值全归到 Manager，更不能声称整个 38 分钟验证会快 8.6 倍。

轻量 worker 原型从独立文件路径加载同一 runner。生产中若仍通过 `python -m verl...` 启动，就可能重新引入训练包导入，不能仅因文件名叫 CLI 而认为优化已成立。

### 5.4 并发与清理

RSS+输出方案，每轮固定 12 个简单任务，每个并发档位两轮，72 次任务全部 PASS：

| 全局执行槽 | 每轮墙钟均值 | 两轮合计任务吞吐 | 子进程 RSS 求和的观测最大 |
| --- | ---: | ---: | ---: |
| 1 | 15.925 s | 0.754 答案/s | 113.14 MiB |
| 2 | 8.004 s | 1.499 答案/s | 225.14 MiB |
| 4 | 4.066 s | 2.951 答案/s | 446.95 MiB |

这组负载以解释器/依赖启动为主，不能用它选择真实 LCB 的最佳 C=4/8/16；它验证显式执行槽能约束在途进程并让内存随并发受控增长。RSS 求和会重复计入共享页，不是节点真实物理占用增量。

独立 helper 实验里，只终止父进程后，后代仍在运行；终止自有进程组后，后代不再运行。检查区分了运行进程与已退出的 zombie 状态。该 helper 没有主动 `setsid()` 脱离进程组，不证明进程组能处理任意逃离行为。正式资源域优先使用 cgroup，父 actor 崩溃后的回收还需独立监督者。

### 5.5 本地数据决定的预算边界

175 道题共有 **7000 个 case**，每题 case 数最少 2、中位数 43、最多 45。最大单个输入为 **4,355,536 字节**，最大标准输出为 **3,444,445 字节**，最大单题 ground-truth JSON 为 **32,048,935 字节**；全部题目 JSON 共 **289,726,919 字节**。

这些数值来自本地 parquet，不代表所有版本 LCB。1 MiB 输出限额会直接小于某个标准答案，不能使用。每 case 6 秒时，当前外层最大等待预算为 **320 秒**；若统一改成整题 60 秒，会改变多 case 题的执行协议。

没有本次故障答案和完整模型生成回放，因此还不能定量给出 4/8 GiB 内存预算的误判率，也不能确定 PID 91804 的分配是否来自输出缓存。

TACO 也经过同一 runner，但这里没有扫描 TACO 的完整测试数据或参考答案。资源隔离机制可以共用，具体输入、输出和时间预算需另行校准，不能将上述 LCB 分片的最大值当作 TACO 上限。


## 6. 候选方案的取舍

| 方案 | 优点 | 限制 | 建议 |
| --- | --- | --- | --- |
| 仅降低 RewardLoopWorker 数 | 改动小，降低并发峰值 | 单个异常程序仍可吃满节点；异步线程池可使实际执行并发大于 actor 数 | 只作临时减压措施 |
| 在现有 spawn 路径直接加 4 GiB AS | 容易添加 | 完整训练依赖已有超过 5 GiB VMS，已复现简单程序误判 | 不采用 |
| 轻量进程 + AS + RSS 监督 | 无需 cgroup 管理权限，部署较容易 | RSS 是采样，存在超限和扫描竞态；AS 仍有虚拟映射限制 | 无权限时的退路 |
| 轻量进程 + 每任务 cgroup + 外部时限/输出预算 | 内存约束覆盖整棵继承进程树；OOM 原因可由内核计数确认 | 需要委派权限；共享页与页缓存 charge 不等于 RSS | 目标环境允许时首选 |
| 保留 LCB 判题逻辑，外置原生执行服务 | 能把 CPU 判分资源与训练节点分开管理 | 服务运维、请求传输与协议对齐有额外成本 | 单机方案不足时演进 |
| 直接切换 SandboxFusion judge | 已有执行和资源隔离能力 | 标准输入、比较规则、超时和依赖可能改变，不能假设分数等价 | 需要独立兼容性验收后再考虑 |

SandboxFusion 官方说明提供执行环境隔离和 cgroup 资源限制，但能力依赖实际启用的隔离模式。仅在 Hydra 中出现 `sandbox_fusion.memory_limit_mb` 不会自动限制我们的自定义本地 runner。未部署或实测 SandboxFusion 服务，表中没有为它虚构速度。[^sandbox]

## 7. 推荐实施方案

### 7.1 一次请求对应一个可回收的轻量进程

保留当前 `reward_func` 外部接口，内部将代码、题目测试和必要上下文交给轻量 CLI。CLI 按文件入口启动，不通过 `python -m verl...` 导入训练包；runner 依赖范围限制为标准库、NumPy、pandas。控制消息通过有界 JSON 或单向 Pipe 传输，不为每条答案创建 Manager 服务。runner 文件仍保留来源许可证。

每个 completion 使用新进程。暂不复用执行过生成代码的解释器：`reliability_guard` 会修改模块和进程全局状态，生成程序也可能污染后续任务。若未来采用预热 fork server，必须单独审计线程、BLAS、CUDA 继承和跨任务状态，不能因启动快就直接启用。

监督者先创建任务资源域，再让子进程进入资源域，随后读取 fixture、导入依赖和执行答案。资源限制覆盖 JSON 解析和 import 阶段；不能等模型代码开始后才限内存。监督者持有资源管理权限，执行程序不得拥有写入父 cgroup 或迁移自身的权限；受控探针的 root 环境不作为生产权限设计。`Popen(start_new_session=True)` 建立自有进程组；限制代码在新解释器内执行，避免在 reward 线程中使用 `preexec_fn`。[^python-subprocess]

### 7.2 内存预算及没有 cgroup 权限时的退路

建议首轮候选配置为每任务 cgroup 4 GiB、swap=0、pids=64，并保留每 case 6 秒的既有时间协议。**4 GiB 是待回放验证的资源预算，不是实验证明的全数据最优值；主压力实验使用 256 MiB 是为了低成本暴露机制。** 对被判 MLE 的样本，在独立回放队列用 8 GiB 复核，报告预算敏感性，不在训练内部自动无限加大额度。

监督者应获得一个专门委派的父 cgroup，只创建和删除自己的子目录，不修改训练父组或其他任务的配置。设置失败应在启动验收阶段暴露，禁止捕获异常后悄悄无上限执行。内核没有 `memory.peak` 时允许用采样作辅助，不影响依靠 `memory.max` 和事件计数执行限制。cgroup 的控制范围、临时超限与 OOM 行为按内核定义解释。[^cgroup]

若开发机没有 cgroup 权限，先使用轻量进程的 AS 8 GiB 兜底、RSS 4 GiB 外部监督、全局并发上限和独立进程组。两个数对应不同资源；8 GiB AS 必须在目标依赖环境核对基线 VMS。RSS 轮询不能提供硬内存上界，要留出快速分配的超调空间，也不能宣称等同于 cgroup。实验未验证这组生产量级参数。

### 7.3 输出预算由真实测试数据校准

候选逐 case stdout 预算为：

$$
B_{\mathrm{out}}=\max(8\ \mathrm{MiB},\ 4B_{\mathrm{expected}}+64\ \mathrm{KiB}).
$$

其中 $B_{\mathrm{expected}}$ 为该 case 预期输出的 UTF-8 字节数，stderr 另设较小的诊断预算。主实验为简化实现，采用一题内最大 expected 长度生成该题统一预算；生产实现建议按 case 刷新计数，避免累积全部 case 输出。

预算是执行协议的一部分，应保存到结果中。超限返回 OUTPUT_LIMIT，不能截断输出后继续判为通过。大量可忽略空白也会消耗预算，因此需回放实际模型答案验证；“所有标准答案均小于预算”并不足以证明所有合法输出形式都不会被拒绝。限制应用于 StringIO 和最终诊断通道；若另有原生 fd 输出，也需有界读取，不能让 `communicate()` 无限制缓冲。[^python-subprocess]

### 7.4 超时、退出和结果分类

保留每 case 6 秒。总执行时限先沿用原 `(6+1)×n_cases+5` 秒，另记录依赖初始化时间并设置独立启动超时。不要在隔离修复中顺带把整题改成 60 秒，避免多 case 题的评测协议变化。

外部 watchdog 独立于生成程序的 signal handler；超时或取消后终止整个任务 cgroup，随后回收直接子进程并确认组内没有运行进程。无 cgroup 时终止自有进程组，并检查后代；进程组不覆盖主动脱离会话的程序，这个边界要明确保留。父 actor 异常退出时，由独立监督者的 lease/心跳或所属 cgroup 清理负责兜底，不能只依赖父进程 finally。

| 结果类别 | 对训练/评估的处理 |
| --- | --- |
| PASS / WRONG_ANSWER | 正常判分 |
| RUNTIME_ERROR / SYNTAX_ERROR | 按既有失败结果处理，保存原因 |
| TIME_LIMIT / MEMORY_LIMIT / OUTPUT_LIMIT | 按明确资源协议计失败，并单独计数 |
| 启动失败、依赖 import 失败、协议损坏 | 环境故障；报错或有限重试，不静默当作答案错误 |
| 超时取消后仍有运行后代 | 执行器故障；停止继续接收该资源域任务 |

尽量用外部证据分类：`memory.events.oom_kill`、父进程 watchdog、输出计数器；不能见到 exitcode=-9 就一律归为 MLE，SIGKILL 也可能来自超时或取消。对于 rlimit 触发但被 runner 捕获成普通异常的情况，需保留 exception type；当前错误字符串可能为空，无法可靠事后分类。

### 7.5 全节点并发和数据搬运

限制对象是正在执行的 completion 数，不是 Ray actor 数或线程数。可以用每节点监督服务管理固定执行槽；若每个 RewardLoopWorker 自己持有 Semaphore，其额度之和必须仍受节点级预算限制。进入执行槽之后再启动进程、解析大测试数据，避免排队任务提前占用执行内存。

令 $M$ 为训练容器实际内存上限，$B$ 为稳态训练与验证数据的基线占用，$H$ 为保留余量，$L$ 为每个执行槽的内存预算，则候选并发满足：

$$
C\leq\left\lfloor\frac{M-B-H}{L}\right\rfloor.
$$

这只是内存约束，还要满足 CPU 预算。必须读取相同 cgroup 口径的 $M,B$；现有 `psutil.virtual_memory().used` 可能是宿主机口径，不能直接代入容器预算。没有开发机基线测量前，建议先验收节点级 C=4，再测 C=8；不把每个 actor 的默认线程池容量当作推荐并发。

同一道题的 16 条回答可以复用只读测试输入的序列化文件，在执行进程内按需读取；不要把 16 份完整测试对象常驻在等待队列。JSON fixture、stdout 和诊断各有容量上限，且临时文件在完成/失败路径都清理。该数据复用尚未做吞吐实验，先测量再优化。

### 7.6 必须保留的诊断

每个任务保存 run/step、训练或验证阶段、数据集、题目 ID、sample ID、执行 PID/父 PID/cgroup、排队和启动/执行耗时、测试 case 数、实际资源配置、退出状态与原始错误分类。峰值内存明确标注 RSS、VmHWM 或 cgroup charge；不混用。

结果要能关联到原始生成记录，但常规日志不复制完整隐藏测试或答案。开发机事故的关键缺口是“PID → 题目/答案”关联；只增加总体 CPU memory 曲线无法补上这个缺口。

## 8. 实施阶段和验收

| 阶段 | 交付 | 通过条件 |
| --- | --- | --- |
| A：离线执行器 | 轻量 CLI、状态协议、配置能力检查 | 正常 stdin/function 用例与原 runner 一致，环境错误不被计为 WA |
| B：资源隔离 | cgroup 首选后端和明确的无权限退路 | 快速分配、忽略 alarm、大量输出、取消与后代清理均受控 |
| C：完整回放 | 保存的真实模型答案，固定题目与代码 | 按题目比较判分差异；对 MLE/OLE/TLE 单独复核；记录 4/8 GiB 敏感性 |
| D：训练接入 | 相同 reward 接口与节点级执行槽 | 先完整跑过一次 175×16 验证，再覆盖下一次验证；没有失联子进程和持续内存增长 |
| E：性能调优 | C=4/8/16、执行槽与只读测试数据复用 | 等答案、等测试、等资源协议，报告判分吞吐与完整验证墙钟 |

尚未完成 C–E，也没有重放 PID 91804 对应程序。四道手写参考题通过，只能支持有限兼容性；binary stdin 的既有失败还需要独立的 judge 修复与分数重评。生产方案的优先顺序来自已测资源隔离和依赖成本，不声称已经得到完整 LCB 最佳准确率/吞吐配置。
