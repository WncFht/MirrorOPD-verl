# OPD 上游优化与 GPU 调度调研

核对日期为 2026-10-20。检索 verl issue/PR 的 OPD、distillation、teacher、hybrid 主题，并检查相关评论、文件 diff、合并时间和本仓 Git 祖先关系。状态依据 GitHub REST 的 `state` 与 `merged_at`，元数据保存在 [reviewed-status.json](data/upstream-opd-20261020/reviewed-status.json)。`closed` 不等于已合并，历史合并也不等于当前功能仍然保留。

本项目当前是 V1 sync、FSDP2、独立 vLLM teacher、sampled-token `k1 + PG`。评价上游方案时分别检查：资源池是否共享、trainer 是否匹配、backend 是否匹配，以及是否改变蒸馏目标。运行时 metadata 报告的是旧 commit，未取得其工作区 patch，因此本仓代码用于确认当前实现结构，不能作为历史运行逐行相同的证明。

## 直接结论

上游确实写过 teacher 共卡、动态借卡、FSDP teacher 和 OPD profiling，并非没有遇到过利用率问题。此前只强调“当前 V1 同步路径没有共享 teacher 开关”不够完整：历史主线曾合入 teacher 共置，后来又删除；现在也有尚未合并的新实现。

最接近当前需求的是 #7058 的 trainer/teacher fusenode 和 #6920 的 FSDP teacher，但二者都有适配限制。已经合并、且本仓包含的 #7373 / #6556 解决的是空闲训练卡借给 student rollout，不能自动借用 teacher 卡。#7307 的共享则发生在多个 teacher 之间，对当前单 teacher 不能产生相同收益。

### #5745 → #6039：曾经支持，后来移除

#5745 区分了两种共置：一种是 teacher/student 推理副本同时留在同池，双方显存都受限制；新方式则让 student 先生成并 sleep，再唤醒 teacher 批量打分。它还提供过 8 卡共池的配置及对照图。随后 #6039 明确删除该模式，保留独立 teacher。

删除 PR 的正文没有说明充分原因，评论中也有人追问；已读取的评论没有提供维护者解释。因此不能编造“因为太慢”或“因为不稳定”作为删除原因。能确认的是功能生命周期与当前源码状态。[^colocate-old] [^colocate-remove]

### #7058：最接近 teacher/actor 共卡，但不是 FSDP2 即插即用

旧 #6914 的维护者意见要求把 teacher 计算能力从 experimental worker 移到通用 engine worker，以便同步 trainer 也能使用；作者随后转向 #7058。新补丁修改了 V1 trainer、worker 和蒸馏配置，并提供 V1 separate-async / fully-async 示例。

代码中 fused 模式不再创建独立 teacher manager/pool；teacher 在训练侧得到整个 batch 后打分。V1 实现中的 `_compute_fused_teacher_log_probs` 明确要求 `actor.megatron.param_offload=True`，示例也是 Megatron trainer/teacher。它支持 sampled-token 路径，例如 k1，而非任意 top-k 路径都可直接使用。

对本项目可以复用的是 teacher 生命周期、TQ 数据注入、计时边界与资源池设计；需要另外适配 FSDP2。不能只把 PR 中的 fused 开关复制到现有配置。维护者还指出其中 legacy fully_async 目录将迁往 recipe，增加了整包移植的维护成本。[^fuse-old] [^fuse-new]

### #6920：FSDP teacher 不等于已经共享 GPU

该 PR 的模型正好是 DeepSeek-R1-Distill-Qwen-1.5B 与 JustRL-DeepSeek-1.5B，提供 frozen forward-only teacher 和 `gather(logits, ids) - logsumexp(logits)` 的分块实现，适合取得 student 指定候选 token 的概率。

但它主要修改 `ray_trainer.py`，没有直接接入我们当前的 V1 trainer。其示例注释提到共置，实际初始化代码仍通过 `get_resource_pool(Role.TeacherModel)` 取得 teacher pool，并把 teacher worker 注册到该 pool；该 head 的 `main_ppo_v0.py` 仍新建独立 teacher_pool 并映射 Role.TeacherModel。按这条资源映射，示例的 student=8、teacher=8 会申请 16 张卡，不能当作单机 8 卡共享。不能仅根据 FSDP teacher 或示例注释判断物理卡是否复用。

它还同时引入 `reverse_kl_topk`，与当前 sampled-token k1+PG 不同。若参考该 PR，应只提取 teacher forward/gather 与资源管理部分，保留当前 loss。[^fsdp-teacher]

## 多 teacher 共享与 full-vocabulary 优化

| 工作 | 核对状态 | 解决的问题 | 当前优先级 |
| --- | --- | --- | --- |
| #7307 multi-teacher shared GPU group | Open，未合并 | 多个 teacher 使用同一 teacher pool；CPU offload、KV 释放、按需唤醒、LRU/pin 管理 | 当前只有一个 teacher，不能自动把 teacher 卡给 student |
| #6705 single-pool hidden-state OPD RFC | Open issue | Teacher 权重切换、hidden state 经 TQ 传输、student 重建全词表分布 | 是系统设计提议，尚不是当前可用配置 |
| #6194 Nitrobrew | Open，未合并 | 传 hidden state、融合 full-vocab KL，降低大词表通信/显存成本 | 对 full-vocab 更直接，当前 k1 不是该瓶颈 |
| #6511 fused top-k kernel | 2026-05-29 合并，本仓包含 | 融合 top-k 蒸馏输出与 loss | 当前 k1 不走该专用 top-k 分支 |
| #6848 top-k 显存修复 | 2026-06-30 合并，本仓包含 | 减少 forward_kl_topk 的中间张量占用 | 已包含，不能再次计作新增提速 |
| #7855 tail-aware top-k KL | 2026-10-20 合并，本仓未包含该合并提交 | 增加 top-k 尾部质量处理，改变蒸馏目标 | 不应作为纯 pipeline 优化直接并入 |

这些方案分别见对应 issue/PR。[^shared-teachers] [^hidden-rfc] [^nitrobrew] [^fused-topk] [^topk-memory] [^tail-kl]

#7307 的池共享范围是 teacher 与 teacher，不是 student 与 teacher。它通过控制同时 awake 的 teacher 数量降低多 teacher 的常驻显存与资源占用；当前单 teacher 并没有多个模型可换出。

Full-vocab/hidden-state 方案也有明确适用范围。按约 40 万有效 token 粗算，单个 FP32 sampled log-prob 的理论 tensor payload 仅约 1.5 MiB；BF16、hidden=1536 的 hidden state 则约 1.15 GiB。后者能替代极大的全词表 logits，但不会比当前单 token 概率更省。实际 HTTP/对象开销另算，这个估算不能当作端到端通信计时。

#6194 的评论重点要求复用现有 manager/replica 抽象、支持多 teacher，并讨论去掉额外的 SVD head 压缩。它是可参考的 full-vocab 实现，不是解决我们 teacher 等待 student 的直接开关。[^nitrobrew]

### 推理引擎与 FSDP teacher 的取舍

Issue #5731 直接讨论了 teacher 为何使用推理引擎，回复指出多 teacher 部署的灵活性。这个理由不等于已经证明当前 1.5B teacher 的独立四卡配置最优；讨论中也有人追问数值差异的消融。应比较的是同一 sampled token 输入下的概率、打分吞吐与资源占用，而不是假定某个后端天然更快或完全等价。[^teacher-engine]

#7373 PR 当时使用较早的 `separate_async.enable_switch` 路径；本仓当前字段是 `trainer.v1.separate_async.hybrid_rollout.enable_switch`。动态阈值决定先生成多少可训练 prompt group 再收回 GPU。官方对照使用多节点、35B-A3B 模型，不能把该加速比例直接套给本项目的 1.8B/8×A800。

### 值得测试的原生拓扑：4 张 hybrid + 3 张 rollout + 1 张 teacher

这是与“7 张 student FSDP + 1 张 teacher”不同的方案：

| 时段 | 4 张 hybrid GPU | 3 张独立 rollout GPU | 1 张 teacher GPU |
| --- | --- | --- | --- |
| Trainer 等待样本 | 临时参与 student 生成 | 持续生成 | 给已完成回答评分 |
| Actor 更新当前 batch | FSDP2 更新 student | 生成后续 batch | 可给后续回答评分 |
| 验证 | 切换为 student 生成 | 参与 student 生成 | 不参与验证 |

这样等待时最多有 7 张卡生成，更新时另外 3 卡仍可生成，teacher 也不必因 actor 更新而完全空闲。Actor DP 仍为 4，因此 batch=64、mini-batch=64 可以保留，不受 7 卡 DP 整除限制。

对应拓扑配置片段如下，已经检查当前字段和初始化约束；尚未做 GPU 训练验收：

```yaml
trainer:
  n_gpus_per_node: 4
  v1:
    trainer_mode: separate_async
    separate_async:
      parameter_sync_step: 1
      hybrid_rollout:
        enable_switch: true
actor_rollout_ref:
  hybrid_engine: true
  rollout:
    nnodes: 1
    n_gpus_per_node: 3
    checkpoint_engine:
      backend: nccl
distillation:
  n_gpus_per_node: 1
```

当前 `naive` checkpoint backend 不支持 separate_async，不能遗漏改为 nccl 等支持的传输方式。Hope 入口强制 4+4，也要在试验中改成这三组资源，总计仍是 8 卡。

该拓扑会引入预生成、partial rollout 和旧策略样本，需要重新验收 rollout correction/IS、staleness、独立验证长度和训练质量。它不是严格同步 OPD 的等价替换。配置中的验证题数、n、长度与频率保持当前值；实际服务该验证的 GPU 数会变化。[^dynamic-v1] [^v1-async]

当前 V1 `_rollout_server_managers()` 只枚举 student manager；teacher manager 没有这条 profiling start/stop 路径。即使给 teacher 配 `profiler.enable=True`，也不能认定已经录到 teacher trace。#7928 刚好针对这个缺口，但没有合并。

本 run 的 `global_profiler.tool/steps` 均为 null，logger 只有 console/wandb，没有启用 RLInsight。GPU busy 的系统采样不是 kernel trace；“代码里有 per-request metrics”也不等于这些字段已进入 W&B。当前数据的可量化结果与缺口见[流水线审计](2026-10-20-OPD流水线组件与阶段审计.md)。

## 更新与同步阶段的近期性能反馈

Issue #7847 报告了另一套 Qwen3.5-9B / 8×B200 配方在 actor update 中出现明显 GPU 空档，后续关闭并转到 #7833 保留测量。这说明 token budget、micro-batch 与通信安排值得用 trace 检查；它不是我们这套 A800 / 1.8B 的实测证据，不能套用其空闲比例。[^actor-idle]

Issue #7848 指出 pre-resume 的 cache cleanup 可能拖慢共置权重同步，评论要求提交 PR，随后作者表示已提交。当前快照不能仅凭 issue 已关闭就判断具体修复已进入本仓。对我们的相关指标是 update_weights，均值约 2.09 秒、只占训练 step 的 1.44%；应先定位，再决定是否值得优化。[^cache-cleanup]

## 当前决策

先把已经包含的性能修复与尚未实现的调度方案分开，避免为一个不存在的开关升级整套环境。固定验证预算下，优先采集当前瓶颈所需的细计时与请求队列；测试 CUDA Graph、7+1，以及连续投喂请求的调度。若选择跨 batch 重叠，原生 V1 4+3+1 值得与同步方案对照；若坚持严格同步，则参考本地 One-Shot-OPD / #7058 设计共享 teacher，但要保留 FSDP2 与当前 k1+PG。

本轮只完成调研、数据审计与可复现分析，没有切换 trainer、应用上述未合并 PR 或修改正式训练参数。
