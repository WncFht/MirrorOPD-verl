# E92：Qwen2.5-1.5B SFT 与 RFT teacher 吸收对照

状态：实验设计，尚未开训。本实验比较从同一 Qwen2.5-1.5B Base 分叉得到的数学 SFT 与 RFT teacher，是否能被同一个 Base student 以相同 OPD 预算吸收。RFT 不是跨论文统一的单一算法名：UFT 用它表示 _Reinforcement Fine-Tuning_；DeepSeekMath 则将 _Rejection Sampling Fine-Tuning_ 缩写为 RFT。本文沿用 UFT 的前一种含义，指 verifier-rewarded、当前策略采样的强化微调。[^uft-paper][^deepseekmath]

## 模型与阶段来源

| 角色              | 固定权重／来源                                                                                                                                                 | 训练路径                                                                                             |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 共同 student 起点 | `Qwen/Qwen2.5-1.5B`，revision `8faed761d45a263340a0528343f099c05c9a4323`[^base]                                                                                | 两个 OPD 臂各自从这份 Base 权重和 fresh AdamW 开始                                                   |
| SFT teacher       | 用下列固定 Base 及 UFT 数学数据、`algo=sft` 重建；公开参考权重 `liumy2010/Qwen2.5-1.5B-math-SFT`，revision `f27d59227c2f368a58f171715d65b8ba4099adfa`          | Base → 在 `data/math/train.parquet` 上最大化参考解答的 token log-likelihood                          |
| RFT teacher       | 用同一固定 Base、同一数学数据及 UFT 代码、`algo=rft` 重建；公开参考权重 `liumy2010/Qwen2.5-1.5B-math-RFT`，revision `017c647c24de8724ddb9b7eca2d863398a0c682f` | Base → 当前策略每题采样 4 条回答 → 数学 verifier 给 outcome reward → GRPO 更新；参考 KL 系数 `0.001` |

两份公开 teacher 模型卡都标注 `Qwen/Qwen2.5-1.5B` 为 base，且属于同一 UFT 数学任务；但卡片没有记录各自实际使用的 Base commit。为使 E92 的两个 teacher 确实从同一组权重出发，主实验应按下文固定 revision 和 UFT 代码重建 teacher。公开权重仅作流程与指标参考，不能直接据它们声称精确初始化完全相同。[^sft-model][^rft-model]

重建使用 UFT 仓库 commit `1fda767dafdec06e37de4b2d83854c1becf45569`。公开脚本给出的共同配方是 seed 0、数学 train/test 划分、最大 prompt/response 各 1024 token、actor LR `1e-6`、train batch 256、总训练步数默认 500、每 25 步测试及每 100 步保存。SFT 用 microbatch 16、5 epochs；RFT 用 GRPO、每题 4 个 rollout、PPO minibatch 64、KL loss 系数 `0.001`，hint 概率设为 0，因而从 Base 直接做 verifier-rewarded RFT，不经过 SFT。执行时需把 UFT 的 `BASE_MODEL` 固定到上述 Base revision，并保存 resolved config、数据文件 hash、最终 checkpoint revision 和训练日志。公开脚本是重建配方；两张已发布模型卡没有证明发布权重确实使用了完全相同的 commit 与所有这些默认值。[^uft-code]

## OPD 训练设置

沿用 [MiMo E91 的学生侧预算与读出协议](2026-11-07-E91-MiMo-RL-Zero到SFT学生.md)，只将模型家族与 teacher 来源改为 Qwen2.5。两个 OPD 臂共用完全相同的 Base student checkpoint、题序、采样设置和优化器初始化；分别用 SFT teacher 与 RFT teacher 完整跑一遍，不从前一个 OPD 臂续训。

| 项目             | E92-SFT teacher 臂                                                                           | E92-RFT teacher 臂      |
| ---------------- | -------------------------------------------------------------------------------------------- | ----------------------- |
| Student          | `Qwen/Qwen2.5-1.5B` 固定 Base revision                                                       | 同左、同一权重文件      |
| Teacher          | 上节重建的 SFT teacher                                                                       | 上节重建的 RFT teacher  |
| OPD rollout 题池 | 冻结 `questions-v2` math/DAPO manifest，shuffle=false；前 2560 题                            | 同一 manifest、同一题序 |
| 每 outer rollout | 当前 student 每题 1 条；temperature=1、top-p=1、seed=42                                      | 同左                    |
| 目标与预算       | full-vocab reverse KL；20 outer、reuse=16、batch=128，共 320 updates                         | 同左                    |
| Optimizer        | AdamW、LR `1e-6`、weight decay `0.01`、gradient clip `1`；从 fresh optimizer 开始            | 同左、fresh optimizer   |
| 长度与精度       | prompt cap 2048、response cap 7168、context 32768；student master FP32，rollout/teacher BF16 | 同左                    |
| 执行资源         | 与 MiMo 相同的 4 卡 shared-sync 路径；teacher 与 student 串行复用 GPU 池                     | 同左                    |

Qwen2.5 与 MiMo 的 tokenizer、EOS/turn-end token ID 不同。E92 应从固定 Qwen tokenizer 和模型配置读取并保存 `stop_token_ids`，不能照抄 MiMo 的 `[151643,151645]`。题池和学生侧优化预算与 MiMo 一致，teacher 阶段、模型尺寸与 tokenizer 不同；所以结果适合比较同一协议下的吸收趋势，不能当作跨模型严格因果效应。

## 重复检测与验证

E92 的训练 rollout、`rollout.val_kwargs`、以及 `EvaluationCoordinator` 每个数学/代码/科学/指令评估协议都显式启用同一规则：`min_pattern_size=16`、`max_pattern_size=128`、`min_count=8`。也就是 16–128 token 的片段连续完全重复 8 次时停止当前回答。重复检测与模型 EOS/turn-end 停止并存，停止后保留已生成前缀及原样本，不丢弃或补采样。[重复检测实现与指标](../../../infra/rollout/repetition-detection.md)

按训练轨迹、固定 teacher-prefix、固定 Base-prefix 和未见四域分别报告 RKL；记录 position RKL、每步 loss before/after、四域 accuracy、回答长度、length/repetition/truncated/stop/unknown finish fraction，以及训练 `rollout/repetition_detection/enabled_fraction`。两个 teacher 银行各自对应各自 teacher 前缀；跨 teacher 的绝对 teacher-prefix RKL 不直接排难度名次。训练阶段还应记录两个 teacher 的训练步数、输入/生成 token 与 GPU 小时，说明 GRPO rollout 造成的额外计算量。

E91/E72、E92/E72 的比较要单列停止规则差异：历史 E72/E73 训练配置与评估协议均把 repetition detection 设为 `null`，E91 与 E92 按当前方案开启。E92-SFT 与 E92-RFT 两臂都开启，因此两臂间的 teacher 对照保持一致。
