# 四域正确率评测与 RKL 银行生成协议调研

核验日期：2026-10-31。本文维护论文的 n、采样参数、长度及 verifier 证据，不再重复维护执行顺序和频率。现行设置见[四域协议](../../experiments/teacher-transfer/protocols/online-four-domain.md)，代码与调度见[verl 接入方案](../../archive/engineering/evaluation/2026-10-31-四域接入设计.md)。

## 1. 生成产物与测量对象

Accuracy 的每题 n 条回答用于估计任务成功率；固定 RKL 银行从其中预先指定的题目与 sample0 保留原始 token。两者可以共用生成，不必有相同的评分条数。初始 current 与 initial bank 在权重、输入和采样协议一致时是同一读出；后续 current 与固定 bank 访问的状态不同，分别解释。

Sample index 由请求身份确定，不按完成顺序或正确率选择；增加 n 不应重新挑选 bank。RKL 始终比较 student→teacher，teacher 生成轨迹只改变前缀来源。保存原始输入和回答，不将 teacher 专用模板的回答重新拼到 student 模板后仍称同一轨迹。具体持久化和复用合同由工程页维护。

这些工作支持按 benchmark 配置 n，也表明不存在“所有任务统一 n4／统一 T0.6”的论文共识。最接近我们跨域研究的 Every Coin 提供一套直接可参考的异构 n；高预算模型报告可用于了解能力评测上限，不必整套迁入每个 checkpoint。

Qwen3 的 thinking 与 non-thinking 主表都报告 IFEval；Cascade 2 则明确选择 IFEval non-thinking、IFBench thinking。IFEval 并没有统一强制关闭 thinking 的评测规则。我们的 thinking／non-thinking 实验线应维持各自模式，不能只为提高 IF 成绩临时切换。若另测原生 non-thinking 最佳能力，应单列条件。[^qwen3][^cascade]

## 3. 每个 benchmark 的建议

### 3.1 n 与题量

用户已选择成本较低、接近 OPD 文献的 A 档；B 档仅保留为文献讨论中的增强候选，不进入当前配置。各 teacher、initial student 和训练后 student 在同一个 benchmark 上使用同一档位。

| Benchmark            | 正式全集候选题量 | A：RKL 主导的常规 accuracy | B：更低采样噪声的读出 | 说明                                                             |
| -------------------- | ---------------: | -------------------------: | --------------------: | ---------------------------------------------------------------- |
| MATH500              |              500 |                         n1 |                    n4 | 题目覆盖较大，Every Coin 的直接先例为 n1                         |
| AMC23                |               40 |                        n16 |                   n16 | 较小题库，用多次采样稳定均值                                     |
| AIME24／25／26       |          每年 30 |                        n16 |                   n32 | AIME24 的 n16 是向既有年度对称扩展的项目建议；n64 留给高精度专项 |
| LCB v5，既定日期窗口 |              279 |                        n10 |                   n10 | 报告采样 pass@1，不能改成“10 次至少通过一次”                     |
| GPQA-Diamond         |              198 |                         n4 |                    n8 | 文献存在 4／8／10 次，n4 先控制成本                              |
| IFEval               |              541 |                         n1 |                    n4 | strict prompt-level 为主；n1 仍可随机采样，不等于 greedy         |

RKL bank 仍每域 128 题、每题 1 条。如果 accuracy 使用全集，训练去污染保护清单也应覆盖 accuracy 全集，而不只覆盖 512 个 RKL 题目。Accuracy 若使用上述全集，A 档每模型每次完整评估生成 6,703 条回答，B 档 12,058 条；这两个数是生成次数，不是独立题数，也不是 RKL 必须评分的轨迹数。用户现已明确选择 accuracy 全集；每域 128 的抽样仅用于 RKL 银行。

现行协议在所有 accuracy 节点使用全集与 A 档 n；B 档增加 n 保留为文献候选。增加 n 减少生成噪声，不增加题目覆盖；30 题×64 次仍然只有 30 道题。

### 3.2 正确率如何聚合

设第 $i$ 题生成 $n_i$ 个回答，$V_{ij}$ 表示该回答是否正确。先求每题正确率，再按题平均：

$$
\widehat{\mathrm{Acc}}=\frac1N\sum_{i=1}^{N}\frac1{n_i}\sum_{j=1}^{n_i}V_{ij}.
$$

它估计的是单次采样成功率。不同 n 影响估计噪声，不把目标改成 best-of-n。Code 的 pass@1 可按此估计；pass@k 和多数投票是其他指标，当前不作为主指标。[^coin][^lcb]

跨数学子集先分别报告 MATH500、AMC23 和各年 AIME。若再给 Math 汇总，应预先确定逐题或逐 benchmark 等权，不能将所有生成回答直接混在一起，否则 n16 的题会比 n1 的题多占 16 倍权重。比较前后时保留逐题结果，按相同问题做配对统计；不要把同题重复回答当作独立新题。

GPQA 原始工作区分 Extended、主集与 Diamond；本项目保持 Diamond 身份，不能用同名其他 split 替换。[^gpqa]

### 3.3 验证器与输出处理

| Benchmark | 建议的评分合同                                                                                                                                |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Math      | 固定答案提取及 Math-Verify／等价验证器版本；使用最终答案，保留无法解析等失败类型；不按模型调提取规则                                          |
| LCB       | 固定 release、日期窗口、题目清单、starter code／stdin 模板和官方执行评测版本；一个答案必须通过要求的测试才算成功，不以通过测试比例代替 pass@1 |
| GPQA      | 生成式 CoT／最终选项正确率；固定选项置换和答案映射，逐模型使用同一题目表示；不把长思考生成分数与直接选项 log-likelihood 分数混称同协议        |
| IFEval    | strict prompt-level 为主，strict instruction-level 及官方 loose 口径可辅助；每条回答独立验证后平均                                            |

IFEval 原文的 strict prompt-level 要求一题中的所有约束都满足；loose 是补充指标，不代替 strict。[^ifeval] 科学答案提取也应固定实现，MegaScience 说明了仅依赖 boxed 提取所带来的漏判问题。[^megascience]

Thinking 模式须分别保留原始 response token 和可见最终答案。RKL 使用原始思考＋答案 token；verifier 使用事先定义的最终答案通道，不能任意删去不满足约束的内容。如果只有思考段而没有最终答案，应按固定失败规则记录，不能从思考中挑选一个有利片段。报告须注明这一项目协议；不同 IFEval 工具的原生行为需分别核对。

模型答错／解析失败与基础设施失败分别记录。题目和 bank sample 都不按评分结果过滤，避免把错误／截断的自然状态排除出 RKL。

## 4. 三篇 OPD 工作的解码证据

### 4.1 以 Semi-OPD、Every Coin 与 One-Shot 为依据的建议

| 工作         | 训练生成                                   | 验证生成                                     | 证据层级                                                                                    |
| ------------ | ------------------------------------------ | -------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Semi-OPD     | T1/p1，采样top-k表中未明确                 | T1/p1，采样top-k表中未明确                   | 论文附录 A 表 2；overlap@64 不是采样 top-k[^semi]                                           |
| Every Coin   | T1/p1/k=-1                                 | T1/p0.95/k=-1                                | 论文 B.3/B.4 明确给出[^coin]                                                                |
| One-Shot OPD | 公开配方默认 T1；基础 rollout 配置 p1/k=-1 | 公开配方默认 T0.7/p0.9，继承 validation k=-1 | 固定 commit 的脚本覆盖基础 YAML；不能只看 YAML 的 temperature0 就称其 greedy[^oneshot-code] |

现行协议选择 Every Coin 作为跨域采样基线，替代较早以 R1 官方 T0.6 为首选的建议；实际值由四域协议统一维护。三篇工作并不存在完全一致的评测解码参数，选择依据是任务覆盖与可复用性，不是将其称为论文共识。

One-Shot 公开配方的`VAL_TEMPERATURE=0.7`与`VAL_TOP_P=0.9`覆盖基础 YAML 的默认值，`do_sample=True`；采样 top-k 仍为 -1。核对 commit 为`6b6b1782cc3f04749dd077de19353f839f6bc048`，见[代码核验记录](data/benchmark-protocol-20261031/oneshot-decoding.json)。它是公开配方默认值，不将未公开的逐实验命令覆盖推断成相同。

这里的 top-k 只指生成采样；蒸馏目标的 top-k 或 overlap@K 不是同一个参数。我们仍计算原生全词表 RKL，不改成稀疏目标。生成 profile 决定访问哪些前缀，RKL 评分依旧用 T1，两者分别记录。

## 5. Valid response cap

### 5.1 原文能支持的判断

16K 有 G-OPD 的直接 generation 先例；32K 在 R1 与 Semi-OPD 中有直接先例；Qwen3 通常 32,768、AIME38,912；One-Shot OPD 的数学 31,744、代码 65,536。Every Coin 的 40K／64K／96K 是总序列长度，应单独理解。训练长度不能推导成验证长度。[^gopd][^r1][^semi][^qwen3][^oneshot][^coin]

DeepCoder 作者公开的 LCB 长度对照尤其相关：DeepCoder-14B 在 16K／32K／64K 下分别为 45.6／57.9／60.6，R1-Distill-Qwen-14B 为 50.2／53.0／53.0；在较短预算下两者的排名会反转。该表按作者的 K 单位与上下文设置报告，不能把它推广成所有 teacher 都需要 64K，但它明确说明截断会改变能力比较。[^deepcoder]

### 5.2 对本项目的建议

项目已选择公共 32K、训练与来源 7K，实际整数值及 bank 定义由四域协议维护。固定 bank 保留同一条完整回答，不额外增加前段／完整时域两套 RKL。公共长预算吞吐仍需验收。

64K 仅作为预先规定、双方都支持的独立长预算条件，不为少数 teacher 临时单方面放宽。IF 也不能因最终答案通常短就把 thinking cap 直接压到 1K／2K；Open-MOPD 的短 IF 训练 cap 不是其通用验证协议，Cascade2 的 IF 评估用 32K。[^openmopd][^cascade]

必须满足 prompt tokens＋response cap 不超过双方被验收的上下文。已读取的本地配置为：R1-1.5B `max_position_embeddings=131072`；Qwen3-1.7B／4B／8B 为 40960，均无显式 rope_scaling。这只提供配置容量依据，不能替代 16K／32K 吞吐与数值验收；32K 回答在这些 Qwen3 配置下最多留 8192 个 prompt token。证据见[本地配置记录](data/benchmark-protocol-20261031/local-context-configs.json)。

执行 32K 前应在预先选定的问题和代表模型上检查到顶率、最终答案缺失率及耗时。该诊断用于验收生成预算，不新增一组双时域 RKL 主指标；不能只挑答错样本或某个 teacher 表现不佳时才加长。Cap 一旦改变，应使用新的协议／bank 身份。
