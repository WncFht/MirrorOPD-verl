# DeepSeek-R1-Distill-Qwen-1.5B 的 MFU 计算

本文按当前仓库的 Qwen2 FLOPs 估算器推导 `perf/mfu/actor`，并把模型尺寸、batch、序列长度、GPU 数和计时边界分别代入。模型 FLOPs 利用率（Model FLOPs Utilization，MFU）衡量单位时间完成的模型有效计算量相对于设备理论峰值的比例；本项目记录的是 actor 更新阶段的局部估计。

## 模型结构与参数量

Student 的模型名是 DeepSeek-R1-Distill-Qwen-1.5B，实际 `model_type=qwen2`。模型名称中的 DeepSeek 表示模型来源和对话协议，FLOPs 计算按 Qwen2 架构进行。可复核的原始配置保存在 [student-config.json](data/student-config.json)，来源是本机对应模型的 `config.json`。

| 符号 | 含义 | 实际值 |
| --- | --- | ---: |
| $L$ | Decoder 层数 | 28 |
| $H$ | Hidden size | 1536 |
| $I$ | SwiGLU intermediate size | 8960 |
| $A$ | Query attention heads | 12 |
| $K$ | KV attention heads | 2 |
| $d_h=H/A$ | 每个 head 的维度 | 128 |
| $V$ | Vocabulary size | 151936 |
| — | Embedding 与 LM head 共享权重 | False |
| — | Sliding-window attention | False |

这是分组查询注意力（Grouped-Query Attention，GQA）：12 个 query head 共享 2 组 K/V。Q 投影宽度为 1536，K 和 V 投影宽度各为 256，O 投影把 1536 映射回 1536。

每层的 attention 矩阵参数数目为：

$$
\begin{aligned}
P_{\rm Q}&=1536\times1536=2{,}359{,}296,\\
P_{\rm K}=P_{\rm V}&=1536\times256=393{,}216,\\
P_{\rm O}&=1536\times1536=2{,}359{,}296,\\
P_{\rm attn,layer}&=5{,}505{,}024.
\end{aligned}
$$

SwiGLU 包含 gate、up、down 三个矩阵，每层为：

$$
P_{\rm MLP,layer}=3HI=3\times1536\times8960=41{,}287{,}680.
$$

Embedding 和 LM head 不共享，因此各有 $VH=233{,}373{,}696$ 个参数。verl 估算器使用的矩阵参数总量为：

$$
\begin{aligned}
P_{\rm dense}
&=L(P_{\rm MLP,layer}+P_{\rm attn,layer})+2VH\\
&=28\times46{,}792{,}704+466{,}747{,}392\\
&=1{,}776{,}943{,}104.
\end{aligned}
$$

本次另只读取 safetensors 的 38613 字节 JSON header，按 tensor shape 累加得到实际参数量 **1,777,088,000**；没有加载权重张量或计算文件摘要。差额为 Q/K/V bias 的 57344 个参数和 RMSNorm 的 87552 个参数。MFU 复核应沿用 $P_{\rm dense}$，显存估算则使用实际参数量。用名义 1.5B 代入会低估矩阵部分 FLOPs 约 15.6%。

## 全局 batch 与有效序列

当前数学配方是全局 prompt batch 64，每题采样 1 条 response，mini-batch 64，`ppo_epochs=1`，每批进行一次全局参数更新。4 个 actor rank 平均各处理 16 条序列；这是同一个全局 batch 的分片。

令 $p_i$ 和 $r_i$ 分别为第 $i$ 条 prompt、response 的有效 token 数，$s_i=p_i+r_i$。定义：

$$
T=\sum_{i=1}^{64}s_i,\qquad Q=\sum_{i=1}^{64}s_i^2.
$$

这里 $s_i$ 包括 prompt，虽然 distillation loss 只作用于 response。模型仍需计算 prompt 上的 hidden state 和 attention。Remove-padding 与动态 batching 会改变实际执行方式；估算器使用去掉 padding 后的长度。

`ppo_max_token_len_per_gpu=32768` 约束动态 micro-batch 的 token 预算，不能用它代替 $T$，也不能把 micro-batch 预算乘 64。一个 rank 的 16 条长序列通常要通过若干 micro-batch 和梯度累积完成。

训练 prompt 上限 4096、response 上限 7168，故训练有效长度最多 11264。Student 为长验证配置的 `max_model_len=35841`，以及 teacher 预留一 token 后的 11265，都不是训练每条样本的实际长度。验证不进行 actor backward，不能把 31744 的验证 response budget 放进 actor 训练 MFU 分子。

## FLOPs 的两部分

[Qwen2 估算器](../../../verl/utils/flops_counter.py) 先计算矩阵部分，再计算 attention 随长度平方增长的部分。一次乘加记作 2 FLOPs；矩阵前向约 $2P$ FLOPs/token，前向加反向用约 3 倍前向得到常见的 $6P$ 估计。

$$
\begin{aligned}
\widehat F_{\rm dense}&=6P_{\rm dense}T=10{,}661{,}658{,}624\,T,\\
\widehat F_{\rm attention}&=6LAd_hQ=6LHQ=258{,}048\,Q,\\
\widehat F_{\rm actor}&=10{,}661{,}658{,}624\,T+258{,}048\,Q.
\end{aligned}
$$

Attention 的长度平方项来自 QK 和 AV；其系数采用当前实现对因果 attention 训练计算量的估计。GQA 减少 K/V 投影和 KV cache，但 attention 仍有 12 个 query head，不能在这一项把 $A=12$ 换成 $K=2$。

这是实现约定的模型计算量估计：embedding lookup 被归入矩阵参数项，norm、softmax、逐元素激活、优化器、通信和 checkpoint 重计算没有逐算子累计。因此它适合比较相同估算方式的配置，精确的硬件 FLOPs 必须另用 profiler 测量。启用 activation checkpointing 会增加实际执行的重计算，MFU 分子仍按有用的前向和反向计数；硬件 FLOPs 利用率（HFU）可能与 MFU 不同。

## 分母与计时边界

[Engine worker](../../../verl/workers/engine_workers.py) 的训练路径使用：

$$
\mathrm{MFU}_{\rm actor}
=\frac{\widehat F_{\rm actor}}{\Delta t_{\rm engine}\,N_{\rm actor}\,F_{\rm peak}}.
$$

- $N_{\rm actor}=4$，是 actor 的分布式 world size。4 张 teacher GPU 不在分母里。
- $F_{\rm peak}$ 是单 GPU 查表得到的峰值；A100/A800 为 $312\times10^{12}$ FLOP/s，H20 为 $148\times10^{12}$ FLOP/s。
- $\Delta t_{\rm engine}$ 是 `self.engine.train_batch(...)` 的内部计时。`engine.train_mode(...)` 先进入，随后 timer 才进入；退出顺序相反，所以前后的部分 load/offload 不在这个时间内。
- 外层 `timing_s/update_actor` 包含更多调度、切换和返回成本；`timing_s/step` 还包含生成、teacher、verifier、old-log-prob 与权重同步。三者不能互换。

峰值来自仓库 `_DEVICE_FLOPS`，应核对实际任务 GPU 与查表匹配结果。镜像名称不能证明 GPU 型号。当前实现对无法识别的 GPU 返回无穷大峰值，结果可能为 MFU=0；它不能被解释为设备完全没有做计算。

MFU=0.40 表示该估计下 actor 内部更新完成了约 40% 理论峰值的有效计算量。`nvidia-smi` GPU utilization 则是采样窗口内有 kernel 执行的时间比例；高 busy 可能伴随带宽瓶颈和低 MFU，两者没有直接换算关系。[^nvidia]

## 完整数值算例

先用等长场景核对公式，**该场景不是从真实 batch 还原的长度分布**。设 64 条序列各长 6300 token，其中 prompt 100、response 6200：

$$
T=64\times6300=403{,}200,\qquad Q=64\times6300^2=2{,}540{,}160{,}000.
$$

$$
\begin{aligned}
\widehat F_{\rm dense}&=4.2987807571968\times10^{15},\\
\widehat F_{\rm attention}&=0.6554832076800\times10^{15},\\
\widehat F_{\rm actor}&=4.9542639648768\times10^{15}\ \mathrm{FLOPs}.
\end{aligned}
$$

Attention 占约 13.23%。若是 4 张 A100/A800、内部训练耗时 12 秒：

$$
\mathrm{MFU}=\frac{4.9542639648768\times10^{15}}{12\times4\times312\times10^{12}}=0.330814\approx33.08\%.
$$

相同长度与时间若代入 H20 的 148 TFLOP/s，则为 69.74%；硬件变慢时实际耗时也会变化，不能据此推断换硬件后的真实性能。

再考虑训练预算的等长上界场景，64 条序列均为 $4096+7168=11264$：

| 场景 | $T$ | $\widehat F_{\rm dense}$ | $\widehat F_{\rm attention}$ | $\widehat F_{\rm actor}$ |
| --- | ---: | ---: | ---: | ---: |
| 每条 6300 token | 403200 | 4.29878 PFLOP | 0.65548 PFLOP | 4.95426 PFLOP |
| 每条 11264 token | 720896 | 7.68595 PFLOP | 2.09539 PFLOP | 9.78134 PFLOP |

PFLOP 是计算量，PFLOP/s 是计算速率。最大长度场景的 attention 比重约 21.42%；用短序列经验系数外推到长上下文会失真。

## 用日志复核真实 batch 的边界

原始 step 1–9 历史日志在 [history.jsonl](data/b38hw8v0-log-step1-9/history.jsonl)。以 step 9 为例，日志给出：

$$
\begin{aligned}
T&=399{,}801,\\
\overline p&=93.15625,\quad\overline r=6153.734375,\\
64(\overline p+\overline r)&=399{,}801,\\
s_{\max}&\le253+7168=7421.
\end{aligned}
$$

只有均值、最大值和总 token 数，无法精确还原 $Q$。Cauchy–Schwarz 不等式与长度上界给出：

$$
\frac{T^2}{64}\le Q\le s_{\max}T,
\qquad
2{,}497{,}513{,}118.765625\le Q\le2{,}966{,}923{,}221.
$$

代入后得到：

$$
4.9070200\times10^{15}\le\widehat F_{\rm actor}\le5.0281504\times10^{15}.
$$

该步日志 MFU 为 0.4379011773。W&B 的 [hardware.json](data/b38hw8v0-api-20261020/hardware.json) 已确认本任务为 8 张 A800-SXM4-80GB，actor 使用其中 4 张；按其 312 TFLOP/s 峰值，可以反推内部时间约 8.979–9.201 秒；外层 `update_actor` 实际为 12.449 秒，边界差异足以解释两者不直接相除。若错误地拿外层时间代入，得到的是另一种约 31.58%–32.36% 的指标。

这是使用长度边界、实际 GPU 型号和历史日志进行的一致性检查。精确复核每一步需要保存 `global_token_num` 的长度列表或至少 $T,Q$，以及内部 $\Delta t$、GPU 型号和峰值；无需保存训练文本。多 rank 的时间与 MFU 若被平均聚合，也要保留各 rank 的原始值才能完全重现聚合结果。

## 可复现计算

计算脚本仅依赖 Python 标准库。命令从仓库根目录执行：

```bash
python3 examples/mirroropd/docs/scripts/compute_mfu.py \
  --config examples/mirroropd/docs/data/student-config.json \
  --uniform-length 6300 --batch 64 --actor-gpus 4 \
  --peak-tflops 312 --seconds 12

# lengths.json 是整个 global batch 的实际 prompt+response 有效长度列表。
python3 examples/mirroropd/docs/scripts/compute_mfu.py \
  --config examples/mirroropd/docs/data/student-config.json \
  --lengths /实验目录/lengths.json --actor-gpus 4 \
  --peak-tflops 312 --seconds 真实内部训练秒数
```

脚本明确标记 `hypothetical-uniform-lengths` 或 `actual-lengths`，并输出矩阵参数、$T,Q$、两部分 FLOPs 和 MFU。计算不会安装 GPU 包，也不会改训练配置。
