# LCB 隔离判分器使用与验收

更新日期：2026-10-22。TACO / LCB 等原先经过 `code_eval_v2` 的数据源已默认使用新的独立监督执行器；外部 reward 入口和 stdin/function 判题规则保持原有含义。HumanEval+ 路径没有切换。设计依据与实现前对照见[调研报告](2026-10-22-判分内存故障与隔离方案.md)。

## 1. 已实现的行为

调用链为 `reward_func → evaluate → 独立 supervisor → 一次性 worker → 原 LCB runner`。Supervisor 和 worker 以文件路径启动，不经 `python -m verl...` 导入训练运行时。每条答案完成后回收解释器，不复用执行过模型代码的 Python 全局状态；批量 API 使用线程提交独立任务，返回顺序仍与输入一致。

| 功能 | 当前行为 |
| --- | --- |
| 默认内存控制 | 每任务 4 GiB 进程树 RSS 监控，8 GiB 地址空间兜底 |
| cgroup 后端 | 配置委派父目录后，按任务建立 memory.max、swap=0、oom.group=1、pids=64 的独立组 |
| 执行并发 | 默认每节点、每用户共享 4 个 flock 执行槽，覆盖多个 RewardLoopWorker |
| 超时 | 保留每 case 默认 6 秒；外部总执行预算 `(timeout+1)×case数+5` 秒；另设启动和排队时限 |
| 输出控制 | 每个 stdio case 使用 `max(8 MiB, 4×预期输出字节数+64 KiB)`；原生 fd/非捕获输出由诊断文件上限兜底 |
| 调用方死亡 | Supervisor 通过 stdin 管道感知调用方消失，清理执行进程组/cgroup 和任务临时目录 |
| Supervisor 死亡 | Worker 安装 Linux PDEATHSIG，监督进程死亡时直接 worker 被终止 |
| 错误分类 | 资源超限与答案错误分别记录；启动、依赖、配置、协议等执行器故障向上抛错 |
| 审计 | 记录 job ID、PID、调用上下文、实际后端、限制、排队/耗时、内存观测和退出原因；不写完整代码或测试内容 |

`RLIMIT_AS` 限制虚拟地址空间，RSS 是采样值，cgroup 是内核 charge 口径，三个数字不能混作同一指标。默认 RSS 方案可能出现短暂超调，因此还保留 AS 兜底和节点并发上限。4 GiB 是可调整的初始预算，没有完成所有模型答案的 4/8 GiB 敏感性回放。

## 2. 启动和 CPU 预检

使用开发机现有原生解释器，在仓库根目录运行：

```bash
.venv-native/bin/python \
  verl/utils/reward_score/one_shot_opd/code_eval_v2/_isolation.py --self-test
```

预检执行一个加法程序，验证解释器、NumPy/pandas、psutil、执行槽、实际限制和结果通道，不加载模型、不启动 Ray、不使用 GPU。成功输出 `status=PASS`、实际 `backend` 和 PID。配置错误、缺依赖或无法启用指定 cgroup 会失败，不退回无上限执行。

普通 code 配方无需额外参数即可使用默认的有界 RSS 后端：

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 \
  bash examples/mirroropd/run_code_deepseek_r1_1_5b_fsdp2.sh
```

GPU 列表应替换为分配给当前任务的设备。上述为启动示例，本轮没有执行 GPU 训练。

若已有可写、已委派 memory/pids 控制器的 cgroup v2 父目录：

```bash
export MIRROROPD_LCB_BACKEND=cgroup
export MIRROROPD_LCB_CGROUP_PARENT=/sys/fs/cgroup/your-delegated-parent

.venv-native/bin/python \
  verl/utils/reward_score/one_shot_opd/code_eval_v2/_isolation.py --self-test
```

本工具只创建自己的子组，不启用父组 controller、不修改训练父组，也不迁移其他任务。`auto` 在提供父目录时选择 cgroup；提供无效父目录会报错，不能把配置错误解释为已启用隔离。没有指定父目录时 `auto` 使用 RSS。开发机是否有委派权限需要在那里预检，本机 cgroup 测试通过不代表远端权限相同。

## 3. 配置参数

参数均采用 `MIRROROPD_LCB_` 前缀。共享启动脚本会显式转发到 Ray runtime environment；直接使用其他训练入口时，也必须把变量传给执行 reward 的 Ray worker。

| 后缀 | 默认值 | 含义 |
| --- | --- | --- |
| `BACKEND` | `auto` | `auto`、`rss`、`cgroup` |
| `CGROUP_PARENT` | 空 | 委派父 cgroup 目录 |
| `MEMORY_MIB` | 4096 | RSS 阈值或 cgroup memory.max |
| `ADDRESS_SPACE_MIB` | 8192 | Worker 地址空间硬上限；必须不小于 MEMORY_MIB |
| `OUTPUT_MIB` | 8 | 每个 stdio case 输出预算的下限 |
| `DIAGNOSTIC_MIB` | 1 | 原生 fd/未捕获输出文件的容量限制 |
| `INPUT_MIB` | 64 | 单任务序列化请求容量上限 |
| `MAX_CONCURRENT` | 4 | 共享槽目录内的节点执行并发 |
| `QUEUE_TIMEOUT_S` | 600 | 等待执行槽的最大时间 |
| `STARTUP_TIMEOUT_S` | 30 | 启动、fixture 解析及依赖导入时限 |
| `POLL_S` | 0.01 | 监督轮询周期 |
| `SLOT_DIR` | `/tmp/mirroropd-lcb-<uid>` | 本机共享锁目录，必须让同一节点的调用者使用相同目录 |
| `AUDIT_DIR` | 未设置时使用 SLOT_DIR | code 启动脚本默认指定 `outputs/<实验名>/lcb-audit` |
| `RUN_ID` | 无 | code 启动脚本默认使用实验名，写入审计上下文 |

示例：

```bash
MIRROROPD_LCB_MAX_CONCURRENT=4 \
MIRROROPD_LCB_MEMORY_MIB=4096 \
MIRROROPD_LCB_ADDRESS_SPACE_MIB=8192 \
DRY_RUN=1 bash examples/mirroropd/run_code_deepseek_r1_1_5b_fsdp2.sh
```

执行槽使用本地文件锁。不要把 SLOT_DIR 放到跨节点共享目录来冒充节点内限流，也不要为每个 RewardLoopWorker 指定不同目录。容量只能在所有槽空闲时调整；已有任务时配置冲突会报错。请求排队时间与执行时间分开记录，队列超时属于执行器故障，不计为答案错误。

客户端仍会进行原有 ground-truth 解析和有限的序列化；排队控制主要限制执行子进程，不宣称消除了 Ray/TQ 中所有测试数据副本。INPUT_MIB 超限会抛错，TACO 的更大测试对象应单独检查后调整。

## 4. 状态、审计与定位

正常返回的状态包括 PASS、WRONG_ANSWER、RUNTIME_ERROR、SYNTAX_ERROR、TIME_LIMIT、MEMORY_LIMIT、OUTPUT_LIMIT。资源失败按所配置的评测协议计零分；配置、启动、import、协议或清理异常以 `EvaluationInfrastructureError` 向上抛出，单题和批量入口都不会把这类故障吞成 WA。

结果中的 `lcb_status`、`lcb_backend`、`lcb_job_id` 随 reward extra info 返回，可关联验证 JSONL。耗时和内存保留在审计文件中，不加入准确率 bootstrap 变量。

审计目录包含 `events.jsonl` 和轮转文件 `events.jsonl.1`，单文件超过约 16 MiB 后轮转，保留两份；并发写入由文件锁保护。每个任务有 started/finished 事件，包含 worker/supervisor PID、job ID、可获得的题目/样本/run 上下文、实际后端和退出信息。没有 caller 提供的 step/sample ID 时不会伪造，代码启动入口至少会补入 run ID。

定位流程是：先在审计文件中找 MEMORY_LIMIT/TIME_LIMIT 或故障 PID，再按 job ID 关联完成验证后保存的 `validation/<step>.jsonl`。若整轮尚未保存且调用方被其他故障终止，原始答案未必已经持久化；本实现没有将全部模型答案复制到审计文件。

cgroup OOM 依靠 `memory.events` 判断。不能把所有 SIGKILL 都当作 OOM：超时和取消也会发 SIGKILL。启动前就超过内存预算属于执行器启动失败；只有进入答案执行阶段后的资源超限才作为答案资源失败。

## 6. 剩余边界和后续验收

- 原 LCB binary stdin/stdout 兼容性问题没有在资源修复中一起改变，避免混入评分语义变化。
- 没有完整回放 175×16 的真实模型答案，也没有取得原 PID 91804 的具体代码；不声称已经复现那个特定程序。
- 未在开发机执行完整验证或多轮训练；下一步应先用原生环境自检，再完成一次真实 LCB 验证，检查随后一轮的内存和进程清理。
- Worker 的 PDEATHSIG 只直接保证自身退出；若 supervisor 自身遭硬杀，任意逃离进程组的后代和遗留 cgroup 仍需要外部运维/执行服务处理。调用方死亡、supervisor 正常执行清理的路径已经测试。
- 当前 worker 与监督者同 UID；cgroup/guard 是资源容错机制，不具备对抗恶意代码逃逸的完整权限隔离。更强隔离需要独立执行账户、受管服务或系统层策略。
- 未来可用真实答案扫描并发 4/8/16 与 4/8 GiB 预算；不要用手写加法程序的吞吐替代完整 LCB 验证时间。
