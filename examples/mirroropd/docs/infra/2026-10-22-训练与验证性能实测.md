## 1. 完整验证与参数对照

### 1.1 条件与结论

2026-10-22 在本机 GPU0–3 的四张 H800 上完成全量提交对照及后续参数筛选。源码固定在 `b517941798ab617bb3d2609988391115f8ba27ad`，使用独立 checkout，避开并行开发中的指标改动；结果适用于这个冻结版本和初始 student checkpoint。GPU4–7 保持原任务运行。实验没有修改正式启动默认值，也没有接入新的调度 PR。

Student 为 DeepSeek-R1-Distill-Qwen-1.5B；shared_sync、四个 TP1 推理副本、BF16、CUDA Graph、chunked prefill 和 prefix caching 开启。每题采样 16 条，temperature=0.7、top-p=0.9，回答上限 31744、引擎上下文上限 35841，验证不返回 log-prob。完整集为 MATH-500 500 题、AMC23 40 题、AIME25 30 题，共 570 题、9120 条回答。筛选子集仍为前一报告中的 112/8/8 题，共 2048 条回答。

速度优先候选是全量提交、每副本并发 128、显存比例 0.65、调度 token 预算 8192。相对此前全量提交/并发 64，TPS 提高 16.55%，完整验证耗时下降 14.57%。显存预算较紧时，并发 96/比例 0.5 提供 10.79% TPS 改善，单卡峰值显存几乎不变。每个配置只完成一次自然生成；完整集的 64 并发是前一轮基线，不能把小幅差异解释为已验证的稳定优势，也不能据此宣称吞吐上限。

全量提交缩短 11.73% 的验证时间、提高 14.59% TPS，CPU 进程 RSS 增加约 2.43 GiB。两组均完成 9120 条回答且无抢占。全量通过现有 `data.val_batch_size=null` 表达；它把整套题目交给既有流程，GPU 活跃 batch 仍由 vLLM 动态调度。请求入队不等于同时为 9120 条回答分配最大长度 KV。

### 1.4 延迟、利用率与收尾

| 完整集配置 | GPU busy | 单卡平均功率 W | 输出 token 能耗 J/token | token 间隔均值 ms | 活跃序列合计均值 | 最后 10% 回答完成跨度秒 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 64/0.50，前一轮 | 93.85% | — | — | — | 226.00 | 540.93 |
| 96/0.50 | 92.93% | 569.27 | 0.06555 | 9.51 | 329.41 | 272.74 |
| 128/0.50 | 91.71% | 590.45 | 0.06475 | 11.57 | 417.88 | 343.11 |
| 128/0.65 | 90.30% | 582.02 | 0.06370 | 11.39 | 416.36 | 331.06 |

能耗为四卡 NVML 功率采样积分除以输出 token，排除启动，未计 CPU/整机能耗。token 间隔是引擎 Prometheus histogram 的 sum/count，不能直接等同于每次调度的固定耗时。采样中的 GPU busy 没有随 TPS 单调增长；busy 不是 FLOPs 或 HBM 带宽利用率。

“最后 10%”指成功完成数从 8208 到 9120 的跨度，仍包含 912 条回答的有效生成，不是可全部消除的空闲时间。各组回答长度不同，不能把跨度差额全部归因于调度浪费。增加并发会增加同时在跑的回答，也会增加单条回答的 token 间隔，因此 TPS 不随并发线性增长。所有完整集采样均未见某实例完全闲置、同时其他实例还有 waiting 的组合；这一采样结果不证明不存在短时负载不均。

### 1.5 正确性与证据

后续参数实验共 7 组、35,552 条回答，全部进程退出 0，题目数及每题 16 条回答完整，评分失败数为 0。与前一轮全量 64 并发相比，96/0.5、128/0.5、128/0.65 的平均分差分别为 +0.12、−0.32、+0.16 个百分点；按题目配对的 10000 次 bootstrap 95% 区间分别为 [−0.57,+0.81]、[−1.02,+0.38]、[−0.46,+0.78]。这不是多随机种子非劣检验。

## 2. 验证窗口筛选与多轮更新基线


### 2.1 实验目标与固定条件

2026-10-22 使用本机 GPU0–3 的四张 H800 80GB，GPU4–7 保持其他任务运行。源码基点为 `fb169fa7f`。实验先验收当前逐更新指标下的 shared_sync 短训练，再比较冻结 checkpoint 的验证请求供给；训练 prompt/mini64、更新算法、学习率和生成长度不作为验证调优变量。

最新云端 E8–E11 使用 epochs16，A100/A800 八卡整步约 118–119 秒，actor 约 74 秒、rollout 批次约 32 秒；前 100 步的两次验证占训练加验证时间约 35%–36%。这些数据用于决定优化优先级，不能替代本机同条件对照。原始云端参照见 E10 运行。[^wandb-e10]历史 eager/Graph 和验证窗口 16/32 的结果见[前一轮测量](#3-本机编译与训练优化)。

| 项目 | 固定值 |
| --- | --- |
| Student / teacher | DeepSeek-R1-Distill-Qwen-1.5B / JustRL-DeepSeek-1.5B |
| 资源 | shared_sync，四个 TP1 student 副本，独立 teacher pool0 |
| 环境 | Torch2.11.0+cu128、vLLM0.25.1+cu129、Transformers5.12.1、Ray2.56.1、TransferQueue0.1.11、FlashAttention2.8.3 |
| Rollout | 编译与 CUDA Graph；推理 token 预算 8192；GPU memory utilization0.5 |
| 验证预算 | MATH-500 112 题、AMC23 8 题、AIME25 8 题；每题 16 次，共 2048 条回答 |
| 验证采样 | temperature0.7、top-p0.9、top-k 关闭、response 上限 31744 |
| 生成概率 | 验证不返回 log-prob；训练保留实际行为概率 |
| 观测 | 离线 W&B、每秒四卡 NVML、约每两秒四引擎 Prometheus |

子集使用 NumPy `default_rng(42)`，按 MATH-500、AMC23、AIME25 顺序无放回选择 112/8/8 行，再按源行号排序。选中行号和软件版本保存在[数据目录](../data/rollout-tuning-20261022)。每个条件重新初始化同一个 student checkpoint；不加载短训后的权重。

### 2.2 计时与验收

验证速度以完整 `_validate()` 墙钟和四个引擎累计的实际输出 token 数计算。该 timer 包含窗口等待、生成、判分、CPU 解码与结果聚合，不包含模型和 Ray 初始化。独立作业墙钟另列。自然停止的回答长度会随调度变化，须同时比较完成时间和 token/s。

完整性要求 2048 条最终回答、128 个题目 UID 组、每组恰好 16 条；四个引擎成功计数之和必须也是 2048，累计 generation token 与 request generation token sum 一致。NVML GPU busy 表示采样窗口内设备工作的时间比例；actor MFU 只描述训练阶段，验证提速不等于 actor MFU 提高。

实验矩阵依次为窗口 32/并发 32、窗口 128/并发 32、窗口 128/并发 64。提高窗口增加等待请求的供给；提高并发改变每个引擎同时运行的序列上限。两者独立比较，保持词表概率、评测题目和回答次数不变。

### 2.3 当前代码的四卡训练基线

E10 短训使用 epochs16、D0，关闭验证与保存，完成 4 个外层 step、64 次实际 optimizer 更新。逐更新坐标连续且 attempts 等于实际更新数，非有限概率比例为 0；进程退出码为 0。首步 145.16 秒包含预热，第 2～4 步作为主窗口。

| rollout 整体流程 | 24.89 秒 |
| teacher forward / transfer | 1.29 / 0.94 秒 |
| old-log-prob | 2.75 秒 |

| 32 / 32 | 812.82 | 12,767,515 | 15,708 | 82.99% | 41.83 | 35.11% | 0 |

#### 2.4.1 请求供给与最后的长尾

基线四个窗口的“90% 回答完成到全部完成”分别为 76.7、93.5、79.1、72.1 秒。窗口 128 只保留一个窗口边界，减少反复排空；但同一窗口中最长回答仍需完成。窗口 128/并发 32 的尾部为 146.5 秒，并发 64 首次为 164.2 秒。不能直接相加这些尾部当成可完全消除的时间，因为窗口大小和请求集合不同。

| 配置 | 采样时四卡活跃请求均值 | 全部等待队列为空的采样比例 | 活跃请求总数小于 16 的比例 | 至少一个副本空闲的比例 |
| --- | ---: | ---: | ---: | ---: |
| 32 / 32 | 67.65 | 63.61% | 24.85% | 26.92% |
| 128 / 32 | 101.01 | 24.06% | 12.78% | 12.78% |
| 128 / 64 | 176.23 | 40.67% | 12.44% | 12.44% |
| 128 / 64，确认 | 171.31 | 41.21% | 14.07% | 17.09% |

这些比例来自约每两秒的完整四引擎采样，不是精确连续时间积分。引擎最终的抢占计数为 0，较大窗口确实增加了等待请求，但没有将全部等待请求变成活跃 KV。KV pool 仍按 memory utilization0.5 预留，实际 KV 使用增加不等于整卡预留显存按同样比例增加。

窗口 128/并发 32 与窗口 128/并发 64 首次的 GPU busy 都约 91%，TPS 仍从 20540 提高到 25575。增加活跃序列改善每次执行承载的工作量，busy 本身不能区分这项效率收益。这里没有定义或报告推理 MFU；actor MFU 仍只引用前述短训基线 30.43%，不将验证 busy 改名为 MFU。

#### 2.4.2 输出与质量边界

## 3. 本机编译与训练优化

### 3.1 共享四卡训练对照

本机前四张 H800 的完整 `shared_sync` 短训练已通过两组各 5 步对照。排除首步后，整步均值从 **94.36 秒降到 35.93 秒，提速 2.63 倍、耗时降低 61.93%**。按实际有效 token 总量除以训练时间归一化，吞吐提高 2.62 倍；两组平均 token 量仅差 0.16%。主要变化在 student 生成，teacher、old log-prob、actor 更新和权重同步时间基本相同。

#### 3.3.1 计时边界与生成后收尾

`rollout_batch`从 driver 提交边界到最后一个 student generate 返回；`gen`从`prepare_step()`之后开始，等待完整题目组完成并执行 sleep。二者重叠但不保证包含关系，不能相加，也不能无条件把差值叫作 verifier 时间。

首步的`rollout_batch`可大于`gen`：eager 为 108.50/98.24 秒，Graph 为 50.03/44.25 秒，原因是提交和首次准备发生在`gen`计时开始之前。主窗口的分解来自各自独立 timer，GPU 阶段反推只使用可相加的阶段，未重复加`rollout_batch`。

Graph step3 的`rollout_batch`为 20.76 秒，`gen`为 30.20 秒；其余 Graph 稳态步的`gen-rollout_batch`约 0.62–1.10 秒。Eager step5 也出现约 8.09 秒差距。现象指向生成后判分/TQ/完成状态汇总/sleep 路径的长尾；代码中数学判分存在秒级超时机制，但现有指标无法将这 9.44 秒完全归因于某个判分函数。后续应在该路径定点加计时，再决定是否调整调度。

从整个独立进程启动到退出，A/B/C/D/E 分别耗时 1065.82/552.59/467.64/435.30/469.98 秒。A→D 的独立作业总时间加速为 **2.45 倍**，小于验证函数内的4.53倍。启动包含Ray、teacher/actor/vLLM初始化和Graph准备，且这些重复实验复用本机缓存，不是每次清空编译缓存的冷启动测量；正式训练中的周期验证也不会每轮重建这些进程。

#### 3.8.1 各项优化的贡献

**编译＋Graph 是最大收益来源。** A→B 的输出量接近，总时间减少 62.7%，输出吞吐提高到 2.71 倍。此前短 CUDA trace 已观察到 eager 的 kernel 发射间隙；这里的验证实验与该机制一致。模型初始化和编译成本不在这张表内，正式长训练应同时计入一次性启动成本。

**增加提交窗口降低反复排空的成本。** B→C 将每窗口从 16×16=256 条回答改为 32×16=512 条，四个引擎的总活跃上限仍为 128；增加的是等待队列，不是每张卡同时处理的序列上限。时间减少 31.1%，输出量增加 4.2%，输出吞吐提高 51.1%。当前 trainer 等上一窗口全部结束后才提交下一窗口，窗口中的长回答会让已空闲的引擎等待。

每两秒采样一次完成计数估算的“窗口内 90% 回答完成到全部完成”的尾部时间，在 A 的两个窗口分别为 239.6/201.4 秒，在 B 为 77.0/66.7 秒，C 的单个大窗口为 88.8 秒。该测量支持减少窗口边界等待的解释；输出长度本身也有变化，不能将全部差值归因于窗口大小。当前没有实现跨窗口持续投喂。

**验证不返回概率，固定工作量实验约有 5% 收益。** C→D 的总时间下降 14.2%，但输出 token 同时减少约 9.8%；归一化吞吐只增加 5.2%。为分离生成长度影响，另做了单卡固定工作量实验：同 32 题，每条强制 2048 token、忽略 EOS、关闭 detokenize，为每条请求固定 seed，顺序为“有、无、无、有、有、无”概率，两个路径都预热。六次生成的 token ID 逐个相同；保留概率平均 6.7392 秒，不返回概率平均 6.4099 秒，吞吐提高 5.14%。原始重复数据见[fixed-logprobs.json](../data/validation-optimization-20261021/fixed-logprobs.json)。

vLLM 0.25.1 在 `processed_logprobs` 模式下，原生采样路径仍可能计算中间 log-softmax；禁用请求概率主要省去 gather、结果输出及后续传输，不能声称消除了全部概率计算。[^vllm-sampler] 本仓不修改 vLLM sampler，不改变训练所需的概率语义。

**max_num_seqs=64 暂不设为默认。** D→E 的 token 吞吐增加约 4.1%，总时间为 177.53→178.46 秒，单次测量不足以确认稳定收益。E 的排队峰值由每引擎 80 降到 44，但验证尾部仍约 76.5 秒。五项正式运行均无 KV preemption，采样到的 KV 占用峰值为 10.7%–17.2%。当前瓶颈不是已经耗尽 KV 容量；直接把显存比例加到 0.75 没有对应证据。

#### 3.8.2 保留的异常与证据边界

首次“不返回概率＋窗口32”观察得到 **280.39 秒、2,848,256 个输出 token**，比 C 慢。该次验证完成后，调试期间修改了正在执行的 Bash 源文件，导致 shell 在 Python 退出后继续读取新位置的代码并意外再次启动训练；第二次启动被取消。第一段验证记录保存在[exploratory observation](../data/validation-optimization-20261021/valid-graph-w32-20261021-2/observation.json)，未混入正常退出的五项正式对照。

这次较慢观察包括明显更长的首个 token 前等待，无法仅凭已有记录确定等待来自哪一层。它说明单次自然停止生成的 testing 不能独立证明概率开关的因果收益。因此同时保留该观察、干净重跑 D，以及固定 seed、固定 token 数的重复实验。launcher 已增加退出保护，并用会在子进程运行期间追加源码的 CPU 测试复现旧问题、验证修复。

这些实验仍有边界：正式表每配置一次，checkpoint 为初始模型；小子集不代表完整验证长度分布；改变 batch 调度会改变随机采样结果，平均答题得分约 0.775–0.795 仅用于检查明显异常，不能判定精度提升或统计等价。完整 570×16 验证、训练后 checkpoint 的验证，以及目标八卡环境尚需独立测量。部分成功运行在 W&B 退出清理时打印连接重置，历史记录完整且主进程退出码为 0；没有把这些日志当作 GPU 算子失败。

| 模式/设备 | GPU 活动包络 | kernel 活跃区间并集 | GPU 活动覆盖比例，含 memcpy/memset | kernel 数 |
| --- | --- | --- | --- | --- |
| Eager GPU0 | 631.81ms | 105.25ms | 16.75% | 14395 |

### 4.1 4+4与共享八卡的历史对照

本项目以 sampled-token OPD 数学训练为工作负载，优化的是整个训练管线：student 生成、CPU 判分、teacher 概率计算、student 更新、权重同步、周期验证，以及各阶段 GPU/CPU 内存驻留。目标是在保留算法和训练/验证预算的条件下，降低完整周期耗时与预留 GPU 小时，而不是仅提高 GPU busy 或某一个计算阶段的速度。

原 `b38hw8v0` 使用 student 4 卡、独立 teacher 4 卡；`rcxtujbi` 使用同池八卡，顺序执行生成、冻结 FSDP2 teacher 评分和 actor 更新。两者均为 V1 sync、`k1 + PG`，数学 verifier 用于诊断和验证，不参与最终训练 loss。算法推导见 [OPD 目标文档](../opd-objective/README.md)；调度、配置、字段对齐和支持边界见 [infra 总览](README.md)，本文只维护实际实验条件、测量和结论。[^baseline] [^shared]

**截至 2026-10-21 08:55（Asia/Shanghai）的 API 快照，共享八卡没有加速已观测的训练步。** 对齐两次运行的 step 2–12，总 token 工作量只差 0.012%，完整步时却从 145.82 秒变为 148.54 秒（慢 1.86%），有效 token 吞吐下降 1.82%。Actor 更新快了 30.26%，但收益被新增串行 teacher 阶段、略慢的生成和同步抵消。

**显存改善主要体现在 FSDP 进程计数器，整卡显存没有同比下降。** 同名 allocated 高水位的观测最大值由 19.82 降到 13.97 GiB；生成阶段八卡整卡显存总占用均值则由 293.91 增至 326.00 GiB。GPU busy 提高，说明原 teacher 卡参与了计算，但这没有转化成相同工作量的训练加速。

**完整训练周期是否加速仍未测到。** 共享 run 只上传到 step 12，没有验证记录；4+4 已上传到 step 98，四次完整验证平均耗时 5.70 小时。验证是旧管线的主要成本，必须等共享模式同预算验证完成后再下总体结论。

![整步差值的来源](../figures/pipeline-comparison-20261021/stage-delta.png)

整步变化可由互不重叠的 timer 核对：

$$
\Delta t\approx\underbrace{3.204}_{gen}+\underbrace{3.907}_{teacher 前向与迁移}
-\underbrace{1.142}_{old\ logprob}-\underbrace{3.909}_{actor 更新}
+\underbrace{0.559}_{权重同步}+\underbrace{0.096}_{adv 与残差}
=2.715\ \mathrm{s}.
$$

旧 teacher 的计算不是零，它与生成重叠并被包含在旧 `gen` 中。新方案把约 3.91 秒评分/迁移明确放到生成之后。完整 teacher 数据生产成本在两种模式下的计时边界不同，不能拿这些数字推导“FSDP teacher 比 vLLM teacher 慢多少”。

共享 `gen` 仍占整步 86.12%。两次每个训练 batch 的 response 最大长度都是 7168，约 62% 的回答达到上限；严格截断仍需 finish reason。固定 64 条请求分给 4/8 个 TP1 副本，平均每副本请求由 16 变 8，均低于 `max_num_seqs=32`。增加副本没有缩短自回归依赖链或最长回答，因此不能期待固定小 batch 的生成延迟自动减半。这是与观测一致的解释；该A800历史run缺少TTFT/TPOT和kernel trace。后续H800 trace已单独确认执行间隙与Graph收益，不能补作这次A800运行的原始trace。

即使假设完全消除 1.17 秒显式 teacher 迁移、其余时间不变，新步时仍约 147.37 秒，高于旧 145.82 秒。后续优先处理生成和完整验证，而不是把小比例搬运时间当作唯一瓶颈。

本次还反算了 `perf/total_num_tokens / timing_s/step / perf/throughput`：两次每行分母均为 8。实际日志已按总资源池归一化；不能误以为旧 run 只除 4 卡。上表吞吐使用总 token 除以总时间，避免与每步比值的算术平均混用。Actor 内部 MFU 均值 39.40%→31.89%，分母/计时范围另见 [MFU 说明](2026-10-22-MFU与利用率口径.md)，不能用它代替整步效率。

### 4.5 新指标已经提供了什么

共享 run 的 12 个训练 step 均包含 `rollout_batch`、`teacher_forward`、`teacher_transfer` 和 `fsdp_worker_peak_allocated_gib_max`。在 step 2–12 中，纯提交到最后生成返回的跨度均值 126.06 秒，teacher 评分 2.74 秒，显式迁移 1.17 秒；这些已是实际上传指标，不再是待实现设计。

`rollout_batch` 与 `gen` 有重叠且起点不同，不能相加，也不能把差值直接归为 verifier 服务时间。首步 `rollout_batch=185.03s` 大于 `gen=138.19s` 正说明提交早于 `gen` timer，不是计时溢出。Teacher forward 包含 RPC/TQ 及分批前向，具体边界只在 [infra 指标表](../metrics/2026-10-22-历史性能口径与验收.md#指标口径)定义。

`rollout/preemptions` 未发布；console 有一次“backend did not report preemptions”的提示。这里是缺测，不是 0 次抢占。共享模式没有独立 teacher RPC，因此没有 `teacher/request_latency_s/mean`；当前快照也没有验证侧新增指标。Verifier/TQ 细计时、纯 GPU forward、逐 rank micro-batch 和分段 actor 搬运仍不能从这些标量直接恢复。

### 4.6 验证、质量与完整周期

4+4 的四次已完成验证分别为 21200.77、20155.49、19643.28、21141.51 秒，均值 20535.26 秒（5.70 小时）。98 步训练 timer 合计 3.97 小时，已完成验证合计 22.82 小时，验证占已计时工作 85.19%。这些不包含启动前成本及未完成的下一次验证，不是整个作业的最终成本。

共享快照没有完成的验证。即便训练步稍慢，共享八卡仍可能改善验证主导的周期：按匹配窗口推算，每 20 步多花约 54.30 秒；若共享验证比旧均值少 54.30 秒以上（约 0.264%），就能抵消这部分训练增量，暂不计保存/初始化差异。这只是收支平衡条件，不是验证加速预测。

目标八卡仍缺同一checkpoint、570×16条、相同窗口/长度/采样条件下的完整验证；执行模式应另作单变量对照。训练阶段 64 条请求与验证窗口 256 条请求的并发条件不同，不能把本次训练侧无加速外推为验证一定无收益；也不能先假定验证会减半。

旧run的GPU采样间隔中位数约15秒。训练取非首步、非保存步区间，两端各留1秒；长gen/验证窗口使用15秒guard，gen起点另剔除未分解残差。窗口均由history的`_timestamp`与timer反推。短teacher/actor阶段没有足够保守内部窗口，因此不报告它们的精确busy。该方法与前述4+4对照的2秒guard不同，结果不能按小数点直接合并。

| `mdxt04lm` | 33.68% | 31.68% | 69.14% | 1782 / 2197 | 2385.84秒 |

One-Shot三个run在上述训练窗口的整卡显存观测最大值分别为61.78/62.05/61.45GiB，本仓旧shared为40.82GiB。前者vLLM memory0.75，后者0.5；它们是整卡驻留，不能等价成actor峰值或证明需要更多显存才快。

Shared run重新查询后仍为12行history、无完整验证；原始source保存新的抓取时间。API服务端finished仅描述上传状态，不能补造未记录的训练进度。相同卡型和工作量下的执行变化与H800 Graph收益分别解释，最终判断仍需目标八卡完整周期。

### 4.8 4+4早期快照的细项审计

以下仅使用2026-10-20的38步快照，提供后续98步对照未细分的replay长尾和CPU收尾证据。窗口、采样边界不能与上面的step2–12表混用。

#### 4.8.1 阶段耗时与资源使用

Step 2–38 剔除首步预热，37 步的算术均值如下：

| old_log_prob | 5.753 | 3.97% | 加载 actor 参数，前向计算概率和 entropy | 无当前 batch 的新评分工作 |
| adv | 0.106 | 0.07% | 主要是 CPU/TQ 张量处理 | 空闲 |

首步为 216.867 秒，其中约 55.1 秒不在上述子 timer 中，属于未分解的首次启动成本，不能全部当作 JIT。

#### 4.8.2 GPU probe 的对齐方法

令 history 的记录时间为 $\mathsf t_{\rm end}$，testing 耗时为 $\mathsf t_{\rm val}$，训练 step 耗时为 $\mathsf t_{\rm train}$。训练区间的近似起点为 $\mathsf t_{\rm end}-\mathsf t_{\rm val}-\mathsf t_{\rm train}$，各子阶段按源码执行顺序累加 timer。所有未解释时间的残差不强行归给某个阶段；选样时剔除可能包含残差的边界，再加 2 秒 guard。详见 [audit_pipeline.py](../scripts/audit_pipeline.py)。

这是 timer 推导窗口，不是 profiler 原始事件。NVML busy 自身也是一个采样窗口统计；2 秒 guard 只能减少边界混入，不能恢复连续 kernel 活动。每个结果都报告 probe 数，零 probe 表示缺数据，不能写成 GPU 利用率为零。

![阶段 GPU 使用](../figures/b38hw8v0-pipeline-20261020/phase-gpu.png)

| 阶段 | 保留下来的 GPU probe 行 | GPU 0–3 busy 均值 | GPU 4–7 busy 均值 | GPU 0–3 显存均值 | GPU 4–7 显存均值 |
| --- | --: | --: | --: | --: | --: |
| gen | 298 | 34.56% | 0.97% | 40.81 GiB | 32.67 GiB |
| old_log_prob | 2 | 样本不足 | 两次均为 0 | 样本不足 | 32.67 GiB |
| adv | 0 | 无法估计 | 无法估计 | 无法估计 | 无法估计 |
| update_actor | 21 | 76.30% | 0.00% | 18.19 GiB | 32.67 GiB |
| update_weights | 0 | 无法估计 | 无法估计 | 无法估计 | 无法估计 |
| step 20 验证 | 1413 | 35.92% | 0.00% | 40.89 GiB | 32.67 GiB |

GPU 0–3 的行为与 student 池一致，4–7 与 teacher 池一致；物理映射还应在下一次启动时打印确认。一个 probe 行包含该时点 8 张卡的观测，不是 8 个独立时间样本。

Actor 更新的 student 平均功率约 306.5 W，gen 为 133.2 W；其内部 GPU 工作明显更密集。改变 guard 为 0/1/3 秒后，actor busy 样本均值约为 70.7%/79.4%/78.2%，gen 约为 33.9%/34.4%/34.7%。因此 actor 的“约七到八成 busy”相对稳健，old-log-prob 的样本则太少，不适合下同样判断。

更新期间的整卡显存观测峰值约 22.09 GiB，生成时约 40.98 GiB。Actor 的 `max_memory_allocated_gb` 是 PyTorch 进程峰值，经 rank 指标聚合后也不必然是全局最大卡；既不是当前值，也不包括另一个 vLLM 进程。不能将它和 vLLM 预算机械相加，或把两者差值全当作碎片。

#### 4.8.3 Teacher 空闲的精确与非精确部分

源码依赖关系确认：同步配方的 teacher 在 actor 更新、old-log-prob、权重同步、验证期间没有新 batch 可评分。Actor 更新内部选中的 21 个 probe 行里，teacher 对应四卡的 busy 全为 0，与这个判断一致。

全部 38 步 actor 更新 timer 合计 490.46 秒，即 8.17 分钟。固定占用四张 teacher 卡，对应约 0.545 GPU 小时的阶段预留；old-log-prob 另约 0.247 GPU 小时，权重同步另约 0.090 GPU 小时。完整 step 20 验证期间，teacher 四卡空闲预留更达到 **23.556 GPU 小时**。这些是分配时长，不是 measured idle-kernel time 或电量。

Gen 内 teacher 有多空闲则不能精确积分：约 15 秒采样可能漏掉短促 teacher forward。需要请求开始/结束、排队和 kernel trace，不能直接将 0.97% 的样本均值当成 teacher 用时占比。当前没有证据证明 teacher 排队是主要瓶颈，也不能仅凭低采样均值证明 1 卡一定够用。

#### 4.8.4 Actor 更新还混合了哪些工作

`update_actor` 包含 CPU/GPU 参数与优化器状态搬运、动态 micro-batch、checkpoint 重计算、FSDP all-gather/梯度通信、反向和 optimizer step。`optimizer_offload=True` 表示状态在阶段间放 CPU，不表示本 run 的 AdamW 必然在 CPU 计算；engine train context 会按配置将其载入 GPU。

当前每 rank 约处理 10 万有效 token，token budget=32768，因此至少需要约 4 个动态 micro-batch；实际 packing 数和每批长度未记录。总 token 平衡后的 rank 差异不到约 0.54%，没有明显的总 token 严重失衡证据，但不能排除长度平方项、micro-batch 数或通信差异。

Entropy coefficient=0、actor.calculate_entropy=False，所以更新阶段不为了 entropy bonus 计算熵；old-log-prob 阶段却明确请求 `calculate_entropy=True` 以记录诊断。这能帮助区分输出头/entropy 优化应该测哪个阶段。

MFU 内部 timer 不覆盖完整 load/offload context，且日志 MFU 有 rank 聚合、序列长度平方项未保留。不能反推一个内部时间后，把外层差值全部记为 PCIe 搬运。要拆分这些部分，需要 profiler 中的 memcpy、NCCL、forward/backward 和 optimizer 标记。

### 4.9 验证阶段的窗口长尾

验证固定 570 题、每题 16 个回答，总共 9120 条请求；val_batch_size=16 将它分为 35 个 16 题窗口和最后一个 10 题窗口，共 36 个。源码等待每个窗口所有 prompt group 完成后，才提交下一窗口。运行中最多 4×32=128 条 student 活跃序列，而不是一次连续喂入全部 9120 条。

从 331 条完整验证状态日志中，恢复到的窗口恰好是 `[16×35, 10]`。`running=4, finished=12` 表示这个窗口只剩四道题的整组回答/后处理未完成，不代表恰好还有四条回答正在 GPU decode。

![验证长尾](../figures/b38hw8v0-pipeline-20261020/validation-tail.png)

按同一窗口内完成数单调增加、失败/待提交为零的条件，统计相邻状态都落在阈值内的连续观测跨度。这个算法不外推首次观测前和最后观测后的时间；在上述条件下可作保守下界。

| 剩余 prompt group 阈值 | 连续观测跨度 | 占 353.35 分钟 testing | 此时最多未完成回答数 |
| --- | --: | --: | --: |
| ≤1 | 8.01 分钟 | 2.27% | 16 |
| ≤2 | 37.04 分钟 | 10.48% | 32 |
| ≤4 | **113.13 分钟** | **32.02%** | 64 |
| ≤7 | 190.22 分钟 | 53.83% | 112 |

阈值互相包含，不能相加。未完成回答还可能在 CPU verifier/TQ 后处理，而非解码，因此真实在 GPU 上运行的数量只能更小。至少约三分之一验证时间的连续日志观测跨度内，最多只有 64 条未完成回答，不超过当前 128 条推理并发容量的一半；下一窗口却还没提交。

这支持一个更直接的系统优化：保持题目、n、长度、频率不变，采用有界的跨窗口连续投喂，在一部分请求完成后补入后续请求，减少等待最慢回答时的空档。这改变的是调度实现与在途窗口数，不减少验证工作量。仅把 student 从 4 卡增为 7/8 卡，不能自动消除这个窗口 barrier；尾部仍可能只有一张卡在做最后一条长回答。

### 4.10 验证结束的 CPU / 后处理区间

![验证末尾 GPU 观测](../figures/b38hw8v0-pipeline-20261020/validation-end.png)

验证末尾先出现仅 GPU 2 仍忙、其他卡为零的观测；随后 10:45:03–10:46:35 的最后 7 个 GPU probe，student 四卡均为 0，覆盖约 91.99 秒。Testing timer 在 10:46:47 才结束。

这段观测与等待 verifier、收集/排序输出、JSONL dump、bootstrap 指标聚合等 CPU/后处理相符，但不能从 sparse probe 精确计算这些组件各用了多少秒。当前 validation aggregation 每题对 best/majority 等做 1000 次 bootstrap，driver 上确有需要计时的 CPU 工作。不能把整个 testing 时长全归给 vLLM decode，也不能把这 92 秒直接命名为某一个 CPU 函数的耗时。这段观测跨度相比 353 分钟 testing 较小，现有证据仍更支持优先处理长 decode 与窗口长尾，而不是先优化指标汇总代码。

W&B driver RSS 在验证中的样本均值约 1777 MiB、观测最大约 1926 MiB，不是整机内存 100+ GiB，也不包含 8 个 verifier worker、8 个 AgentLoop worker 和 8 个 TQ storage 的 RSS。现有 CPU 指标缺逐组件采集，无法判断哪个 worker 或文件系统占用了剩余主机内存与 CPU 时间。

### 4.11 启动、保存与离线记录

Ray/TQ actor 创建、模型与 tokenizer 加载、数据过滤、vLLM 的 KV profiling 和首次 kernel 编译没有分别记录 timer。首步 216.867 秒及其 55.1 秒子 timer 残差只能描述部分首次成本；启动中发生在第一个 step 之前的耗时另算，不能用 steady step 或实验名称里的时间戳反推各组件初始化耗时。

保存频率为 50，这个38行历史快照 没有 checkpoint 保存样本，不能估计写盘代价。每步 update_weights 是内存中的参数同步，与保存 checkpoint 不同。验证 JSONL dump 由线程池异步执行，提交与排序在验证路径上，实际后台写入可能跨越 testing 结束；它与 bootstrap/后续工作可能重叠，需要独立线程事件才能分开计账。

W&B 在 TaskRunner 中离线记录，系统采样后台执行；后续上传快照的服务端 finished 状态不是训练循环完成的充分证据。现有 console 没有该快照中的异常退出信息，也没有完整 epoch 完成标记，因此不补造结束原因。

### 4.12 基线快照缺失的观测

| 子阶段 / 组件 | 早期快照能测到 | 尚缺证据 |
| --- | --- | --- |
| Student prefill / decode | 整体 gen 和逐卡稀疏 busy | TTFT、TPOT、prefill/decode token 数、running/pending、KV usage、preemption |
| Teacher | 逐卡采样与源码调用顺序 | Queue wait、RPC/forward/序列化分段、每请求与每副本 p50/p95 |
| Verifier | CPU worker 数与调用位置 | 排队、Math-Verify 服务时间、timeout/fallback、进程级 CPU/RSS |
| TQ | Group 状态与后端配置 | Tag 同步、tensor put/get、字节数、每 storage 的内存/延迟 |
| Actor | 外层更新时间、局部 MFU | 每 rank 的 micro-batch、recompute、memcpy、NCCL、optimizer 时间 |
| 权重同步 | update_weights timer | 参数导出、IPC、wake、KV 重建、cache reset 的各自时间 |
| 验证汇总 | testing timer 与末尾 GPU probes | 最后一条 GPU 完成、verifier 全完成、dump、bootstrap 的明确边界 |

AgentLoopOutput 已有 generate_sequences / compute_score 等字段，但本 run 的 W&B history 没有它们；teacher 还缺自己的请求 timer。数据没有记录就无法通过下载更多同一 history 字段补出这些时间。

#### 4.12.1 基线的 profiling 边界

该历史审阅版本的teacher manager不在 V1 默认 profiling manager 列表；训练 step 的停止点在随后验证之前。仅启用 teacher profiler 或将 step20 列入 steps，都不足以证明录到了 teacher 或完整验证。具体上游状态见[profiling 调研](2026-10-21-上游实现与论文基线.md#profiling-与可观测性)。现在已按[指标与验收](2026-10-21-指标与验收.md)实现常规指标和共享 teacher 阶段计时；上面的完整缺口用于后续定点诊断，不要求全部实现。
