## 测量对象

这是单轮数学 reasoning 的 on-policy distillation。代码复用了 `AgentLoop` 接口，但本配方没有 agent 工具调用、多轮环境或跨轮轨迹等待。输出长短不同会改变工作量，但目前没有证据表明长尾就是主要瓶颈。

## 流程与计时边界

完整生命周期 Mermaid、各阶段调用链、hidden IO 和 precompute/fused 算子的具体源码行号已集中到 [Full-KL 全流程源码走读](../../../full-vocab/2026-10-23-Full-KL全流程源码走读.md#pipeline)。本页只维护测量设计、观测边界和待验证问题。

Driver 的 `gen` 包含取样等待与 `on_sample_end()`，并行 reward worker 的评分也可能落在请求完成链上；没有单独的 `reward` 条目不等于评分耗时为零。Teacher/actor 的 host 区间可以包含 CUDA 等待，后台 IO 与计算可能重叠，各子区间不能直接求和。

本次记录真实请求起止、输入/输出 token 数和停止原因。vLLM 可用的 first-token 字段单独保留；缺失字段列为采集缺口。HTTP 指标补充运行/等待请求数、KV cache、累计 token 和可用时延；没有逐 token 全量事件时，不声称已经测出所有 decode token 的延迟。

现有 `timer/step` 包含按需 checkpoint 和步末权重同步；验证、指标处理、日志和 TQ 清理在这个区间之外。报告因此保留两种时间：

- **步内耗时**：`timer/step` 的开始到结束，用于拆分训练阶段。
- **完整步间周期**：本步开始到下一步开始，包含步后的额外工作。最后一步没有下一步起点，记为缺失；收尾另看命令总时长和事件。

初始化、graph capture、首次编译和首次 teacher head 获取属于冷启动问题。先单独观察，不能平均到短程稳态步骤中后再声称吞吐下降。

## 采集工具与分析顺序

| 层次 | 工具与产物 | 本次目的 | 主要限制 |
| --- | --- | --- | --- |
| 低开销总览 | driver 指标、每进程 JSONL host spans | 对齐阶段和跨进程请求，解释一个完整周期 | 主机区间包含等待/提交；观测开销尚待开关对照 |
| 请求与引擎 | 请求事件、vLLM backend metrics、HTTP `/metrics` | 区分长度工作量、吞吐、并发、排队与完成分布 | 字段依 vLLM 版本而定，缺失不补零 |
| 资源趋势 | NVML 每 2 秒采样、进程 RSS、主机可用内存、共享内存 | 解释阶段切换和资源压力 | 可能漏峰，主机指标受其他任务影响 |
| 算子与通信 | PyTorch profiler 四 rank trace | 查看 actor / teacher 算子、CUDA kernel、NCCL 和 memcpy | profile 会扰动执行；不能用其步骤替代基线 |
| 系统时间线 | Nsight Systems + NVTX | 检查训练 worker 多线程、提交、传输及同步关系 | 当前配置不自动采集全部 vLLM GPU 进程 |

用 Perfetto 或 PyTorch trace viewer 走读 Torch trace，用 Nsight Systems 打开 `.nsys-rep`。本地交互页面用于总览、筛选和统计，原始工具用于验证细节。本阶段不默认使用 Nsight Compute：只有某个 kernel 已被证明位于值得优化的关键路径上，才值得追加其 roofline / occupancy / memory throughput 分析。

当前 host spans 使用同主机 `monotonic_ns` 并保存时钟命名空间，聚合器拒绝混合不同域。Torch trace 的时间基准另行校准，在确认之前不强行叠加到 host 时间线上。不同 async 请求可共享线程，不能仅按线程嵌套关系推断请求归属；没有关联 ID 的评分子区间仅用于整体观察。

### 三个运行窗口

| 运行 | 工作量与采集范围 | 用途 |
| --- | --- | --- |
| baseline | 14 步；第 14 步保存 checkpoint 并执行小验证窗口 | 步骤 4–13 作为 10 个候选稳态样本，先检查曲线后决定是否剔除预热 |
| torch-profile | 5 步；第 4 步详细采四 rank；vLLM 前 128 个 engine iteration | 解释阶段内部；128 iteration 不是每个请求的前 128 token |
| nsys-profile | 2 步；第 2 步采训练 worker | 短窗口检查系统行为，不当稳态基准 |

三者分别从相同种子与模型开始。真实更新和动态调度仍可能使输出不同，因此不将不同运行的耗时差直接解释为 profiler 的精确开销。实际采集成本可先比较工作量相近的步骤；若足以影响结论，再增加固定输入/固定 seed 的有无采集对照。

## 图表应回答的问题

1. **每步阶段组成与完整周期折线**：训练时间到底花在哪里，预热持续多久，周期任务带来多大变化。driver 子阶段重叠时改成并列展示，不用堆叠制造错误总量。
2. **四卡显存和活动曲线**：哪些阶段出现显存峰值、资源释放和空闲。NVML busy 不是 MFU；显存已分配也不表示 GPU 正在计算。
3. **请求完成分布和长度—耗时散点**：当前 batch 的长回答工作量和最后完成区间有多大。t90 到 t100 的间隔既包含有效 decode，也可能包含调度问题，需要 trace 判断。
4. **引擎并发、KV cache 和 token 增量**：请求减少时吞吐是否同步下降，是否发生排队、cache 压力或抢占。HTTP 累计计数应求时间差分后再计算速率，不能把累计值当 token/s。
5. **Teacher/actor 与 IO 泳道**：D2H、写入、预取、H2D、head 和 backbone 的重叠情况；最终等待是否位于关键路径。
6. **每 rank micro-batch 工作量与时长**：是否存在 token 切分、序列长度或 FSDP 通信导致的不平衡。
7. **GPU trace 分类与关键片段**：矩阵乘、attention、逐元素 KL、NCCL 和 memcpy 各自的工作量，以及它们在关键路径上的暴露时间。累计 kernel duration 可大于墙钟时间，必须区分。

当前页面已提供前六类图的容器和原始 trace 覆盖入口。第七类的关键片段、精确通信重叠和 allocator 内存归因需要实际 trace 后继续补充。没有实测数据之前，不生成具有真实读数外观的占位图。

## 从现状到优化的判据

先按完整周期中的暴露成本排序，再判断是否值得深入。以一次周期耗时 `T`、某个完全串行阶段耗时 `t` 为例，即使该阶段被完全消除，总加速也不超过 `T / (T - t)`。实际有依赖和重叠时，要按关键路径重新计算；不能套用所有 kernel 时间相加的结果。

| 观察到的现象 | 下一步证据 | 可能的后续优化方向（尚未执行） |
| --- | --- | --- |
| Rollout 占比大、GPU 持续忙 | token/s、长度分布、prefill/decode trace | 推理计算效率或 batch 设置；不能先断言是长尾 |
| 请求变少时吞吐和 GPU 活动同时降低 | 引擎队列、请求结束时间、对应 kernel 时间线 | 调度、批次形成或负载分配 |
| Teacher 或 actor 的 rank 完成时间差大 | 每 rank 输入/有效 token、micro-batch 数、NCCL 等待 | 工作量平衡和动态切分 |
| Hidden IO 总量大但等待小 | read/write 与计算重叠及最终 flush | 可能无需优先优化 IO |
| D2H/H2D 或 hidden 等待占关键路径 | memcpy、CPU 等待和 payload 体积 | pinned buffer、传输/预取的更深重叠 |
| Head 算子占 actor 大头但 actor 占整步很小 | 整步暴露比例与固定输入对照 | 核算已有 fused backend 的实际端到端收益 |
| 权重同步、wake/sleep 或 checkpoint 明显暴露 | 对应 CUDA / NCCL / 文件 IO 片段 | 权重同步和生命周期管理，而非只改 KL |

已有 Full-KL 算子实验及限制见 [之前的优化结论](../2026-10-23-Full-KL优化结论与启动.md)。这些历史结果不能证明本次正式 graph rollout 的整步收益。

## 验收与仍需补齐的证据

当前已完成可关闭的埋点、三份 CPU 配置导出、空闲检测队列、聚合脚本、交互页面和计时归属单测。进入性能结论之前仍需：

- 14 步真实训练成功，并核对 loss/grad、更新计数、保存与验证；检查 4–13 步是否真达到稳态。
- 核对 64 条训练请求与实际 batch / padding、有效 token 总数和四 rank micro-batch；失败或被取消请求单独记录。
- 确认 actor、teacher 和 rollout trace 各自实际存在，指出未覆盖的进程/窗口；检查 backend timing 与 HTTP 指标缺失情况。
- 审阅原始 CUDA trace 的计算、通信、传输和同步关系；不能只用候选算子速度或脚本退出码宣布完成。
- 显存先给 NVML 趋势和 profiler 可用证据；如果需要区分参数、梯度、临时 logits、KV cache 和碎片，再追加短窗口 allocator snapshot。当前三任务没有宣称包含完整 allocator snapshot。
- 输出真实数据的 PNG/PDF/SVG、交互快照与结论文档，然后与用户讨论具体优化。

GPU 队列沿用共享锁 `/tmp/mirroropd-gpus-0-1-2-3.lock`，只有 GPU 0–3 连续空闲 120 秒才启动任务，每次任务前重新检查。没有新增第二条 GPU 队列，没有启用旧的每小时触发器，也不会结束其他任务的进程。失败重试使用新证据目录，冻结源码不做原地修改。
