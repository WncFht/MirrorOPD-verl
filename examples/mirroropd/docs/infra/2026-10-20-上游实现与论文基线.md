### #5745 → #6039：曾经支持，后来移除

#5745 区分了两种共置：一种是 teacher/student 推理副本同时留在同池，双方显存都受限制；新方式则让 student 先生成并 sleep，再唤醒 teacher 批量打分。它还提供过 8 卡共池的配置及对照图。随后 #6039 明确删除该模式，保留独立 teacher。

删除 PR 的正文没有说明充分原因，评论中也有人追问；已读取的评论没有提供维护者解释。因此不能编造“因为太慢”或“因为不稳定”作为删除原因。能确认的是功能生命周期与当前源码状态。[^colocate-old] [^colocate-remove]

### #7058：最接近 teacher/actor 共卡，但不是 FSDP2 即插即用

旧 #6914 的维护者意见要求把 teacher 计算能力从 experimental worker 移到通用 engine worker，以便同步 trainer 也能使用；作者随后转向 #7058。新补丁修改了 V1 trainer、worker 和蒸馏配置，并提供 V1 separate-async / fully-async 示例。

代码中 fused 模式不再创建独立 teacher manager/pool；teacher 在训练侧得到整个 batch 后打分。V1 实现中的 `_compute_fused_teacher_log_probs` 明确要求 `actor.megatron.param_offload=True`，并要求 nonrouter=True；worker 同时显式拒绝非 Megatron actor/teacher，示例也是 Megatron trainer/teacher。它支持 sampled-token 路径，例如 k1，而非任意 top-k 路径都可直接使用。

对本项目可以复用的是 teacher 生命周期、TQ 数据注入、计时边界与资源池设计；需要另外适配 FSDP2。不能只把 PR 中的 fused 开关复制到现有配置。维护者还指出其中 legacy fully_async 目录将迁往 recipe，增加了整包移植的维护成本。[^fuse-old] [^fuse-new]

### #6920：FSDP teacher 不等于已经共享 GPU

该 PR 的模型正好是 DeepSeek-R1-Distill-Qwen-1.5B 与 JustRL-DeepSeek-1.5B，提供 frozen forward-only teacher 和 `gather(logits, ids) - logsumexp(logits)` 的分块实现，适合取得 student 指定候选 token 的概率。

但它主要修改 `ray_trainer.py`，没有直接接入我们当前的 V1 trainer。其示例注释提到共置，实际初始化代码仍通过 `get_resource_pool(Role.TeacherModel)` 取得 teacher pool，并把 teacher worker 注册到该 pool；该 head 的 `main_ppo_v0.py` 仍新建独立 teacher_pool 并映射 Role.TeacherModel。按这条资源映射，示例的 student=8、teacher=8 会申请 16 张卡，不能当作单机 8 卡共享。不能仅根据 FSDP teacher 或示例注释判断物理卡是否复用。

它还同时引入 `reverse_kl_topk`，与当前 sampled-token k1+PG 不同。若参考该 PR，应只提取 teacher forward/gather 与资源管理部分，保留当前 loss。[^fsdp-teacher]

这些方案分别见对应 issue/PR。[^shared-teachers] [^hidden-rfc] [^nitrobrew] [^fused-topk] [^topk-memory] [^tail-kl]

#7307 的池共享范围是 teacher 与 teacher，不是 student 与 teacher。它通过控制同时 awake 的 teacher 数量降低多 teacher 的常驻显存与资源占用；当前单 teacher 并没有多个模型可换出。

Full-vocab/hidden-state 方案也有明确适用范围。按约 40 万有效 token 粗算，单个 FP32 sampled log-prob 的理论 tensor payload 仅约 1.5 MiB；BF16、hidden=1536 的 hidden state 则约 1.15 GiB。后者能替代极大的全词表 logits，但不会比当前单 token 概率更省。实际 HTTP/对象开销另算，这个估算不能当作端到端通信计时。

#6194 的评论重点要求复用现有 manager/replica 抽象、支持多 teacher，并讨论去掉额外的 SVD head 压缩。它是可参考的 full-vocab 实现，不是解决我们 teacher 等待 student 的直接开关。[^nitrobrew]

### 推理引擎与 FSDP teacher 的取舍

Issue #5731 直接讨论了 teacher 为何使用推理引擎，回复指出多 teacher 部署的灵活性。这个理由不等于已经证明当前 1.5B teacher 的独立四卡配置最优；讨论中也有人追问数值差异的消融。应比较的是同一 sampled token 输入下的概率、打分吞吐与资源占用，而不是假定某个后端天然更快或完全等价。[^teacher-engine]

## NeMo RL 的共置与分池实现

审阅提交为 `d1e23adb3df33dedd0e9c6edd9482430a2e5e8ad`。`examples/run_distillation.py` 调用 `nemo_rl/algorithms/distillation.py`；共置时 `train_cluster` 和 `inference_cluster` 指向同一个 `RayVirtualCluster`，vLLM 路径允许三组 worker 共置。Teacher `Policy(init_optimizer=False)`、student `Policy` 和 student `VllmGeneration` 都放在这组资源上。[^nemo-loop]

代码的切换顺序是 refit student→student generation→`finish_generation()`→teacher `prepare_for_lp_inference()/get_topk_logits()`→teacher `offload_after_refit()`→student `prepare_for_training()/train()`。Automodel worker 的 offload 将模型和优化器放到 CPU；普通 vLLM worker sleep 使用 level1。共置权重同步使用 CUDA IPC/ZMQ，随后卸载训练态并唤醒 KV。完整调度图集中在[方案 S3](2026-10-20-八卡调度方案.md#s3同步共享八卡分阶段运行冻结-teacher)。[^nemo-offload] [^nemo-vllm] [^nemo-refit]

`validate()` 使用同一个 student generation 接口，没有 teacher 参数；共置时可覆盖全部推理池。它仍按 dataloader batch 逐批等待，不能当作已解决跨窗口长尾。官方网页有旧 backend 说明，因此资源与切换判断以固定提交代码为准，不将当前实现倒推为论文作者当时的配置。

## 本地 One-Shot-OPD 与 ResOPD

本地 One-Shot-OPD 的固定版本 `6b6b1782` 中，`register_opd_teacher()` 将teacher worker注册到actor共置集合；冻结FSDP teacher前向后返回sampled token概率，参数可CPU offload。`ray_trainer.py` 在重算old log-prob后调用teacher逻辑。它是共享资源的直接参考，但V0 DataProto、训练reward/advantage分支与当前V1/TQ不同；迁入时保留当前current-policy k1+PG，不能复制冻结reward路径。[^oneshot-mixin] [^oneshot-worker]

ResOPD审阅配方为 `3bdf019d`：student Qwen3.5-4B用4卡，teacher Qwen3.5-27B用4卡、TP4，top-k4与resopd loss。大teacher的容量解释了这组配比的用途，不能由其存在推断我们小teacher的4+4最优。上游#8228新增相应loss，当前仍未合并；head/tail估计和支持集处理不消除专用teacher池等待。[^resopd] [^resopd-pr]

## 论文 2610.11291 的设置与比较边界

读取版本为v1。原文比较OPD与Semi-OPD，在17对模型上研究初始teacher/student分布重合与蒸馏效果；其基础设施写明NeMo RL DTensor训练、vLLM生成、1–8节点，每节点8×H100。逐模型TP/DP、CPU offload和角色分配未披露，也未给出NeMo RL版本；当前源码只能证明框架存在共置实现，不能补成作者的运行配置。[^paper]

| 设置 | 论文主实验 | 当前math基线 |
| --- | --- | --- |
| 数据 | 去重DAPO英文14116题 | 当前parquet17917题 |
| 每批prompt / 每题回答 | 128 / 1 | 64 / 1 |
| Prompt上限 | 2048 | 4096 |
| Thinking训练回答上限 | 16384 | 7168 |
| 训练采样 | T=1，p=1 | T=1，p=1 |
| 优化 | AdamW，lr1e-6常数、无warmup，wd0.01，clip1.0，BF16 | 上述优化器数值相同 |
| 数学评测 | AIME24/25/26、HMMT Feb26，avg@32，T1/p1，通常32768 tokens | MATH500/AMC23/AIME25，mean@16，T0.7/p0.9，31744 tokens |
| 训练目标 | sampled-token reverse KL，advantage停梯度 | current-policy k1+PG |

Semi-OPD固定的是初始student回答和teacher概率，当前student概率及advantage仍随更新重算。原文表3包含同名DeepSeek-R1-Distill-Qwen-1.5B→JustRL-DeepSeek-1.5B：初始top64 overlap79.7%，最后共同评测点Semi-OPD高1.4个百分点，但曲线面积/训练区间的差为−1.36个百分点。这些是论文值，不是我们当前数据上的overlap测量。[^paper]

表4的11.4倍来自Qwen3-1.7B←4B-Instruct案例：100步56.8与5.0 H100 GPU小时。Semi-OPD成本包含离线生成、teacher打分和训练，但所有方法排除验证；该行Semi-OPD训练cap4K、OPD cap16K。不能将它写成同算法、同轨迹预算只改调度的加速。与我们相同1.5B→1.5B没有对应成本行。[^paper]

### Lightning OPD：确实取消在线teacher，但对照并非同池

读取 `configs/opd/qwen3-4b-opd.py`：独立SGLang teacher固定设备6,7、TP2；actor2卡，rollout4卡。在线配置每轮64 prompts×4回答，global batch256、response4096。不能将其2+4+2称作两个模型轮流占满8卡。

读取 `configs/lightning_opd/qwen3-8b-lightning-opd.py`：actor8、rollout0，global batch256，response4096，训练TP4、PP1、CP1。`data_curation/prepare_lightning_opd.py` 将teacher概率写入parquet metadata；`slime/rollout/sglang_rollout.py` 检测离线标记后直接使用response token，不调用在线生成；`slime/rollout/on_policy_distillation.py` 优先读取缓存teacher概率；Megatron loss中使用teacher-minus-current-student log-prob。[^lightning-code]

作者完整流程还包含teacher生成SFT数据、student SFT、student rollout、teacher预计算和离线训练。SFT默认启动脚本使用多节点，离线训练未给出与我们相同的在线八卡验证生命周期。八卡改造目标图见[方案 A1](2026-10-20-八卡调度方案.md#a1lightning-opdsft-初始化后离线蒸馏)，不能将其README整体称作默认八卡已验收。


离线预计算入口与在线对照的资源声明还需分别检查：`scripts/serve_teacher_8b.sh`使用TP8；`configs/sft/run_sft.sh`默认4节点×8卡。它们与在线对照的teacher2卡不是同一个阶段。迁入八卡时应逐阶段重配，不直接套用README硬件表。[^lightning-server] [^lightning-sft]

### Relay-OPD：生成池里同时有target与draft

读取 `opd/scripts/relay_opd/train.sh` 和 `vllm_async_server.py`：总池为actor/rollout4加teacher scoring4，生成服务将main model路径切为teacher target，通过`speculative_config`加载student draft。`opd/patches/vllm/speculative_decode.py` 按条件触发teacher接管、记录teacher mask与实际token概率。默认K5、最多接管M2次、每次L3段；默认训练response16384、batch/mini128，训练入口默认不开周期验证，仓库提供独立student评测脚本。[^relay-code]

它固定vLLM0.21.0并patch内部采样/weight update路径，与我们0.25.1接口不同。该机制增加生成阶段teacher工作，并改变轨迹；完整图见[方案 A3](2026-10-20-八卡调度方案.md#a3skd--relay-opdteacher-介入生成)。评价student能力必须独立做student-only生成，不能用teacher接管后的回答分数替代。


双模型恢复也有专门处理：`utils.py::_use_opd_draft_only_sync`只将actor权重注入student draft，保持target teacher固定；`_sleep_hybrid`对该引擎采用level1。如果丢弃target/draft双方权重却只重传draft，teacher没有恢复来源。S2/S3应逐模型声明恢复来源，不能将它们压成一个无角色区分的wake调用。[^relay-utils] [^relay-server]

### SKD：作者原始实现与Relay复现不同

Google原始代码的README提供7B teacher、2B student、8×A10080GB设置。`config/kd_train.yaml` 默认8进程；`train/ddp_skd.py` 将student和冻结teacher都交给Accelerator，在同一进程使用teacher的`generate(...assistant_model=student...)`，随后做student/teacher前向与KL训练。它不是verl的4+4独立池，也不是按阶段sleep/wake的NeMo模式。原始实现需要Transformers4.44.2生成代码替换，数据获取与完整可运行性未在本机验收。[^skd-code]

Relay的 `baselines/skd.sh` 是另一实现：draft proposals4、acceptance top-k5、默认forward_kl_topk_teacher_renorm、k128、固定4+4。不能将它的loss与2610.11291统一sampled-token目标或我们k1+PG混为一谈；代码存在与原论文结果严格复现是两个判断。

### FastOPD：prefix算法与公开代码的边界

对应论文是arXiv2602.15260《Fast and Effective On-policy Distillation from Reasoning Prefixes》，不是arXiv2610.02832的同名VLA工作。作者公开TeX提到prefix-only GKD参考实现distillm和verl FLOP counter；公开投稿版注明代码在附件中。已核对ACL页面和作者论文，但尚未核验该附件内容，未确认作者维护的专门FastOPD仓库。因此不写成“作者没开源”。[^fast-paper] [^fast-submission]

可以直接阅读的第三方代码是Relay的 `opd/scripts/baselines/fastopd/4096.sh`，仅设置 `MAX_RESPONSE_LENGTH=4096` 并执行 `../opd.sh`，另有1024/2048/8192对照。标准入口仍为4+4与k1 PG。它证明这套对照的训练prefix设置，不证明作者所有调度、训练目标或报告FLOPs完全相同。
