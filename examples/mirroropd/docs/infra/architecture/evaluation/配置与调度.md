# 统一验证的配置与调度契约

本页保留任务抽象与配置演变方案，示例不是可直接运行的 Hydra 配置。已实现的字段和入口以[评估包合同](../../../../../../verl/trainer/evaluation/README.md)为准；概率空间与模型能力的扩展见[动作空间与模型兼容](动作空间与模型兼容.md)。科学预算只在[四域协议](../../../experiments/teacher-transfer/transfer-mechanism/2026-10-31-四域单域训练与RKL评估协议.md)维护；本页定义这些设置怎样映射为任务与执行计划。相关取舍见[决策记录](../../../../.agents/notes/proposed/architecture/2026-10-31-统一验证的任务计划与产物边界.md)。

## 1. 四个核心抽象

| 抽象                    | 负责什么                                                              | 不负责什么                                  |
| ----------------------- | --------------------------------------------------------------------- | ------------------------------------------- |
| `EvalTaskSpec`          | 评什么、在哪个边界评、引用哪些轨迹、比较哪些权重                      | 不直接操作 GPU，不嵌入 Python 条件表达式    |
| `EvalPlan`              | 对一个冻结训练边界解析到期任务、缺少的生成请求、结果消费者和 RKL 窗口 | 不读取指标决定下次频率，不持有 Ray handle   |
| `EvaluationCoordinator` | 执行计划，协调现有 RolloutService／worker／scorer，提交结果           | 不实现另一个训练循环，不重新实现 RKL 数学   |
| `ArtifactStore`         | Parquet 轨迹／结果、history 引用及最小产物 manifest                   | 不保存长期 teacher hidden，不充当 TQ 替代品 |

`GenerationProtocol`、`ExecutionProfile`、`ActorVersion`、`InputRef`、`TaskOutcome`是这些边界的数据结构，不各自扩成一个服务。首版只需要两类评分任务：`accuracy`和`rkl`。生成是被消费者请求的公共能力；bank 构建是从生成产物选取样本的操作。

## 2. 三种配置不得混在一起

1. **科学协议**：题目清单、n、T/top-p/top-k、cap、template/mode、EOS、seed 策略、RKL 支持集与评分精度、聚合方式。它决定结果含义。
2. **执行资源**：GPU 集合、TP／副本数、max_num_seqs、prefill token budget、KV bytes、FSDP 推理微批预算、head chunk、CPU hidden 窗口和 I/O 并发。它决定容量与速度。
3. **调度**：在哪个完整训练边界执行任务。它不能覆盖前两者或根据 acc/RKL 好坏临时换题、换 n。

不同 bench 通过不可变的 resolved protocol 逐请求传递参数。相同模型可以在同一个 vLLM 引擎接收不同 T、n 和 cap 的请求；无需每换 bench 重建引擎，也不能原地修改共享`val_kwargs`。n 是请求次数，`max_num_seqs`是引擎并发上限，两者独立。现有`__rollout_n__`可作为兼容入口，新增协议最终都汇入同一请求构造器。

引擎级 max_model_len、TP 和 KV 容量在创建时确定；逐请求 cap 不能把一个短上下文引擎变成长上下文引擎。Current student 的同一引擎按训练和公共任务所需的最大上下文预先验收，训练请求仍限 7K。请求级 inflight 可以限流，但不能假装动态修改引擎的 max_num_seqs 或 TP。首版优先使用一个已校准的 student 引擎包络；只有实测表明明显损失吞吐，才考虑按阶段重建引擎并把启动代价算入总时间。

Hydra／OmegaConf 保留为配置层，用 dataclass schema 在启动前检查字段和类型；不另造配置语言。Task guide 中常见的 generation kwargs、重复次数和后处理分离也支持这一边界，但不引入第二套评测主程序。[^hydra][^harness]

## 3. 可审查的配置形状

下面的路径是待提供的 manifest 位置；资源数值仅是待校准候选。示例 prompt_limit 也不是已冻结的题目过滤阈值，必须根据渲染后长度和双方上下文容量确定。`evaluation`命名空间需要 P1 实现后才能用于生产。Accuracy manifest 覆盖已确认的各 bench 全集，共 1648 题；public_rkl_panel 单独引用抽样的 512 题。

```yaml
evaluation:
  schema_version: 1
  clock: outer
  artifact_root: runs/teacher-transfer
  bootstrap: before_trainer

  protocols:
    source:
      temperature: 1.0
      top_p: 1.0
      top_k: -1
      max_new_tokens: 7168
      prompt_limit: 2048
      template: run.input_protocol
      seed_stream: evaluation/source
    public:
      temperature: 1.0
      top_p: 0.95
      top_k: -1
      max_new_tokens: 32768
      prompt_limit: 8192
      template: run.input_protocol
      seed_stream: evaluation/public

  datasets:
    source_holdout: {manifest: manifests/source-holdout.json, protocol: source, n: 1}
    math500: {manifest: manifests/math500.json, protocol: public, n: 1, verifier: math}
    amc23: {manifest: manifests/amc23.json, protocol: public, n: 16, verifier: math}
    aime24: {manifest: manifests/aime24.json, protocol: public, n: 16, verifier: math}
    aime25: {manifest: manifests/aime25.json, protocol: public, n: 16, verifier: math}
    aime26: {manifest: manifests/aime26.json, protocol: public, n: 16, verifier: math}
    lcb_v5: {manifest: manifests/lcb-v5.json, protocol: public, n: 10, verifier: lcb}
    gpqa: {manifest: manifests/gpqa-diamond.json, protocol: public, n: 4, verifier: gpqa}
    ifeval: {manifest: manifests/ifeval.json, protocol: public, n: 1, verifier: ifeval}

  collections:
    public_accuracy: [math500, amc23, aime24, aime25, aime26, lcb_v5, gpqa, ifeval]
    public_rkl_panel: {manifest: manifests/public-rkl-panel.json}

  productions:
    initial_public: {model: initial_student, collection: public_accuracy}
    teacher_public: {model: teacher, collection: public_accuracy}
    initial_source: {model: initial_student, datasets: [source_holdout]}
    current_public: {model: current_student, collection: public_accuracy}

  banks:
    initial_public: {producer: initial_public, selector: public_rkl_panel, sample_indices: [0]}
    teacher_public: {producer: teacher_public, selector: public_rkl_panel, sample_indices: [0]}
    source: {producer: initial_source, sample_indices: [0]}

  history:
    capacity: 128
    policy: equal_batch_priority
    seed: 42
    tokens: actual_training

  schedules:
    source: {at: [0], every: 1, start: 1, final: true}
    history: {every: 1, start: 1, final: true}
    banks: {at: [0, 1, 2], every: 5, start: 1, final: true}
    bench: {at: [0, 25, 50], final: true}
    bootstrap: {at: [0], final: false}

  tasks:
    source_rkl: {kind: rkl, input: {bank: source}, schedule: source}
    history_rkl: {kind: rkl, input: {history: true}, schedule: history}
    initial_bank_rkl: {kind: rkl, input: {bank: initial_public}, schedule: banks}
    teacher_bank_rkl: {kind: rkl, input: {bank: teacher_public}, schedule: banks}
    bench_acc: {kind: accuracy, input: {production: current_public}, schedule: bench}
    bench_current_rkl:
      kind: rkl
      input: {production: current_public, selector: public_rkl_panel, sample_indices: [0]}
      schedule: bench
    teacher_acc: {kind: accuracy, input: {production: teacher_public}, schedule: bootstrap}

  rkl:
    student: current_student
    teacher: teacher
    temperature: 1.0
    support: native_equal
    numeric_profile: native_bf16_fp32
    report_aggregation: question_mean_of_token_mean
    history_aggregation: equal_batch_mean
    public_aggregation: equal_domain_mean

  execution:
    generation_profiles:
      small_dense:
        tensor_parallel_size: 1
        max_num_seqs: 32
        max_num_batched_tokens: 16384
        gpu_memory_utilization: 0.65
        max_model_len: 40960
        max_inflight_requests: 256
      larger_teacher:
        tensor_parallel_size: 2
        max_num_seqs: 8
        max_num_batched_tokens: 16384
        gpu_memory_utilization: 0.65
        max_model_len: 40960
        max_inflight_requests: 64
    model_profiles:
      initial_student: small_dense
      current_student: small_dense
      teacher: small_dense
    rkl:
      student_tokens_per_gpu: 49152
      teacher_tokens_per_gpu: 49152
      token_chunk: 256
      teacher_payload_window_bytes: 17179869184
      host_copy_reserve_factor: 2.5
      async_write: true
      microbatch_prefetch: true
    verifier_workers: 8
```

该示例不表示`small_dense`适合所有小模型。资源 profile 必须按实际模型配置校准；改变模型绑定时，资源预检必须重跑。Teacher 使用`larger_teacher`前，冻结模型生成的 TP2 路径也要独立验收；现有训练 rollout 的 frozen executor 被限制在 TP1。

输入解码、final-answer parser、verifier 版本和停止 token 等较长定义放入被引用的 input／verifier 定义（合入共享配置或其不可变引用），生成完整 resolved protocol 后再发请求。不能靠未记录的模型 generation_config 默认值补齐科学参数。

## 4. 时钟和计划编译

首版在完整 outer 边界调用一次`plan(boundary)`，初始边界为 0。Boundary 携带 outer、已尝试更新数、成功更新数、run/attempt、当前模型版本及配置 hash。复用原生`OptimizerProgress`，不再凭 outer×reuse 伪造成功更新数。

`at`、`every`和`final`取并集，同一点只触发一次；`every`必须为正整数，且不早于 start。`final`是本次配置的实际预算终点，不硬编码 50。首版不在 inner 中途插入评分；未来需要 optimizer 时钟时，必须定义实际可用的模型边界，不能将跨过的多个目标步伪装成同一 checkpoint 的多次测量。

计划编译依次完成：

1. 选出到期任务，检查当前 ActorVersion 在本次事件内不可变。
2. 解析 bank／history／generation 输入；history 绑定刚完成的训练批次集合。
3. 将 accuracy 与 current RKL 需要的相同 sample 合并为生成请求并集。身份至少包含生成模型版本、问题与渲染输入、protocol、sample index 和 seed。
4. 将已存在的冻结 bank 或初始化评估产物绑定到具体内容 hash。已绑定的 bank 不追踪一个可变化的 latest 路径。
5. 将 RKL 按 student 版本、teacher 身份、输入 token 对齐规则、支持集及数值口径分组；origin／domain 不是必须换模型的理由。
6. 在各兼容组内按真实长度和字节预算分块，形成固定顺序的执行计划。
7. 输出计划摘要：到期任务、缓存命中、需要生成的回答数、需要评分的逻辑轨迹数、窗口、资源和预计上限；这些不是性能实测。

这一过程只需少量 typed 操作和固定阶段顺序，不需要引入通用 DAG 调度系统。相同问题的不同回答不能去重；相同轨迹的不同模型版本 RKL 也不能复用。

### Trainer 边界的最小调用合同

拟议入口是`compile_plan(boundary, tasks, artifact_inventory)`与`coordinator.execute(plan)`。前者是纯函数；后者返回带完成状态和逐任务产物引用的结果，退出时生成引擎保持休眠，交由同一个 outer 边界完成最终导出（如到终点）和生成引擎恢复。不要让每个 scorer 自行唤醒 vLLM。

```text
完成本批actor更新，冻结Boundary与当前权重版本
持久化真实训练shard；更新history索引
plan = compile_plan(Boundary, TaskSpecs, ArtifactInventory)
result = coordinator.execute(plan)
    有current生成：确保当前版本 → 原生生成 → drain并休眠
    各兼容RKL窗口：teacher评分 → student评分 → 清理本窗口
    收齐verifier；提交完整评估产物
提交outer进度、数据游标与history
仅最终节点：在rollout仍休眠时原子导出一个model-only，不保存optimizer
非终点：确认actor释放，沿既有RolloutService恢复当前版本并进入下一批
终点：导出完成后结束；异常不进入下一批、不提交伪完成记录
```

`Boundary`和`InputRef`是普通不可变数据，不包含活跃 worker 句柄。资源句柄由执行 adapter 持有，scorer 只返回逐题 sum/count 或任务结果；汇总、文件发布和异常处理由协调器统一完成。Accuracy 聚合结果和 bank 各有完整性记录，不能仅因 bank 已存在就宣称整套 n 次 accuracy 也已完成。

## 5. 初始化与后续节点

### 5.1 冻结模型准备放在 Trainer 创建前

首版建议在 prepare 阶段用同一原生生成 adapter 完成 teacher 和 initial student 的评估、source bank 及两份公共 bank。独立预备进程拥有 GPU 资源，结束并释放后再创建训练 worker，避免训练 worker 已占 Ray GPU 资源时又启动 standalone teacher 服务。所有产物由同一个 ArtifactStore 管理，准备完成标记和模型／协议身份匹配后才启动训练。

这多了一个显式 prepare 阶段，但不新增训练循环。它使 teacher 按自己的 TP／并发配置生成成为可能，也避免把训练用 frozen TP1 限制隐藏在评估里。已有 bank 可跨训练域／配对复用时，prepare 直接命中缓存。将来需要进程内复用，再在相同接口下优化，不改变任务与产物语义。

初始 bench current 任务可以引用 initial student 的完整评估产物；公共 RKL 取其中的 sample0。Teacher acc 使用 teacher 完整产物，teacher bank 取其 sample0。初始化 RKL 仍比较 initial student→teacher，源留出 128 加两份公共 512，最多 1,152 条记录。

### 5.2 普通、bank 与 bench 节点

| 节点       | 生成需求                                        | RKL 输入                                            |
| ---------- | ----------------------------------------------- | --------------------------------------------------- |
| 普通 outer | 只有训练生成                                    | source128＋history128                               |
| bank 节点  | 不新增公共生成                                  | 再加 initial/teacher 公共 bank 各 512               |
| bench 节点 | 同版本 current student 按各 bench 的 n 生成一次 | 再取指定 512 条 current 回答；accuracy 消费全部回答 |

Bench 节点必须先确保 vLLM 装载当前版本再生成，然后休眠，再将本轮所有兼容 RKL 任务一起分块评分。CPU verifier 可以与同次评估的 GPU 评分重叠，但首版在离开评估边界前收齐必需结果，不引入跨 outer 的后台评估队列。

## 6. 权重版本与请求身份

传输 request ID 可以带 attempt nonce；科学 sample ID 不使用随机 UUID 或完成顺序。Eval seed 建议由 suite seed、评测集合、问题 ID、sample index 和独立 eval namespace 派生，训练使用独立 namespace。是否使用跨 checkpoint 配对 seed 作为研究约定写入 protocol；首选保持相同问题／sample 的 seed，checkpoint 身份仍进入生成产物 key。

n 不进入单个 sample 的随机身份：从 n1 扩到 n16 不能重新定义 sample0。默认 vLLM 并不保证仅靠 seed 就跨调度逐 token 一致，因此要保存实际 token；数值复现、语义身份与吞吐配置分别记录。[^repro]

当前 student 与 initial student 只在实际初始权重和输入／采样协议相同的边界允许别名。Resume 到已更新权重后，缺少 initial bank 不能拿当前 student 补生成。每个正常 RKL 任务比较的是声明的 student 与 teacher，不随输入 bank 的生成者切换两侧模型。

## 7. 兼容与演变

旧的`test_freq`／`val_before_train`在没有新 evaluation 配置时保留行为。启用新配置后，由一个计划器拥有所有评估触发；同时显式设置旧周期回调应拒绝，不能静默运行两次。`FixedRKLReadout`可保留为迁移适配器，只转换为 source/history 任务并警告旧路径，不继续维护第二套执行逻辑。

未来增加领域只添加 dataset／verifier／renderer 适配；增加固定状态来源只增加 InputRef 与 bank；新增模型通过能力验收与 execution profile；新评分数学需要新增 scorer，不复制 generator、history 或存储层。多教师评分、不同 tokenizer、异步训练、multi-turn 及跨卡数恢复不在首版支持范围，配置应明确拒绝而不是假装通用。

首版训练配方固定 LR1e-6、reuse32 和训练 token-mean；周期 checkpoint 关闭，仅最终导出 model-only。上面的 evaluation 命名空间只定义验证，不用 report_aggregation 改训练梯度。全集 accuracy 生成每模型每节点 6703 条，RKL 仍只取指定面板；首次 teacher 与 initial student 加来源留出共 13534 条。
