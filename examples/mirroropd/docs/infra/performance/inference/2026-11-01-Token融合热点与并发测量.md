# Token fusion 热点与并发测量

更新日期：2026-11-01。本文维护受控热点、自然生成并发与拓扑的实测证据，适用版本和负载分别在各节声明。当前功能支持见[Rollout 支持范围](../../rollout/fusion/support.md)。下列章节从旧 vLLM 方案迁入，保留原章节锚点和测量口径；单独生成收益不外推为完整训练收益。

## 8.4 Token fusion 的受控热点测量

2026-10-31 在 `28180c4b` 上完成十个独立生成诊断，使用物理 GPU 4、5，环境为 vLLM 0.25.1+cu129、Torch 2.11.0+cu129。P 配对为 R1-1.5B＋Polaris-7B-Preview，Q 配对为 Qwen3-1.7B non-thinking＋Qwen3-4B-Instruct-2507。每组的两侧读取相同 token 前缀；Q 使用 student 的 non-thinking 模板。完整模型 revision、输入、命令和失败启动记录保存在仓库内 `runs/token-fusion-hotspots-20261031/`。

诊断使用真实 DAPO prompt、α=0.5、temperature=1、top-p=1、top-k=-1，保留逐请求 seed；仅在诊断中忽略 EOS，固定每条回答的解码步数。TP1、BF16、Triton attention、KV 预算 24 GiB、声明上下文 11264；prefix caching 和 chunked prefill 关闭。每个配置完整预热一批后测三批，随后单独采集 32 个 worker step 的 trace。短窗口从约第 128 个 engine step 开始，较长窗口从约第 1536 步开始，KV 由实际逐步生成累积。它们不是自然生成、cap7168 容量或训练生命周期验收。

| ------------------------- | ---------------- | -------------------: | --------: | -------------------: | --------: |
| Eager，logit              | 32／384          |               12.242 |      1004 |               13.762 |       893 |

十个配置均完成预热和三次测量，原生计数均为零抢占；各配置内部三次输出 token 哈希一致，不代表不同配置或后端逐 token 一致。Q 短批三次测量保留了约 0.3 秒的波动，没有剔除异常值。独立生成进程的 NVML 采样峰值约为 P 45.2 GiB、Q 37.7 GiB，包含启动和固定 KV 预分配；这不表示长上下文提高并发不会增加所需 KV，也不代表训练切换峰值。

热点采用真实 GPU kernel 时长求和，通过 CPU External id 和 graph launch correlation 归因。Profiler 的 GPU user annotation 区间可能包含空隙，不能直接作为 kernel 时间，也不能将父子区间相加。分析脚本包含异步 kernel 与 CPU 标注错位的反例检查。以下为 logit fusion 的 GPU kernel 时间占比；attention kernel 列是模型主体的子集，不能再次相加。

| 配对／窗口    | 双模型主体 | 两个 LM head | 融合、对齐与 mask | 完整 sampler | 其中 attention kernel |
| ------------- | ---------: | -----------: | ----------------: | -----------: | --------------------: |
| P／短窗口     |      90.1% |         6.0% |              1.0% |         2.8% |                  8.5% |
| Q／短窗口     |      89.5% |         6.1% |              1.0% |         3.2% |                 18.1% |
| P／约 1536 步 |      91.6% |         5.1% |              0.8% |         2.3% |                 22.4% |
| Q／约 1536 步 |      93.6% |         3.7% |              0.6% |         1.9% |                 50.2% |

其余约 0.1%–0.2% 为 runner 辅助 kernel。短窗口 probability 的融合部分占比为 P 3.6%、Q 4.0%，完整批耗时较 logit 增加约 3.5%。因此，融合公式本身不是当前主要成本；即使完全消除该部分，也不足以支持成倍提速的预期。逐请求随机噪声确有额外 kernel 启动，但整个 sampler 的 GPU 占比仍较小。当前 top-p=1、top-k=-1 不执行排序过滤分支。

Eager 的细分归因中，P 的 teacher MLP 占全部 kernel 时间约 47.1%；Q 的 attention 模块合计约 43.5%，包含 QKV/O 投影，不能等同于 attention kernel。Graph 相比 eager 的未开启 profiler 墙钟加速为 P 3.38 倍、Q 4.18 倍，短窗口 kernel 总时间变化较小，支持“减少 CPU 逐算子提交空隙”的解释。正式 fusion 已启用 decode graph，这不是尚未开启的额外优化开关。带 profiler 的 active fraction 只用于观察 trace，不作为生产 GPU 利用率。

较长窗口中，P 的 32 步 kernel 时间从约 284 ms 增至 334 ms，Q 从约 252 ms 增至 409 ms，增量主要来自 attention。Q 的双模型 KV 每 token 为 256 KiB，显著高于 P 的 84 KiB，因此下一阶段必须把并发和实际历史长度一起考虑。短负载活跃请求从 32 增至 64，吞吐分别提高约 74% 和 79%；但 Q 的 64 条请求同时达到 11264 长度时，仅 BF16 KV 理论值就为 176 GiB，不能将短批配置直接用于单卡正式负载。

后续按以下顺序推进，保留既有数学、版本和失败合同：

1. 按配对和实际历史长度扫描活跃请求与 KV 预算，确认完整 batch64 的墙钟、长度分布和零抢占范围；优先利用已经观测到的批量收益。
2. 在两卡比较 TP2 与两个 TP1 replica，保持全局工作量一致，补齐同前缀数值、refit 和训练切换检查。不能将独立生成吞吐直接外推为 outer 提速。
3. 对 Q 的长 KV attention 路径和 P 的 teacher MLP／GEMM 路径分别研究后端与编译候选。更大的批量收益与计算、权重读取的摊销改善一致，但尚无 SM/HBM 计数，不能断言所有 GEMM 均受显存带宽限制。
4. 再评估 probability 归一化、FP32 加权和 mask 的融合实现；预期收益受上述占比限制，必须通过固定 logits 的 FP64 oracle、合法支持与 behavior log-prob 检查。
5. 双 CUDA stream 放在上述工作之后。两侧模型共用同一 GPU 的计算与带宽资源，顺序执行本身不能证明重叠执行会更快。

这些测量没有修改正式训练设置或生产融合算术。各批原始时间、kernel 归因、显存与重复性结果见[诊断汇总](../../../../../../runs/token-fusion-hotspots-20261031/summary.json)，代码与资源身份见[执行清单](../../../../../../runs/token-fusion-hotspots-20261031/manifest.json)。

## 8.5 完整自然生成的并发与拓扑选择

2026-10-31 继续使用 §8.4 的 P/Q 配对、原生精度和采样参数，在 GPU 4、5 测量固定 64 条 DAPO prompt、response cap7168、声明上下文 11264。停止规则恢复为自然 EOS：P 使用 151643，Q 使用 151645、151643，并保留 Q 的 non-thinking 模板。两侧均为固定初始 checkpoint。每次启动排除一批完整预热，计时包括完整生成与结果收集，启动、权重哈希和审计另计。其他 GPU 的同期占用、CPU RSS 和 GPU 资源采样保存在各运行目录，不能由这里的 GPU 数值推定共享 CPU/I/O 完全隔离。

在该负载下，优先选择 P 单卡 C64/KV48、双卡 TP2 C64/KV32；Q 双卡优先 TP2 C32/KV48。Q 单卡 C32/KV60 仅作为容量较紧的候选，C16/KV48 留有更多空间。容量还依赖输入：P 的 BF16 双模型 KV 为 84 KiB/token，Q 为 256 KiB/token；全部17917条冻结 DAPO 数据渲染后的最长 prompt 分别为 1493、1500。P 的 C64/KV48 能覆盖这份数据的 cap7168 上界，但不覆盖任意 4096-token prompt。Q C32/KV60 对任意批次无保证；固定 seed42、batch64、n=1、无补样的实际 sampler 顺序中，前 40 批按块取整及额外块保守估计最高 57.59 GiB。见[输入审计](../../../../../../runs/token-fusion-tuning-20261031/prompt-audit.json)与[批容量审计](../../../../../../runs/token-fusion-tuning-20261031/batch-capacity-audit.json)。这只是输入侧 KV 上界，不包含训练 actor、refit 或其他驻留内存。

Q 配对的 TP1、C16/KV48 候选已在 `462e3f3a` 上完成 LM/PM 各 40 轮、640 次真实更新与规定读出，整作业 NVML 峰值分别为 67.05、66.65 GiB。普通 outer 中位耗时为 493.9、513.9 秒；完整作业中评估读出占约 37%–39%。详细条件、图表和计时边界归[Qwen 六种前缀报告](../../../experiments/rollout-policy/2026-11-01-Qwen3非思考模式六种前缀对照.md#速度显存与完整成本)，不将这项结果扩展为 C32、TP2 或其余科学条件的训练验收。

## 8.6 私有生成器的训练窗口

公共启动入口的引擎窗口兼顾训练和验证，按 prompt cap 加两类 response cap 的较大值设置。固定 single 和 native fusion 只执行训练生成，之前仍继承该窗口。现在两者共用 `training_generator_config`，将私有副本的窗口限制为训练 prompt cap＋response cap，并保留更小的显式窗口；借用的 current/validation 引擎和调用方配置保持原值。

以 Qwen4B 固定 teacher、并发 32 为例，prompt4096、训练响应 7168、验证响应 31744 会产生共享窗口 35840。修复后的私有窗口为 11264，自动 KV 原始预算从理论 157.5 GiB 降至 49.5 GiB；这两个数是预算公式值，不能当作实测释放的显存。更高并发仍可能超出单卡容量。CPU 回归覆盖固定 single、native fusion、副本隔离与较小显式窗口。GPU 4 上真实 Qwen4B 固定 teacher 的加载、batch2/cap32 生成和 sleep/wake 已通过，全参数哈希及恢复 token 一致、退出码 0；见[运行回执](../../../../../../runs/token-fusion-tuning-20261031/context-status.json)及同目录 `context-gpu-check/complete.json`；这项检查不含 actor 训练/refit。

后续先将上述候选接入真实 current 更新，核验训练→生成→scoring→update 的完整驻留和墙钟，再决定默认配置。独立生成测量没有验收这些候选的 actor refit、保存恢复和所有融合公式；长负载 probability、chunked prefill、preemption 及替换 attention 后端需各自补证据。
