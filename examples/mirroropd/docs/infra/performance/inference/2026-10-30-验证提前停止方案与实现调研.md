# 验证提前停止方案与实现调研

本文比较传统规则、语义 verifier、隐藏状态分类头及公开实现，并给出在线检测的容量预算和待实现方案。除[使用说明](2026-10-30-验证重复检测与提前停止.md)中已经接入的 vLLM 精确检测外，本文方案均未在本项目启动服务或完成 GPU 性能验证。样本、误停和 AUC 证据见[参数回放报告](2026-10-30-重复停止参数回放与误停分析.md)。

## 原生检测与上游框架

vLLM PR #35451 已合并，检测在引擎内部执行，非流式调用也支持，原生默认关闭。作者在 Qwen3-VL 多模态场景报告约 33% 吞吐改善；该结果不代表数学评测的预期收益。[^vllm-pr] 本机安装的 `0.25.1+cu129` 已包含 `RepetitionDetectionParams` 和 `check_sequence_repetition`，无需升级。

NVIDIA Model Optimizer 的评测说明也使用同一请求字段，并要求基线与候选使用相同设置。[^modelopt] 检查的 NeMo RL 标准 vLLM worker 尚未在 `_build_sampling_params` 中透传该字段；本项目直接接入底层 vLLM。[^nemo]

## 更智能的停止方案

下面是调研与拟议设计，尚未接入运行。当前运行配置统一见[使用说明](2026-10-30-验证重复检测与提前停止.md)。

| 方法                     | 已核对的机制                                                                                                                                 | 对本项目的适配判断                                                                                                        |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 增量文本检测             | Qwen Code 用字符块哈希、实际内容复核、周期距离验证和有限历史，区分短片段聚集与长段落重复[^qwen-loop]                                         | 实现成本低，可借鉴按段落与编号归一化；它的 thought 检测仍是字符串规则，不能称为语义理解                                   |
| 小 verifier              | TrimR 将思考按反思边界分段，用 7B 指令模型判断是否出现答案、相邻答案是否一致；短输入与异步批处理降低成本，另有 rolling-hash 重复检测[^trimr] | 可借鉴异步系统，但 7B 对我们的 1.7B 学生并不小；原论文主要面向有 think 阶段的大模型，注入结束思考或总结提示会改变生成协议 |
| 隐藏状态线性头＋持续告警 | Circular Reasoning 对句子平均的最后层 hidden state 做线性分类，再用 CUSUM 累积与连续超阈值条件预测 statement loop[^circular]                 | 与“是否进入循环”最接近；不需要另跑完整语言模型，但要在 vLLM 内提取特征并用我们的模型状态校准                              |
| 隐藏状态 MLP 判断可答性  | LYNX 在反思 cue 处读取若干层特征，训练小 MLP 预测强制退出后是否答对，再校准阈值[^lynx]                                                       | 更接近“已经足够回答”；标签构造与内部特征接入较重，且持续训练中的 checkpoint 漂移不能直接继承冻结模型的校准结论            |
| 自身试答置信度           | DEER 在转折点额外生成试答，用答案概率决定是否结束思考，并研究分支并行[^deer]                                                                 | 省去外部 verifier，但多了试答请求、KV 与调度成本；不只是检测并取消原请求                                                  |
| 低成本序贯统计           | Statistical Early Stopping 将不确定性词语的到达间隔建模并作序贯判断[^stat-stop]                                                              | 可作为候选筛选信号；`Wait` 密集不能单独证明循环，数学正常复查也会触发                                                     |
| 训练模型自行停止         | ESTAR 用轨迹分类器、自生成 stop 信号的 SFT 和相应 RL 学习停止[^estar]                                                                        | 属于新的训练目标，需要单独实验；不是当前 valid 加速的小改动                                                               |

对于答案反复一致的方案，已有针对性负结果：Stable Answers, Unfinished Reasoning 在其实验中发现一致答案可能只是未完成推导中的暂定答案，后续仍会修正；增加一致次数也未完全消除问题。[^consensus] 因此，“连续给出相同答案”和“继续生成不会带来收益”必须分开验证。

隐藏状态头的算术开销可以很小，但接入成本并不为零：要避免为了取内部状态关闭 CUDA Graph，或导出完整 attention／每层全历史激活。优先考虑最后层的在线汇总与批量分类；不要为每个 token 增加独立 CPU/GPU 同步。具体 head、阈值和跨 checkpoint 泛化均未在本项目测量。另一个候选是只读短文本的几十 M 至几百 M 参数判别模型；这个规模是工程候选，不是已经验证有效的现成 stopper。

论文提出在线算法、仓库提供离线回放、代码实际接入在线主循环，是三种不同的交付状态。以下核对了 README 和对应执行源码；没有在本机安装或运行这些第三方模型。

| 项目                       | 公开交付物与源码核对                                                                                                                                                | 可复用范围                                                                              |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| PUMA                       | 公开 0.6B 冗余检测权重、训练数据和完整离线流水线；README 明确在线版本仍在准备[^puma-code][^puma-model]                                                              | 最适合作为已有语义 detector 做离线校准；在线请求观察、调度和取消仍需适配                |
| Gemini CLI                 | `LoopDetectionService` 包含周期性模型判断与二次确认，`client.ts` 在实际 turn 和流式事件中调用检测；首次告警尝试反馈恢复，重复告警退出[^gemini-loop][^gemini-client] | 已集成的语义循环监控实例；针对多轮 agent，不是单次数学 decode，可借鉴分层检查和误报控制 |
| DEER                       | 有 `vllm-deer.py`、`vllm-deer-qwen3.py`，按 active questions 的阶段循环调用 `LLM.generate`；README 的分支并行加速仍标为 coming soon[^deer-code]                     | 有可执行的 vLLM 试答／退出研究实现，但不是对现有服务加一个停止开关                      |

| Qwen Code                  | 长周期内容检测直接位于流式循环检测服务中[^qwen-loop]                                                                                                                | 可借鉴增量检测、有限历史与实际内容复核，仍是规则方法                                    |
| TrimR / Circular Reasoning | 已核对论文中的系统或算法描述；本轮未定位到可确认属于作者、可直接复用的在线实现                                                                                      | 保留为机制参考，不能据论文描述承诺工程接入已完成                                        |

PUMA 的检测器为专门微调的 `Qwen3-Embedding-0.6B`，Hub 元数据显示约 595.8M 参数，目标是区分推理步骤是否新增进展；不是直接拿通用 embedding 相似度当停止信号。它把步骤编码后，与近期步骤比较，仓库配置的常用阈值是 0.35、回看窗口 k=1，然后用试答一致性与置信度进一步确认。代码另有 late-stage Loop Breaker。默认阈值只属于其训练后的表示空间，不能直接移植给其他 embedding 模型或当成我们样本上的已验证参数。[^puma-code][^puma-model]

源码有一个在线迁移必须处理的细节：`embed_and_filter_steps.py` 在观察到连续冗余后，将 `forced_stop_step` 指向第一段冗余之前。离线可以回溯裁剪，在线却已经付出了等待连续确认的生成成本。在线实现应保留实际检测位置、保留前缀位置和已经生成的 token 数，不能把事后裁掉的确认段都计为节省。

Gemini CLI 的模型检查在同一请求内至少经过 30 个模型回合后启用，间隔在 5–15 回合间调整，查看近期 20 条历史记录；判断阈值为 0.9，高置信时通常由配置的第二个模型复核，复核模型不可用时存在单模型决策分支。提示词明确要求同时出现重复模式与没有净进展，并豁免不同文件、不同参数、结果变化等正常工作。这里的单位是 agent 回合，不是 token。我们的本地模型方案可以借鉴这个控制流程，无需接入它的外部模型服务。[^gemini-loop]

因此，近期优先级可以从“自行训练一个 stopper”调整为：先使用 PUMA 已发布的 0.6B 检测器，对已有明确循环、正常数学复用、枚举和后来恢复的样本只评分，测误报和批量延迟；通过后再接入本地异步观察路径。只复用冗余检测器不等于复现完整 PUMA，也不能继承其整套方法的准确率与加速结论。

## 生成速度、检测频率与服务容量

用于估算的实测来自 E56/E57 的 outer10 验证快照，并非当前机器实时 GPU 监控。E56 八卡约 5,641 output token/s，E57 约 5,431；平均到单卡为 705、679 token/s。一次完整验证耗时分别为 5.46 h、6.12 h。来源与计时边界见[长程耗时诊断](../full-vocab/2026-10-30-MDPO长程训练与验证耗时诊断.md)。这些是包含整个生成流水线的平均 goodput，不是单条序列速度，也不包含每个阶段的峰值。

以八卡合计 $T=5,500$ output token/s 作为容量规划的近似，若每条序列每新增 $k$ token 检查一次，总检查到达率约为 $\lambda=T/k$：

| 每条序列的检查间隔 k | 八卡检查请求约每秒 | 若每次检查输入 512 token，额外输入处理量约每秒 |
| -------------------- | -----------------: | ---------------------------------------------: |
| 64 token             |               85.9 |                                    44.0k token |
| 128 token            |               43.0 |                                    22.0k token |
| 256 token            |               21.5 |                                    11.0k token |
| 512 token            |               10.7 |                                     5.5k token |

这是所有序列都检查的近似；首段、句子边界、输出长度与候选筛选会改变实际请求数。若廉价筛选只把 10% 窗口交给语义模型，256-token 间隔对应约 2.15 次语义检查/s。稳定服务要求处理能力大于到达率；建议以利用率不超过 50% 留出突发余量，即全量方案至少约 43 次/s，10% 筛选示例至少约 4.3 次/s。两者都是待验收目标，不是现有模型测速结果。容量估算输入保存在[数据文件](data/semantic-stop-study-20261030/capacity.json)。

吞吐与延迟要分别验收。设单条请求实际生成速率为 $r$，检查排队加推理延迟为 $\tau$，那么在检测规则所需证据已经出现后，周期采样通常还会多生成约 $k/2+r\tau$ token，最坏采样等待约 $k+r\tau$；若还要求第二个连续窗口确认，再加一个间隔。该估算不包括形成重复或无进展证据本身所需的长度。建议语义检测以 p95 延迟 ≤0.5 s 为初始目标，在 $r=20$ token/s 的示例下，延迟只多产生约 10 token，而 k=256 的采样间隔更重要。20 token/s 是示例，不是实测单请求 TPOT。

不能直接把每卡 700 token/s 当成单请求速度。如果平均活跃序列数为 B，粗略平均是 $700/B$：B=16/32/64 时分别约 44/22/11 token/s。当前 `max_num_seqs=64` 是上限，缺少实际活跃数与逐请求 TPOT，因此只能把这三个值当作场景估算。需要补采样的指标是活跃／等待请求、每请求 token 时间戳、检测队列长度、批量大小、p50/p95 检测延迟与 stale-result 数。

原生检测器的 87 微秒微测量也可以换成 CPU 预算：若单卡每秒输出 700 token、每 token 检查一次，约消耗 0.061 CPU 核秒/秒；512 周期对应约 0.127。它们不是 6.1% 或 12.7% 的已测墙钟减速，因为主机开销可能与 GPU 重叠，瞬时吞吐也不同。对于新增的轻量文本筛选，若每 64 token 检查一次并希望平均开销低于一个引擎单核预算的 1%，目标约为每次不超过 0.9 ms；每 128 token 则约 1.8 ms。

## 建议实现顺序与必要验收

以下仅作为离线或只记录告警的研究方向。可以每 64–128 token 做廉价候选筛选：长块哈希、局部新 n-gram 比例、相邻段落重复、重复失败结论。可以去掉 Markdown `Step N` 标题中的编号，但保留数学式中的数字、符号和候选身份；把所有数字替换成同一个占位符会误伤正常枚举。

语义复核初始可按每 256–512 个新 token 或完整段落触发，只对候选发送问题与最近若干段落。输出 `loop/continue/uncertain` 和简短的重复依据，避免再生成长解释；两次告警一致仍不构成安全停止保证；在误停风险尚未校准时只记录告警，不据此中止。先以只记录不停止的方式校准，再离线回放误截与可能节省量，最后做真实吞吐对照。隐藏状态小头属于更深一层优化，适合有足够跨 checkpoint 标签后接入。

按本地代码，最小文本观察点在 vLLM server 的 `async for output in generator` 内，而不是等 agent loop 收到完整回答。每个请求最多保留一个待判窗口，队列满时合并为最新窗口；检查通过异步 worker 执行，不能阻塞整个 decode batch。结果必须绑定 request ID、模型版本、窗口结束位置；请求已经结束或出现新进展后，不得把陈旧告警直接用于停止。

取消还要区分“重复停止”和基础设施中断：当前 `FullyAsyncLLMServerClient` 会对 `abort/aborted` 自动重试，直接调用通用 abort 可能把刚停止的循环重新启动。实现时需要保留已生成前缀、显式记录语义停止原因、阻止自动续跑，并只释放目标请求的活跃资源；不能顺带清空全引擎 prefix cache。语义停止计数与自然 EOS、精确重复、长度上限分别记录。

验收同时看误截正常证明、误截后来恢复答对的回答、循环开始到告警的 token 延迟、保留前缀的判分、总输出 token、检测输入量、KV 占用及整个 valid 墙钟耗时。训练与评测标注划分以题目 ID 为单位，另留 checkpoint 阶段作迁移检查；推理时不读取标准答案。我们的目标是用小开销减少明确无进展的输出，而非通过额外模型修改答案来提高验证分数。

完整工具检索报告原样保存在[paper-search 报告](data/semantic-stop-study-20261030/paper-search.md)，该轮 arXiv 返回 6 条、0 条诊断；它是检索记录，不等于六篇都已深入审读。正文比较另外核对了 TrimR、DEER、LYNX、Circular Reasoning 及相关仓库源码。当前没有启动新的模型服务或训练 stopper；运行配置统一见[使用说明](2026-10-30-验证重复检测与提前停止.md)。
