## 1. 实施决策

| 项目           | 决策                                                                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 两种融合       | 同一全局 batch 内分配完整轨迹；每次 decode 对共同前缀的 logits 加权                                                    |
| Student 身份   | current / initial，与融合模式正交                                                                                      |
| 第一条生产路径 | Trajectory mixture 复用现有 vLLM 整请求生成，按来源串行执行                                                            |
| Token 数值基准 | 新增本地 HF 双模型解码器，固定微批、双 KV、一个采样器                                                                  |
| Token 优化     | 双模型生产性能为必交付；完成分阶段 profiling、批处理/KV/通信优化和端到端对比，不能停在 HF 数值原型；具体技术由测量选择 |
| 训练目标       | 第一组对照保留 Full-KL、anchor、optimizer 与 reuse；不移植 GSPO/DAPO 的 ratio clipping 配方                            |
| 失败边界       | 新融合模式首版禁用动态过滤/refill；任一响应失败则整批失败，排空后清理，不用其他来源补齐                                |
| 默认路径       | Current single 继续使用现有后端，不强制经过 HF 解码或新的逐 token 循环                                                 |

Global batch 的来源分配只能由一个 plan 决定。Runtime 负责执行这个 plan，AgentLoop 负责单条轨迹的 token 构造和判分。不要把跨来源的资源切换分散到各个 agent 自己判断。

## 3. 本批计划与阶段协议

### 3.1 最小数据结构

`BatchRolloutPlan` 是一份不可变的本批描述，不是通用执行图。只需包含：

| 字段                                                 | 内容                                                                                                           |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `collection_step`                                    | 采样 outer step                                                                                                |
| `actor_version`                                      | 本批 current 绑定的 outer 与已应用 optimizer 更新坐标，不能混用 attempt 计数                                   |
| `student_binding / teacher_binding`                  | current actor 或原始本地 checkpoint                                                                            |
| `coefficient_rule / resolved_control / weight_clock` | 系数规则、本批已解析的控制量与时钟；固定/衰减规则解析为 α，未来 TRB 解析为预算 ε，逐前缀 α 留在 decoder 内求解 |
| `requests`                                           | 稳定样本身份、TQ uid、response_index、seed、来源或融合配置                                                     |
| `phases`                                             | 一或两个顺序生成阶段：decoder 与所属请求集合                                                                   |
| `expected_sessions`                                  | 每个 prompt 的预期 response_index 集合                                                                         |
| `sampling / termination`                             | cap、温度、过滤、有效词表与停止规则                                                                            |

Single 是一个 phase；trajectory mixture 是两个来源 phase，空来源自动跳过；token mixture 是一个使用双模型 decoder 的 phase。Policy 解析生成计划，collector 执行顺序阶段，不要求 trajectory mixture 自己实现 token 解码。首版只实现常数和线性规则；trajectory mixture 的规则输出轨迹比例，拒绝逐前缀控制。为 TRB 留出上述数据表达即可，不为尚未实现的规则增加空插件或对外可选项。

保留现有 UUID 作为 TQ key 的一部分，另用稳定的数据行 ID、epoch/occurrence、采样轮次和 response_index 推导路由与 seed。随机 UUID 不参与决定训练样本的来源。

### 3.2 Trajectory Mixture 的明确执行顺序

1. 从现有 dataloader 取原始 $B$ 个 prompt，建立全部 $Bn$ 个响应请求；padding 不参与配额。
2. 固定 α 和 actor 版本，生成一次全局随机排列，按配额分配完整轨迹。
3. 只登记一次 train partition 的 parent prompt marker。一个 collector 是这些 parent 状态的唯一写入者。
4. 准备 student 来源，提交分给它的响应，等待所有任务及 TQ 发布完成；排空并休眠。
5. 准备 teacher 来源，执行相同过程。
6. 验证返回的 session 身份恰好覆盖预期集合，无缺失、重复或来源改变；发布 parent finished。
7. 原 ReplayBuffer 取出同一个完整 batch，做原有 balance、teacher 评分、actor 更新和日志。
8. 清理当前批 TQ 数据与临时完成表。

推荐给 `AgentLoopWorkerTQ` 增加一个阻塞的 `generate_sessions(requests)` 接口，内部复用 `_run_agent_loop / _agent_loop_postprocess`。它只运行指定 response_index 并报告成功/失败，不写 parent finished。Collector 在各来源 phase 全部返回后统一发布 group 状态。现有 single 的 `generate_sequences` 路径保留。

这样同一 prompt 的不同响应可以落到不同来源或 worker；不必为此新增持久化队列或分布式完成状态服务。单节点 sync 的 collector 只保存本批 $O(Bn)$ 的小元数据。启动验收使用不同模型结构，防止来源虽然标为 teacher，实际仍调用 student。

### 3.3 异常与计时

任何异常先等待已经派发的 sibling 任务结束或明确取消，确保不会再写 TQ，然后将本批标为失败并清理。禁止一边训练成功子集、一边让另一个来源继续写同一批 key。所有阻塞生成/同步调用都设置有限 deadline。取消或排空超时后停止当前 run 并交由进程级清理恢复，不能继续下一 GPU 阶段。首版不做中途生成恢复；从已有 outer checkpoint 恢复后按计划重新生成。

关闭新融合模式的 DAPO group filtering 与 failed-group refill，直到定义好按原来源补齐的规则。这个支持限制只作用于新模式，不改变原 single 模式的失败行为。

两个来源共享一个总 submission ID 和 `expected_requests=Bn`。总生成墙钟从 plan 开始执行到最后响应结束，包含两阶段等待与切换；保留分来源计时作为附加指标。现有 `_step_once` 内的等待时间不包含此前阻塞在 prepare_step 的工作，不能拿它代替总生成耗时。

## 4. α 的时钟、配额与衰减

常数 α 是第一组算法对照。可选全局线性衰减作为后续对照，不与来源功能同时默认开启：

```yaml
rollout_policy:
  mode: token_mixture
  student: current
  teacher_weight:
    kind: linear
    start: 0.5
    end: 0.0
    steps: 1600
    clock: optimizer_step
```

以上是拟议配置，`1600` 仅示例。`optimizer_step` 指已成功应用的 actor 更新次数，取现有 [OptimizerProgress](../../../../../../verl/trainer/ppo/v1/progress.py)，不使用 attempts。每个 outer 开始采样时只计算一次 α，整个 batch、所有来源 phase 和内部 reuse 都使用记录下来的值。若旧 checkpoint 的绝对 optimizer 次数未知，拒绝依赖该时钟的 schedule，而不是猜测。若希望训练后段真的出现 α=0 的采样批，衰减结束点必须早于训练结束；把结束点设为总更新预算只会在最后一次更新后达到 0。

对公共的 batch=mini-batch、reuse16，100 outer 对应约 1,600 次成功更新，但 skipped updates 会改变实际对应关系。原 logit-fusion 的 `Trainer.state.global_step` 也不能未经核对就改写为本项目的 outer step。[^lf-code]

Trajectory 配额使用 $N_T=\lfloor\alpha N+0.5\rfloor$，记录 $\alpha_{\rm effective}=N_T/N$。衰减末期，即使 $\alpha>0$，整数化也可能得到 $N_T=0$；该批跳过 teacher phase，不能报错中止 schedule，也不能强制最少一条 teacher 而悄悄改变比例。Token fusion 则只有 α 精确为 0 时才能省略 teacher；它没有轨迹配额的整数化。

按难度缩放不放入首版默认。原仓库把难度映射为 `(d-1)/9`，开关默认关闭；当前 DAPO 不能假定存在相同的有效难度标签。若以后加入，必须声明标签来源、范围及缺失处理，并作为单独实验因素。[^lf-config]

当 `student=initial` 时，α 衰减到 0 后得到的是初始 student 的采样策略，仍不是当前 learner 的 on-policy rollout。

## 5. Token Fusion 的本地参考后端

### 5.1 后端边界

新增 `hf_fusion` decoder/replica 和其 ServerAdapter，接入既有 Manager/Client 与 TQ 输出。它持有两个只做推理的 HF 模型，以及自己的 KV 会话；不直接对训练中的 FSDP 模型逐 token 调用 `generate`，也不复制 optimizer。

新增后端需要同时接入 `get_rollout_class` 与 replica 工厂，并由 policy 选择它；不要把整个 `actor_rollout_ref.rollout.name` 改为 HF，导致默认 student 验证也被替换。Current student 通过显式权重同步更新推理副本；initial student 与 teacher 从本地 checkpoint 加载后冻结。验证继续使用当前 learner 的现有 student 引擎。每个服务、socket 和接收目标都带独立身份，避免默认 student 和 fusion student 使用同一命名地址。

首个参考后端限定为 TP1、单 GPU 上两模型能放下、固定微批的同步解码；可以用多个独立 replica 做 DP。超过这个边界明确报错。TP、异构 GPU 子组和连续批处理是后续验收项，不能从可加载 checkpoint 推断支持全部模型规模。

### 5.2 Prefill、Decode 与结果

| 阶段     | 必须保持的条件                                                                                            |
| -------- | --------------------------------------------------------------------------------------------------------- |
| Prefill  | 两边消费相同有效 prompt token；各自构造 KV；只有最后一个有效预测位置参与第一次采样                        |
| Decode   | 每次使用两边对同一真实前缀的 logits；融合、处理和采样只发生一次                                           |
| KV 推进  | 选出的 token 提交两边；即使它不是任一模型单独最可能的 token，也不能换成另一 token                         |
| Padding  | 使用显式 attention mask 和真实长度；不能用 `input_ids != pad_id` 推断全部语义，尤其 pad 与 EOS 共用 ID 时 |
| Position | 通过模型支持的 cache/position 接口维护，区分 padding 后存储位置与真实 token position                      |
| EOS      | 第一枚合法 EOS 包含在有效响应内，之后 mask 为 0；到 cap 时记 length，不人工补 EOS                         |
| 微批结束 | 等待全部活跃请求结束，释放两份 KV；当前 student 权重可以缓存到下一次 refit                                |
| 返回     | 保留原 prompt_id/session_id；发布 response_ids、mask、finish_reason、版本和实际采样信息                   |

本机 Transformers 的 Qwen3/Qwen3-MoE forward 支持 `logits_to_keep`，普通 prefill/decode 可以只返回所需的末位置 logits，避免物化 prompt×vocab 输出。使用 block verification 时必须返回该块所需的多个预测位置，不能继续固定为 1。具体输入和模型能力要在启动时核实。

返回值交给现有 `SingleTurnAgentLoop` 的 `ct_merge_assistant_token` 与元数据对齐逻辑，不能把生成文本重新 tokenize，也不能把模板插入 token 当作真实采样 token。显式测试第一步 EOS、cap=1、pad==EOS 与 response/log-prob 长度一致。

第一版使用静态微批。已结束行即使继续参与底层张量计算，其后续 token 不能进入响应或 loss。以后压紧活跃 batch 时，两侧 KV、request_id、位置、随机状态与完成掩码必须使用同一重排表。

### 5.3 公共采样器与 Behavior 概率

固定操作顺序：校验共同合法词表 → 计算 FP32 加权 logits → 公共温度 → 公共过滤/约束 → 归一化并采样。不能拿各模型已经 top-p 过滤的结果冒充 raw logits。

Teacher/student backbone 可以 BF16，融合、logsumexp 与选中 token 的 log-prob 使用 FP32。不要先求很小的概率再取 log。每个请求使用由其稳定身份推导的随机流，不能因来源 phase、micro-batch 切分或另一次验证而改变路由决定。

只保存实际选中 token 的最终 behavior log-prob，不保留 `[batch, length, vocab]` 的全部 scores。Full-KL 不消费这个分母时允许省略传输；数值验收仍需抽样对照最终分布。

原仓库在生成后重算融合 log-prob，代码重放了融合和温度，但没有在这个函数中重放 top-p/top-k/repetition penalty。默认无截断时与配置相容；改变采样处理后不能据此认为分母仍然精确。本项目优先在实际采样点记录最终分母。[^lf-code]

### 5.4 Current Student 的权重接收路径

当前 naive 同步绑定在 actor 的 `self.rollout`。建议在不改变默认行为的前提下增加命名接收目标：

| 接收目标          | 用途                              | 是否接收 actor 更新 |
| ----------------- | --------------------------------- | ------------------- |
| `student`         | 现有 current rollout / validation | 是                  |
| `fusion_student`  | Token fusion 的 current 分量      | 是                  |
| initial / teacher | 冻结推理分量                      | 否                  |

非默认融合模式的 `on_step_end` 只将 current 接收目标标为过期，不无条件唤醒默认 student vLLM；进入 current 生成 phase 或验证时再按版本与驻留状态同步。`on_init_end` 也不能自动激活未使用的生成器。默认 single 先保留已有行为，改为统一生命周期后仍需默认兼容测试。

同 GPU 映射的首版可在 `ActorRolloutRefWorker.update_weights` 中选择目标 adapter，复用 `get_per_tensor_param` 的流式导出；不要复制第二套 gather 逻辑，也不要每个 outer 保存完整 HF checkpoint 再从磁盘加载。各目标分别保存 loaded_version、权重是否有效和 KV 是否有效。

接收侧先停止生成和清 KV，再逐 tensor 拷贝，并检查期望的参数名、shape、dtype 与 tied 参数关系。全部 tensor 完成并经相关 rank barrier 后才发布新版本、允许生成。任何接收失败都让该目标保持不可用，不能继续使用半更新的模型。

模型导出涉及 collectives，所有相关训练 rank 必须一致进入与遍历；只让某个 rank 单独导出会挂起。HF 接收目标的 resume/release 由自身 adapter 实现，不套用 vLLM 专用的内存标签判断。Teacher 固定参数与 KV 不属于 student refit 的覆盖范围。

若生成与 actor 的拓扑不同，使用已有非 naive checkpoint-engine 发送/接收机制，并新增 fusion adapter 的接收端验收。现有训练入口强制 naive 的位置也必须改成显式策略选择；不能只替换接收 replica 列表。[^local-sync]

## 6. Base / Instruct 的停止概率问题

EOS 集合与终止动作 KL 合并解决的是不同问题。把 `[e_S,e_T]` 都加入 stop IDs，只定义“采样到哪个 token 后停止”；它不会改变融合前各模型对两个 ID 的分配。

下面是自构造的数值反例，三个动作分别为 $e_S,e_T,\mathrm{continue}$：

$$
p_S=(0.9,0.001,0.099),\qquad
p_T=(0.001,0.9,0.099).
$$

两个模型各自的总停止概率都是 $0.901$。但 α=0.5 的原始 token logit fusion 得到

$$
p_{\rm fusion}(\mathrm{stop})
=
\frac{2\sqrt{0.9\times0.001}}
{2\sqrt{0.9\times0.001}+0.099}
\approx 0.3774.
$$

因此，即便两边都愿意结束，偏好的 EOS ID 不同也可能让融合轨迹变长。这个结论来自上述代数反例，不是已经在真实 Qwen3 上测得的数值。

基础实现保持用户指定的 raw-token logit fusion，不暗中合并生成事件。验收必须同时记录 $p_S(e_S)$、$p_S(e_T)$、$p_T(e_S)$、$p_T(e_T)$ 与融合总停止质量。先用相同 EOS 的配对跑通，再对 Base/Instruct 配对做停止率与长度检查；不通过时暂停该配对的长程实验。

可以另设研究对照：先把两个 EOS 的质量合成一个 STOP 事件，再融合。它改变了生成策略与选中 token 概率的含义，不能作为无标记的实现修复。若采样为 STOP 后输出 learner 的规范 EOS，sampled loss 也必须计算事件概率而不是只查该单一 token 的概率。

现有 [termination_equivalent_kl_rows](../../../../../../verl/trainer/distillation/full_vocab.py) 只处理 loss 侧的 coarsened action space；它不会自动修改生成分布。已实现的 Full-RKL EOS 修复不能代替这一生成侧验收。

TRB 附录 D 为生成侧对齐提供了直接先例：对每个模型 $M$ 定义映射 $\phi_M$，把其原生 EOS 映到共同事件 $e_\star$，其余 token 保持原义，然后计算推前分布：[^trb]

$$
\widetilde p_M(v\mid h)=\sum_{u:\phi_M(u)=v}p_M(u\mid h).
$$

论文在这个对齐空间里完成行为分布构造、采样及稀疏支持 KL；抽中 $e_\star$ 时输出 student EOS。其说明为每侧一个原生 EOS，移动该坐标质量并屏蔽重复坐标。这个按模型定义的映射，与“在两侧都把两个原始 EOS ID 无条件合并”的规则不应混称为同一个实现。

本项目仍将 raw-token fusion 保留为独立基线；复现 TRB 的 EOS 处理时需要单独声明规范事件映射。具体需核验非原生 EOS 坐标残余概率如何处理、共同支持怎样归一化，以及发出 student EOS 后的 loss 事件概率。论文附录未穷举任意 special-token 映射的所有边界，不能据此跳过本项目词表检查。验收同时比较 stop-set union、明确映射的事件融合和 raw-token fusion，记录实际停止概率，而不只检查是否正常终止。

## 7. 显存预算与成本估算

### 7.1 使用真实模型配置，不按 Active 参数估权重

以下值于 2026-10-28 从仓库同级 `model/` 的配置和 safetensors 文件读取。权重文件体积只作为权重存储量近似；KV 按 BF16、TP1、无共享的静态满长缓存计算。这是容量估算，不是实际峰值显存或吞吐测量。

$$
M_{\mathrm{KV},i}
=
2L_iH_{\mathrm{KV},i}D_i\,b\,m\,\ell,
$$

其中 $L_i$ 为层数，$H_{\mathrm{KV},i}$ 为 KV heads，$D_i$ 为 head dimension，$b=2$ 字节，$m$ 为该 replica 的活跃序列数，$\ell$ 为总 context 长度。两模型融合要加上两份 KV。

| 模型                        | 层 / KV heads / head dim | 权重文件 GiB | KV 每 token | $m=8,\ell=8192$ 的 KV |
| --------------------------- | ------------------------ | -----------: | ----------: | --------------------: |
| Qwen3-1.7B-Base             | 28 / 8 / 128             |         3.21 |     112 KiB |                 7 GiB |
| Qwen3-8B                    | 36 / 8 / 128             |        15.26 |     144 KiB |                 9 GiB |
| Qwen3-30B-A3B-Instruct-2507 | 48 / 4 / 128             |        56.87 |      96 KiB |                 6 GiB |

1.7B-Base + 30B-A3B 在上述 $m=8$ 条件下，仅权重文件体积加理论 KV 就约 73.08 GiB；$m=2$ 时约 63.33 GiB。两者都未包含 prefill 激活、kernel workspace、分配器、CUDA context、同步临时张量和休眠中的其他实例残留。不能据此宣称 80GB GPU 上某个并发必定可用。

$\ell=8192$ 对应示例中的 1024 prompt + 7168 response；使用 4096 prompt 时要按新的总长度重算。上述 $m$ 是 fusion decoder 微批，不是全局 batch64，也不是之前单 student vLLM 的 max_num_seqs=64。

TP 分片后的权重、KV 和临时空间依赖具体后端布局，不能将总值直接除以 TP 后当作验收结果。先使用 TP1 reference 做真实短测，再决定是否需要分片或拓扑调整。

### 7.2 优化顺序

| 顺序 | 优化                                                   | 正确性约束                                      |
| ---- | ------------------------------------------------------ | ----------------------------------------------- |
| 1    | 保留双 KV；prefill 只做一次；减少无用 head 输出        | 同一真实前缀、位置和 attention mask             |
| 2    | 每次生成前同步 current 一次；冻结模型持久保留 CPU 备份 | 不按 token 同步或反复读 checkpoint              |
| 3    | 按 prompt 长度组成静态微批，测不同 $m$                 | 请求身份和采样 seed 不依赖排序                  |
| 4    | 只保存选中 token 的概率；FP32 融合和归一化             | 不改变合法支持与过滤顺序                        |
| 5    | 活跃行压紧、双模型并行 forward 或图捕获                | 两侧 KV 同步重排；并发不保证比顺序更快          |
| 6    | 专用融合 sampler / 批量解码后端                        | 与 reference 的最终概率和 mask 对照             |
| 7    | 精确 speculative fusion                                | 目标仍是融合分布，按下节验证接受/拒绝与 KV 回滚 |

两个模型若在同一 GPU 上运行，两个 CUDA stream 可能只是在竞争内存带宽，不能默认认为会加速。跨 GPU 融合也需要同步同一 token 位置和词表布局；不要通过 trainer 每个 token 搬两个完整 vocab 向量。

临时用现有整请求接口反复生成单 token，只适合极小规模调试：它会增加逐 token 调度、重复前缀处理和数据传输，并不提供我们需要的双 KV 调度器。优化指标必须包含这些成本。

### 7.3 Speculative Fusion 是后续优化，不是改变采样策略

普通 speculative decoding 以 proposal $q$ 提议 token，并用目标分布校验。这里把目标替换为已完成融合、温度和过滤的 $\beta$，接受概率为

$$
a(v)=\min\left(1,\frac{\beta(v)}{q(v)}\right).
$$

拒绝后从归一化的 $[\beta-q]_+$ 采样。单位置的输出概率为

$$
q(v)a(v)+[\beta(v)-q(v)]_+
=
\min(q(v),\beta(v))+[\beta(v)-q(v)]_+
=\beta(v),
$$

其中第二项已计入拒绝事件的总概率。这个等式要求使用同一前缀上的、正确归一化的实际 proposal 与目标概率。[^spec-decoding]

实现时可由小模型提出 $k$ 个 token，再并行计算这些前缀上的两模型 logits，构造融合目标进行验证。目标不是纯 teacher；不能直接打开普通 teacher-target speculative decoding 就声称完成 fusion。需要处理拒绝后的双 KV 回滚、EOS、cap、全接受后的额外 token，以及实际输出 token 的 $\log\beta$，不能记录 proposal 概率或接受概率来代替。

Model Arithmetic 已给出将 speculative sampling 用于组合分布的机制和受控生成实验，说明这是可研究的优化方向。它的速度结果不属于当前 Qwen3、Full-KL、长 rollout 设置；只有接受率足够且实测墙钟收益覆盖额外验证开销时才启用。[^model-arithmetic-paper]

### 7.4 TRB 系数求解与实际采样分布

TRB 的优化问题和实验结果见[主设计第 10.4 节](2026-10-28-可组合Rollout策略架构与实现方案.md#104-trb用-kl-预算决定-logit-fusion-强度)。下面是面向本项目的拟议实现与验收要求；数学依据为论文第 4 节和附录 E。[^trb]

在共同合法事件空间上，令 $p,q$ 为严格正的 student、teacher 分布，$r(v)=\log q(v)-\log p(v)$。拉格朗日乘子 $\eta\geq0$ 对应 $D_{\mathrm{KL}}(\mu\Vert p)\leq\varepsilon$，$\lambda$ 对应归一化：

$$
\mathcal L=\sum_v\mu(v)\log\frac{\mu(v)}{q(v)}
+\eta\left(\sum_v\mu(v)\log\frac{\mu(v)}{p(v)}-\varepsilon\right)
+\lambda\left(\sum_v\mu(v)-1\right).
$$

对 $\mu(v)$ 求导并令其为零，得到 $(1+\eta)\log\mu(v)=\log q(v)+\eta\log p(v)+c$。归一化后即几何融合，teacher 系数为 $\alpha=1/(1+\eta)$。定义对数归一化常数：

$$
A(\alpha)=\log\sum_v p(v)e^{\alpha r(v)},
\qquad
\mu_\alpha(v)=p(v)e^{\alpha r(v)-A(\alpha)}.
$$

对有限共同支持，直接求导有 $A'(\alpha)=\mathbb E_{\mu_\alpha}[r]$、$A''(\alpha)=\operatorname{Var}_{\mu_\alpha}(r)$。代入约束：

$$
C(\alpha)=D_{\mathrm{KL}}(\mu_\alpha\Vert p)
=\alpha A'(\alpha)-A(\alpha),
\qquad
C'(\alpha)=\alpha A''(\alpha)
=\alpha\operatorname{Var}_{\mu_\alpha}(r)\geq0.
$$

因此可以二分求最大的可行系数。实现顺序如下：

1. 在共同支持上以 FP32 log-space 归一化；拒绝 NaN、空支持与未声明的事件映射。不要用未归一化 logits 直接计算 KL。
2. $\varepsilon=0$ 直接返回 student；若 $D_{\mathrm{KL}}(q\Vert p)\leq\varepsilon$，直接返回 teacher。
3. 其余情况在 $[0,1]$ 上二分，维护可行下界与不可行上界；在给定容差和最大迭代数后取可行下界，重新检查实际 KL，再从对应分布采样。
4. $p=q$、接近零的预算和端点需要独立测试。被屏蔽坐标不能参与 $0\times(-\infty)$；两侧不同硬支持的情况首版拒绝，不悄悄加 smoothing 改目标。

系数控制器消费同一步已有的两侧分布与预算，返回逐行系数及求解诊断；它不负责模型 forward 或 KV 更新。每次二分只有向量计算，无须再次调用 teacher。TP 分片词表需要正确的全局 log-sum-exp、期望与 KL 归约；每轮 collective 的真实开销必须计入，不能仅凭 FLOPs 小就判断墙钟成本可忽略。

首个 TRB 对照采用 `temperature=1, top_p=1, top_k=-1`，避免在求解后再次改变分布。若求解后做温度变换、top-p、repetition penalty 或其他过滤，实际 sampler 就不再是已验证预算的 $\mu$。未来允许这些变换时，必须重新定义约束所比较的 student 分布，并对最终采样分布检查约束；不能沿用原预算保证。

这里的预算是**每个前缀的条件 KL**。对至多 $T$ 个位置、EOS 后吸收的轨迹分布，KL 链式法则只给出轨迹 KL 不超过 $T\varepsilon$，并不保证整条轨迹 KL 不超过 $\varepsilon$。训练期的预算时钟固定为明示的 outer 或成功 optimizer updates；一个 rollout batch 内保持同一预算和模型版本，不能在逐 token 生成过程中读到变化的 learner。

新增诊断记录预算、系数分位数、实际条件 KL、超预算率、二分迭代数、取纯 teacher/student 端点的比例，以及 teacher 在线解码的时间。CPU gate 用 FP64 小词表 oracle 检查可行性、端点、单调性与选中事件 log-prob；GPU gate 增加 TP 归约、EOS 映射与预算归零后释放 teacher 生成资源的测试。TRB 的 current 版本先通过，再另测 initial 中心，后者不标为 on-policy warmup。

论文附录 C 提到复用在线 teacher 统计来计算后续稀疏 KL。我们的 Full-KL 不能只凭选中 token 或 top-16 概率完成同样复用。首版保留原 teacher scoring；未来只有在前缀位置、模型版本、head/hidden、精度和 EOS 空间都对齐后，才评估缓存复用。这样会比论文的复用方案多一次 teacher pass，应明确报告，不能声称 FLOPs 相同。

| 初始 student 基线  | single student     | initial      | 0            |
| Teacher state 基线 | single teacher     | 不适用       | 1            |
| 轨迹混合 A         | trajectory mixture | current      | 固定 0.5     |
| 轨迹混合 B         | trajectory mixture | initial      | 固定 0.5     |

| Token 融合 B       | token mixture      | initial      | 固定 0.5     |

这里不自动分配新的 E 编号，不启动实验。额外本地 checkpoint 的 single 用例先用于接口验收，需要研究问题时再加入学习矩阵。

第一组优先采用已有兼容基础且 EOS 一致的模型对。Base/Instruct 的终止质量检查、30B MoE 的容量和 refit 验收分别完成后再扩展。固定权重比较通过后，再单独测试 α 衰减；initial 分量的衰减结果标注为“最终回到 initial 来源”，不宣称最终 on-policy。

文章的 RL 结果不能直接作为本项目 Full-KL 的预期效果。若以后复现其 RL 配方，应单独注册 RL 对照，明确 reward、IS 粒度、ratio clipping、梯度 clipping、LoRA 和训练数据；不要把这些变化混进 state-source 对照。

TRB 扩展放在固定 fusion 验收之后：对 current student 比较固定 $\alpha$、衰减 $\alpha$、固定 $\varepsilon$ 与衰减 $\varepsilon$，分别回答固定强度、退出 guidance 和按前缀适配的作用。四组保持同一 EOS 事件空间与 learner loss，否则不能把改进归因于预算控制。另做 raw-token / EOS 对齐的独立消融。论文 top-16 配方复现与 initial 中心变体各自标明目标与采样设置，不与这组 Full-KL 预算实验合并报告。TRB 完整算法是后续独立阶段；SKD、AdaSwitch 不进入实施范围、配置、测试或实验矩阵。

### 9.2 预算与统计

主要横轴保留 outer 和成功 optimizer updates，同时报告实际训练响应数、有效 token 数与累计 GPU-hours。固定更新次数不代表固定计算量；融合与不同来源产生的长度变化也要报告。

至少使用多个独立训练 seed；资源只允许单 seed 时标为探索结果。验证继续使用五集、相同采样数和当前 learner，按数据集分别报告，评估波动按 prompt 分组而不是把同题重复回答当成独立题目。

性能分两种测量：

- 正确性/系统微测：相同 prompt、固定 cap、相同 α 和 source identity；报告 logits、log-prob、长度/停止和各阶段延迟。
- 自然生成训练：保留真实 EOS，不人为延长输出来提高 TPS；同时给自然总 token 数、完整批次时间及吞吐。

采样方式和优化器相同的比较中，训练 rollout 的 acc/length/repeat 仍然属于生成策略。只用 student-only validation 判断 learner 是否内化能力。

故障注入包含：第二来源 worker 失败、判分失败、一个 rank refit 失败、生成被取消、旧版本请求未排空、失败后的延迟 TQ 写入。每项都要求不发布成功训练 batch，并能由当前资源清理/恢复机制收尾。

## 11. 明确的实施与合并顺序

1. 配置、ModelBinding、plan、稳定请求身份和源码级测试；默认 single 行为保持不变。
2. 实现 trajectory collector 与阻塞 session RPC，完成 G0、G3 和真实 vLLM 短运行。
3. 实现 HF fusion decoder 与统一 sampler，在无训练模型的环境通过 G1、G2。
4. 接入命名 weight target 或显式 transport，完成 G4，再做 G5。
5. 进行真实模型 G6；Base/Instruct 的停止问题单独判断，不通过不进入长训。
6. 完成 G7：优化真实双模型解码、批处理、KV 与通信；必要时支持 TP 或独立 GPU 子组，并同时验收权重同步。每个优化独立变更、与参考实现对照。
7. 在通过 G7 的实现上完成短训练、验证和恢复验收，提供全部来源模式的可复现启动配置。长程学习矩阵单独执行，不作为基础设施已经正确的替代证据。
8. 精确 speculative fusion 仍是可选优化；若现有优化已满足性能验收，不为引入该机制而扩大工程范围。

每个阶段的报告区分“源码检查”“CPU 数值”“GPU 功能”“真实短训练”“完整学习曲线”。本轮完成的是调研、接口裁决、估算和验收设计；没有把未来测试写成已经通过。

## 12. 生产性能要求与完成标准

### 12.1 建立可对照的数值参考与真实基线

保留小而清楚的 HF reference，用于 logits、缓存、mask、采样概率与事件映射对照。它不承担所有生产调度能力。真实模型的 baseline 至少具备双 KV、单次 prefill、合理微批和所需位置的 logits，避免以故意低效的“每个 token 重算全部前缀”夸大优化收益。

另测同硬件上的纯 student、纯 teacher 和 trajectory mixture，帮助判断额外成本来自哪个模型、通信还是调度。单模型速度仅作成本参照，不要求双模型融合达到单模型相同 TPS。

### 12.2 分阶段 Profiling

必须测量权重同步/唤醒、student/teacher prefill、student/teacher decode、融合与采样、通信、KV 操作、休眠/卸载、teacher scoring、learner update 和验证切换。若阶段存在重叠，使用时间线解释，不能将重叠计时简单相加冒充总耗时。

记录每张卡的峰值显存、利用率时间序列、CPU RSS、KV 使用量及后端可观测的 preemption/recompute。后端不暴露某项时标为 unavailable，不能填 0。GPU util 高不是吞吐已优化的充分证据。

详细 profiler 单独采集短窗口，正式吞吐测量使用低开销计时；报告是否启用 profiler，不能直接比较不同插桩强度的数据。

### 12.3 按瓶颈落实优化

| 必须检查的方向  | 实施要求                                                                                                         |
| --------------- | ---------------------------------------------------------------------------------------------------------------- |
| 重复计算        | 两侧各 prefill 一次，持续复用 KV；只产生当前所需 logits；不在循环中重分词或重复读取 checkpoint                   |
| 无效 batch 工作 | 测长度分桶、多个微批；长短混合负载检查结束行浪费，必要时压紧或引入连续批处理；两侧 KV 使用同一请求重排           |
| 调度与数据传输  | 融合与采样留在推理执行侧；避免每 token 经 trainer/TQ、CPU 搬运完整词表；测量不可避免的跨 GPU 通信                |
| 模型布局        | 比较可行的共置/顺序 forward 与独立 GPU 子组；并发只有实测更快才保留；TP 调整同时验收 logits 对齐与 current refit |
| 显存和缓存      | 联合预算两模型权重、KV 和常驻开销；评测切换时正确释放/恢复；不能通过缩短正式 cap 掩盖容量问题                    |
| 生命周期        | Current 按需 refit；冻结模型避免重复加载；不在不需要时唤醒验证引擎；完整批 α=0/1 可跳过无用分量                  |
| 算子与图捕获    | 先定位 Python/launch/reduction 开销，再决定 fused sampler、CUDA graph 等；无收益的额外复杂度不保留               |

α 端点优化只用于能确定后续不再需要该分量的阶段。未来 TRB 在某个位置解出 α=0 或 1，不意味着下一个位置可以不计算另一模型，求系数仍可能需要两侧分布。

后端选择以测量为准：可优化 HF，也可接入本地 vLLM/SGLang 的双模型执行路径。不要同时维护多个未经验证的生产后端。HF 可以成为最终方案的前提是通过同样的真实负载、生命周期和性能验收，而不是因为参考实现已经可运行。

Teacher 在线输出复用给 Full-KL scoring 属于可选优化；选中 token 的概率不够支撑全词表 loss。先保留现有 scoring 保证正确，并将额外 pass 计入总成本。

### 12.4 统一工作负载

两组实际模型配对都要测：1.7B-Base + 8B、1.7B-Base + 30B-A3B-Instruct-2507。采用全局 batch64、训练 response cap7168，记录实际 prompt 长度分布、公共采样参数、α、EOS 规则与硬件。性能主对照固定 α=0.5；α=0/1 用于正确性和退化快路径验收。并发与微批可以优化，但不能改变原始任务、样本数量与有效 token 定义。

先短 cap 做功能检查，再进行正式长 cap 测量。并发扫描从小到大，依据显存、吞吐、排队与 preemption 收敛；至少覆盖三个可行点，并在最佳点附近细化或说明资源边界。不要照搬单 student 的 max_num_seqs=64 作为双模型固定答案。

分别准备初始 Base 的长/重复响应负载，以及同模型结构的可用后期 student checkpoint 短响应负载。两组分别报告，后期 checkpoint 仅用于工作负载测量；不能因此把实验中的 initial 重新绑定到后期权重。

每个最终候选完成预热后，至少做三次独立完整批测量，报告原始值、中位数与范围；差异接近波动时继续重复，不据单次最快结果作结论。每轮重置请求/KV，明确是否保留权重、图缓存和 prefix cache；冷启动和热运行分别报告。

使用两类对照：固定 token 前缀/回放用于算子与缓存的同工作量比较；自然 EOS 生成用于实际训练吞吐。回放速度不能代替自然生成结果。跨后端采样轨迹不同造成 token 数不同时，须同时报告有效 token 数、长度分布与耗时，避免把更早停止当作纯系统加速。

### 12.5 必须交付的指标

| 层面   | 指标                                                                       |
| ------ | -------------------------------------------------------------------------- |
| 生成   | 完整 batch 墙钟、有效 response tokens/s、响应长度分布、完成/失败条数       |
| 阶段   | 同步、prefill、decode、融合、通信、切换耗时；单独统计首次加载              |
| 资源   | 每卡峰值显存、GPU util 时间序列、CPU RSS、KV/preemption 可观测值           |
| 训练   | 每 outer 总耗时、teacher scoring、actor update、含定期验证的累计 GPU-hours |
| 正确性 | 共同前缀 logits/最终概率误差、mask、EOS、source/model version、输出数量    |

Tokens/s 的分子只计实际输出的有效 response token，不把两侧模型的 forward token 数相加。报告固定有效 token 的资源成本时同时给总 GPU 数，避免用更多 GPU 的总 TPS 冒充同成本加速。

### 12.6 完成性能验收的条件

1. 两组配对均通过正式 cap 的完整批运行；所选并发有实测余量，跨训练/验证/恢复切换不 OOM。若某模型未通过，明确标为未交付，不能只写“不支持”后宣布全部完成。
2. 所有保留优化通过 reference 对照；数值容差由 dtype、后端和 FP64 oracle 共同确定，测量前固定，不能为掩盖失败事后放宽。
3. 相对真实 reference 的收益在重复测量中可复现，同时没有改变采样目标、缩短 cap 或减少样本数。报告全部成本，包括同步、切换、额外 scoring 与资源数量。
4. 默认 current single 做相同负载回归。中位完整批耗时增加超过 5% 视为回归待解决；接近该阈值先增加重复次数确认，不以噪声定性。
5. 若候选优化没有稳定收益，保留较简单实现，并用瓶颈剖析、尝试过的布局/并发对照及原始测量说明原因。只有证据表明主要时间已由必要模型计算或必要通信占据、且可避免的重复计算/空转已处理，才能给出“当前硬件下不采用该优化”的结论；“HF 能跑”不满足此条件。

不预先承诺任意倍数的速度提升。上述条件定义的是可检查的工程完成标准；仍有明显低效或未测模型时，性能任务保持未完成。
