# Rollout 双融合实施交接说明

更新日期：2026-10-30。当前开发实现位于独立 `MirrorOPD-verl-vllm-fusion` worktree 的 `feat/vllm-fusion` 分支，尚未合并到本主仓库。完整通过项、失败候选和后续容量复测以[实现与验收记录](2026-10-28-Rollout双融合实现与验收记录.md)为准；阶段顺序与数值策略见[vLLM 方案](2026-10-28-vLLM双模型融合重构与优化方案.md)。

## 当前执行环境与优先级

物理 GPU6、7 用于本轮工作，持久环境为工作区 `envs/mirroropd-fusion`，使用 vLLM 0.25.1/V1、Torch 2.11 和 Transformers 5.12.1。两张卡当前优先运行[十组正式前缀实验](../../../experiments/rollout-policy/2026-10-30-E20设置下的五种前缀对照.md)，入口源码、配置与冻结版本见该报告的源码快照和队列 manifest；后续扩展验收不与该队列争用 GPU。

新入口显式选择 `rollout_policy.execution.backend=vllm_fusion`，HF 静态微批与 vLLM 活跃请求上限分开配置；默认 single 和验证继续使用各自入口。运行脚本、监控、Ray 临时目录和 IPC 命名空间都需使用开发分支的隔离实现，不能只替换下面旧命令的模型名就认为已切到新后端。

## 历史 HF 入口与实现说明

以下保留 2026-10-28 的 HF 使用方式，便于回溯旧证据。GPU0–3、临时环境和脚本默认值均是历史配置，不能用于当前 GPU6、7 的 vLLM 正式实验。

## 运行边界

新增路径使用单节点 shared-sync、FSDP2、全参数 learner、单轮文本、TP1 和本地 checkpoint。Token 融合的当前实现限定 Qwen3 dense learner，teacher 可以是 Qwen3 dense 或 Qwen3 MoE；验证继续使用当前 learner 的默认 vLLM 接收器。模型必须共享 token-ID 映射。

默认 `single / student / current` 保留原来的生成入口。`initial` 始终指配置中原始 learner checkpoint，不受训练恢复路径影响；额外 checkpoint 由 `model_path` 指定。Teacher、initial 和额外 checkpoint 不接收 learner refit。

本机验收只使用物理 GPU 0–3。隔离 Python 环境为 `/tmp/mirroropd-fusion-venv`，CUDA 兼容库位于工作区 `cache/fusion-runtime/cuda-compat-12-9/`。该环境使用 Torch 2.11、Transformers 5.12.1、vLLM 0.25.1、TransferQueue 0.1.11、FlashAttention 2.8.3 和 Triton；完整版本记录在工作区 `runs/rollout-fusion-20261028/environment-requirements.txt`。

## 启动入口

在仓库根目录运行短训练：

```bash
bash examples/mirroropd/smoke/smoke_rollout_fusion.sh token_mixture current
bash examples/mirroropd/smoke/smoke_rollout_fusion.sh token_mixture initial
bash examples/mirroropd/smoke/smoke_rollout_fusion.sh trajectory_mixture current
bash examples/mirroropd/smoke/smoke_rollout_fusion.sh trajectory_mixture initial
```

上述入口默认使用 1.7B-Base + 8B、短 response cap；`TEACHER_MODEL` 和 `FUSION_MICRO_BATCH_SIZE` 分别覆盖 teacher 路径和微批上限。生产性能结论必须使用正式负载，不能引用这些 smoke 的吞吐代替。

冻结单来源与额外 checkpoint：

```bash
bash examples/mirroropd/smoke/smoke_rollout_fusion.sh single initial
bash examples/mirroropd/smoke/smoke_rollout_fusion.sh single current rollout_policy.source=teacher
bash examples/mirroropd/smoke/smoke_rollout_fusion.sh single current \
  rollout_policy.source=checkpoint rollout_policy.model_path=/absolute/local/checkpoint
```

系数可用标量，或明确时钟的线性计划：

```bash
bash examples/mirroropd/smoke/smoke_rollout_fusion.sh token_mixture initial \
  'rollout_policy.teacher_weight={kind:linear,start:1.0,end:0.0,steps:4,clock:optimizer_step}'
```

`optimizer_step` 只计算已成功应用的更新；`outer_step` 计算已完成的 outer。缺少 applied optimizer 计数的旧 checkpoint 不能恢复绝对 optimizer 衰减计划。常数与 outer 计划不伪造这个计数。Token 融合的完整批 α=0/1 仍使用同一 HF 数值实现，只加载和执行活跃的一个生成分量，避免端点切换后端时改变推理精度。

真实训练、五个验证集、保存、恢复和 initial 衰减端点的可复现矩阵入口为：

```bash
bash examples/mirroropd/benchmarks/fusion/run_fusion_lifecycle_fsdp2.sh my-unique-run-prefix
```

脚本采用短 response cap、验证 n=1，检查训练生命周期；它不构成长程任务精度结论。运行目录必须不存在，避免覆盖已有证据。

正式 batch64/cap7168 的执行分块在 `run_fusion_benchmark_fsdp2.sh` 中；`run_fusion_long_lifecycle_fsdp2.sh dense|moe <prefix>` 记录参考路径和优化路径的完整训练、验证、保存与恢复成本。诊断开关 `++actor_rollout_ref.rollout.engine_kwargs.hf_fusion.reference=true` 保留相同权重、精度和采样，仅关闭预分配 KV、Flash KV decode 和 CUDA graph，便于在原 trainer 内作对照。

停止诊断只观测概率，不改变输出：同时记录两模型在两个原生 EOS 坐标上的概率、raw stop-set union 的总质量、各自原生 EOS 映到 STOP 的事件融合，以及双方共同合并 stop set 的事件融合。两种事件映射的定义不同，不能混称为一个 EOS 修复；实际生成始终采用 raw-token fusion。

推理精度修改只作用于独立推理实例。Dense 与 MoE 均保留 BF16 权重和 FP32 中间激活，减少中间舍入对后续层及 router 的影响；MoE router 的小型权重矩阵做精确 FP32 扩展。Attention/KV 使用 FP16 中间量。图缓存在微批结束、压紧和 refit 之前失效。仅保留 FP32 linear 输出的 Dense 候选已因长批数值误差被拒绝。正式性能与训练验收通过前，当前组合仍视为待验收候选。

发生来源失败时，整批不进入更新。取消 await 不能证明远端 RPC 已停止；必须取得独立排空确认后才清理 TQ 和切换 GPU。无法确认排空或 parent 发布超时时终止运行，不复用不确定的 GPU/TQ 状态。真实 Ray/TQ 故障测试和四 rank refit 注入位于 `tests/experimental/rollout_policy/`。
