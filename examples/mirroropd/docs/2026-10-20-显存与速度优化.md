# A800 数学 OPD 基线的显存与速度优化

本文依据 run `b38hw8v0` 的 [38 步训练快照](data/b38hw8v0-api-20261020/history.jsonl)、[系统统计](data/b38hw8v0-api-20261020/system-analysis.json) 与[实际配置](data/b38hw8v0-api-20261020/config.json)分析性能，更新于 2026-10-20。实验质量、算法与验证指标定义见[实验记录](2026-10-20-sampled-token-OPD数学基线-b38hw8v0.md)。文中候选参数尚未做 GPU 对照，不代表已获得对应加速。

## 当前测量结论

最优先处理的是 **完整验证的频率与推理调度**。一次 step 20 验证用了 5.889 小时，比当前 38 步训练合计的 1.550 小时长得多。训练阶段本身约 85.66% 时间在 `gen`，actor 更新约 8.83%。先去掉 offload 或提高训练 MFU，无法解决当前大部分墙钟开销。

硬件已由 W&B metadata 确认为 8 × A800-SXM4-80GB。4 张 student 卡在训练与 rollout 间切换；另外 4 张是同一 teacher 的独立评分副本，TP 均为 1。[系统曲线](figures/b38hw8v0-api-20261020/system-gpu.png)显示，长时间验证期间有一组 4 卡一直没有 kernel，却保留了约 32.7 GiB/卡的显存。这组卡与 teacher 的用途一致，资源调整前需核对 Ray 的物理 GPU 映射。

### 训练阶段计时

以下为 step 2–38 的算术平均，剔除首步预热；均值来自 [analysis.json](data/b38hw8v0-api-20261020/analysis.json)。

| 阶段 | 秒 / step | 整步占比 | 能确认的范围 |
| --- | ---: | ---: | --- |
| `gen` | 124.176 | 85.66% | Student 采样、verifier、teacher 评分、请求等待与 TQ 路径 |
| `old_log_prob` | 5.753 | 3.97% | Actor 重算已采样 token 的概率及相关调度 |
| `adv` | 0.106 | 0.07% | Advantage 与诊断计算 |
| `update_actor` | 12.802 | 8.83% | 外层 actor 更新，含部分切换与返回 |
| `update_weights` | 2.092 | 1.44% | Actor 向 rollout 同步权重 |
| 其余 | 0.039 | 0.03% | 用整步时间减上述阶段得到的残差 |
| 整步 | 144.967 | 100% | 不包括独立的 `testing` timer |

首步为 216.867 秒；以上几个 timer 的残差约 55.1 秒，应归为尚未拆分的首次启动成本。日志存在 Triton JIT 提示，但没有证据把全部残差都归因于编译。

稳态约 26.49 题/分钟，按整个计时区间累计 token 除以累计步时得到约 2691 有效 token/s；W&B 每步 `perf/throughput` 的平均约为 336.39 token/s/GPU，归一化分母为申请的全部 8 卡。这里 token 包含 prompt+response，不是服务端纯 decode token/s。

单独消除 actor 更新的全部耗时，理论整步加速上限也只有：

$$
S_{\rm actor,ideal}=\frac{144.967}{144.967-12.802}\approx1.097.
$$

若能将 `gen` 加速 20%，其他阶段不变，整步约变为 $144.967-124.176+124.176/1.2=124.271$ 秒，约加速 16.7%。这是 Amdahl 计算场景，不是实测结果。

### 验证的总成本

当前验证集有 570 题、每题 16 个回答，每轮 9120 个生成请求，最长 response 为 31744 token。训练每 20 步验证一次并在最后一步验证：step 20、40、……、260、279，共 14 轮；checkpoint 另在 50、100、150、200、250、279 保存。

$$
N_{\rm val}=570\times16\times14=127{,}680,\qquad
N_{\rm train}=279\times64=17{,}856.
$$

仅比较回答条数，验证就是训练的约 7.15 倍，而且验证允许约 4.43 倍的 response 上限。实际生成 token 数还取决于自然终止长度，不能只乘这两个比值估计精确时间。

按目前唯一一轮验证的 5.889 小时和稳态训练步时作粗外推：

| 验证间隔 | 279 步内验证轮数 | 验证小时 | 训练 + 验证小时 |
| --- | ---: | ---: | ---: |
| 20，当前基线 | 14 | 82.45 | 约 93.68 |
| 50，候选 | 6 | 35.33 | 约 46.57 |
| 100，候选 | 3 | 17.67 | 约 28.90 |

这些估计不包括启动、保存和其他等待，且训练后的回答长度可能改变，不能作为完成时间承诺。8 卡一直占用时，当前粗估约 749.5 GPU 小时，其中验证期间专用 teacher 的 4 卡没有参与计算。

## 显存占用的三个口径

### Actor 进程的 PyTorch 显存

到 step 38，actor 指标的 allocated 高水位为 19.815 GiB，reserved 高水位为 20.852 GiB。其来源分别为 `torch.cuda.max_memory_allocated()` 与 `max_memory_reserved()`，经 worker 汇总，属于 actor 进程 allocator 的峰值统计；统计窗口还受 reset 位置影响。不能把两条曲线差值直接理解成整卡碎片，更不能用 80 减这两个数推断 rollout 可用显存。

它们没有覆盖另一进程中的 vLLM 权重、KV cache、CUDA context 和其他设备分配。到 step 19 就已达到当前 19.815 GiB 高水位，step 20 后保持不变；曲线不支持 actor allocated 持续泄漏的判断。

### 整卡设备显存与 busy

系统 stream 中 `memoryAllocatedBytes` 是设备已分配字节，按 $2^{30}$ 换算 GiB；`memoryAllocated` 是容量百分比，`memory` 是内存读写忙碌率。`gpu` 是 kernel busy 百分比，不能把 `memory` 当显存占用百分比。[^nvidia]

两个主要系统指标的单位关系为：

$$
\mathrm{GPU\ busy}=100\frac{t_{\rm kernel\ active}}{t_{\rm sampling\ window}},\qquad M_{\rm GiB}=\frac{M_{\rm allocated\ bytes}}{2^{30}}.
$$

Busy 是设备在该窗口内至少执行一个 kernel 的时间比例，不是所有 SM 或 Tensor Core 的平均满载程度。

系统 API 返回 3825 行，其中 GPU 行 1912，GPU 样本间隔中位数 15.003 秒。下表为样本均值；验证区间按 step 20 `_timestamp` 减去 `timing_s/testing` 近似定位，边界会受日志延迟影响，原始 stream 也可能被服务端抽样。

| 区间 | 物理 GPU 组 | Busy 均值 | 显存均值 / 最大值 | 功率均值 |
| --- | --- | ---: | ---: | ---: |
| 训练，排除首步前与验证 | 0–3 | 39.58% | 37.04 / 40.98 GiB | 150.40 W |
| 同上 | 4–7 | 0.81% | 32.67 / 32.86 GiB | 99.25 W |
| 验证近似区间 | 0–3 | 35.92% | 40.89 / 40.98 GiB | 153.22 W |
| 同上 | 4–7 | 0.00% | 32.67 / 32.86 GiB | 95.53 W |

0–3 在验证中持续计算，4–7 完全空闲，支持“student 生成占主导、teacher 卡数有缩减空间”的判断。Teacher 评分是短促工作，15 秒采样可能漏掉峰值；缩减前仍需测 teacher 请求延迟和排队。全 8 卡平均 busy 会把工作与空闲卡混在一起，优化时应按资源池与阶段分别看。

### 权重、优化器与 KV cache 的理论预算

模型实际 $P=1{,}777{,}088{,}000$，BF16 全权重约 3.310 GiB。典型混合精度 AdamW 的示意状态预算为 BF16 权重 2 bytes、BF16 梯度 2 bytes、FP32 master weight 4 bytes、两个 FP32 moment 8 bytes，共约 16 bytes/parameter：

$$
M_{\rm states}\approx16P=26.481\ \mathrm{GiB},\qquad
M_{\rm shard}\approx\frac{16P}{4}=6.620\ \mathrm{GiB/rank}.
$$

这是规划量，不是本实现保证的精确内存布局。实际 FSDP2 参数 dtype、梯度累积、all-gather 峰值、激活、临时 logits 与 offload 会改变分布。`fsdp_config.model_dtype=fp32` 与混合精度运行配置同时存在，不能把 BF16 权重大小当成训练全部状态。

GQA 的 BF16 KV cache 每个 token 需要：

$$
M_{\rm KV/token}=2_{\rm K,V}\times L\times K\times d_h\times2_{\rm bytes}
=2\times28\times2\times128\times2=28{,}672\ \mathrm{bytes}=28\ \mathrm{KiB}.
$$

| 每副本场景 | 理论 KV cache |
| --- | ---: |
| 16 条完整训练 context，11265 token/条 | 4.813 GiB |
| 64 条完整训练 context，11265 token/条 | 19.252 GiB |
| 16 条完整验证 context，35841 token/条 | 15.313 GiB |
| 32 条完整验证 context，35841 token/条 | 30.626 GiB |

还需权重、workspace、block rounding、CUDA Graph 等空间，且 vLLM 会按预算预分配 cache。Teacher 32.7 GiB 的常驻显存与 `gpu_memory_utilization=0.4` 一致，并不表示 teacher 实际同时保存了这么多有效 token。Student 训练每副本约 16 条，而验证负载可接近 32 条；提高并发前应优先验收长验证样本，不能只看训练峰值。

## 参数调整顺序与验收

本次只提出对照方案，保留已有 baseline 的参数和记录。所有命令从仓库根目录运行，默认需要申请对应 GPU；Hope 的 worker 仍经 `hope/mirroropd/run.sh` 调用领域入口。

| 优先级 | 单项候选 | 依据 | 主要验收项 |
| --- | --- | --- | --- |
| P0 | 新 run 设 `TEST_FREQ=100`，保留每轮 n=16 与 31744 上限 | 直接减少 14→3 次完整验证，不改变 KD loss 设置 | 最终验证完整；不同 run 的训练步数一致；总 GPU 小时 |
| P0 | 另设固定小验证集和较少采样用于快速监控，最终 checkpoint 仍跑完整基线预算 | 缩短开发反馈周期 | 明确区分快速监控与正式评测，不能混画成相同精度的点 |
| P1 | `ROLLOUT_ENFORCE_EAGER=False` | 当前 student 强制 eager；长 decode 中减少逐步 launch overhead 可能有益 | 图捕获成功，预热后 gen/验证耗时与整卡峰值；回答数和 mask 正常 |
| P1 | `VAL_BATCH_SIZE=32`，再单独比较 64 | 当前 16 题窗口全完成后才提交下一窗口，长尾可能让后半段 GPU 闲置 | 单轮验证时长、请求失败率、尾部 busy；不会减少实际验证题数 |
| P1 | `TEACHER_GPUS=2`，随后 1 | 专用 teacher 采样 busy 很低，验证时一直空闲 | Teacher 排队 p95、gen 步时和 GPU 小时；资源申请同步减少 |
| P2 | `TEACHER_TOKEN_BUDGET=16384`；另测 student 同名 rollout budget | Teacher 长序列评分可能获益于更大 prefill batch | Teacher 评分吞吐和延迟；student decode 并发未必因此提高 |
| P2 | 独立尝试 `TEACHER_ENFORCE_EAGER=False` | 可比较推理图对 teacher 评分的收益 | 评分 shape 是否受益、capture 显存和长序列行为 |
| P3 | 依次关闭 optimizer offload、parameter offload、gradient checkpointing | 有显存余量，但 actor 更新只占约 9% | 外层 update_actor、内部训练时间、切换时间与长验证峰值 |

vLLM 的 graph、并发和 token budget 都有显存/吞吐权衡；chunked prefill 的吞吐参数对 decode 和长序列评分的影响不同，应按请求形态测试。[^vllm]

增大训练 batch 可能提高生成的并行度，但它也改变更新次数和样本分布：batch=128 时同一 epoch 只有 139 次更新，不能只比较 epoch 耗时。当前全局长度均衡后的最大 rank 差值不到均值的 0.54%，没有明显的 token 总量失衡证据；全局增 batch 的收益应先和验证、CUDA Graph 方案比较。

当前全 38 步约 58.6% 回答达到 7168；将训练 response budget 直接降为 4096 会改动大量训练样本。降低 temperature、top-p、改 TP、去掉 teacher 或改变 KL 算法也都会改变质量或执行语义，应分别立项，不能算作等价的纯性能开关。GPU memory utilization 控制 vLLM 的内存预算；提高它主要扩展 cache 容量，不会直接提高 SM busy。

### 短训练对照

保持相同模型、数据、seed、batch 和 response budget，关闭验证和保存，每组至少观察 10–12 步，剔除第一步或首次 graph capture。对比统计中同时报告 token 总数和生成长度，避免把生成变短误当作系统加速。

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 TEST_FREQ=-1 SAVE_FREQ=-1 \
  EXPERIMENT_NAME=math-perf-baseline \
  bash examples/mirroropd/run_math_deepseek_r1_1_5b_fsdp2.sh \
  trainer.total_training_steps=12

CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 TEST_FREQ=-1 SAVE_FREQ=-1 \
  EXPERIMENT_NAME=math-perf-student-graph ROLLOUT_ENFORCE_EAGER=False \
  bash examples/mirroropd/run_math_deepseek_r1_1_5b_fsdp2.sh \
  trainer.total_training_steps=12
```

同样的方法分别比较 `TEACHER_TOKEN_BUDGET=16384`、`OPTIMIZER_OFFLOAD=False`。训练关闭验证的设置只用于吞吐对照，不能据此交付质量结论。最终一步在 `TEST_FREQ=-1` 时也不会触发验证，正式 run 要恢复验证配置。

### 较低验证频率与更大窗口

先独立试验证频率，再比较窗口；下面两条是不同候选 run，不要同时启动在同一组卡上：

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 TEST_FREQ=100 \
  EXPERIMENT_NAME=math-sampled-eval100 \
  bash examples/mirroropd/run_math_deepseek_r1_1_5b_fsdp2.sh

CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 TEST_FREQ=100 VAL_BATCH_SIZE=32 \
  EXPERIMENT_NAME=math-sampled-eval100-window32 \
  bash examples/mirroropd/run_math_deepseek_r1_1_5b_fsdp2.sh
```

当前 [V1 验证循环](../../../verl/trainer/ppo/v1/trainer_base.py)按 batch 提交，等本 batch 的 session 都结束后取回结果、清理 TQ，再处理下一个 batch。16 题 × n=16 展开为 256 条请求，student 4 副本 × max_num_seqs=32 最多同时执行 128 条；队列和 batch 尾部仍可能有空档。增加窗口会增加排队请求，不等于一次让所有请求占 KV cache，但可能提高主机/TQ 用量，必须实测。

### Teacher 卡数与实际资源申请

直接配方支持 4+2 或 4+1，例如在已申请 6 卡的开发环境中：

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5 TEACHER_GPUS=2 TEST_FREQ=-1 SAVE_FREQ=-1 \
  EXPERIMENT_NAME=math-perf-teacher2 \
  bash examples/mirroropd/run_math_deepseek_r1_1_5b_fsdp2.sh \
  trainer.total_training_steps=12
```

Hope 当前入口固定 4+4 并检查 8 卡；通过 Hope 做这个对照时，需要修改接收端本地 `run.sh` 的资源校验和 teacher 配置，并把任务资源申请同步改为 6 或 5 卡。本次文档没有修改它。仍申请 8 卡再只使用 6 卡，不能节省平台占用 GPU 小时。

设 4+2 使步时变为原来的 $r$ 倍，则 GPU 小时比值为 $6r/8=0.75r$；只要 $r<4/3$ 就更省 GPU 小时。4+1 的对应条件为 $r<8/5$。质量配置相同时，还应分别报告绝对墙钟时间，不能只按资源成本选方案。

## 值得做的代码改动

### 先补充计时，定位 gen 内部成本

[AgentLoop 后处理](../../../verl/trainer/ppo/v1/agent_loop_tq.py)先 await verifier，再 await teacher log-prob，最后写 TQ。一个 prompt 的这些时间会顺序累积，不同 prompt 又可能重叠；因此把它们的逐请求耗时相加不能直接当作整步墙钟。

建议新增可聚合的请求级时间：student request submit/start/end、verifier start/end、teacher enqueue/start/end、TQ put/ready；按每步报告 count、均值、p50/p95 和关键路径等待。同时保存生成 token 数、finish reason、每个副本的 pending/running 请求数。只有这些数据到位后，才能区分长尾解码、teacher 排队、CPU 判分和调度空档。

MFU 另可记录每步 $T=\sum s_i$、$Q=\sum s_i^2$、内部 train_batch 秒数、识别到的 GPU 型号和峰值。这样可精确复核 [MFU 计算](2026-10-20-MFU计算.md)，而不需要保存训练文本。

### 验证跨窗口连续调度

如果增大 `VAL_BATCH_SIZE` 后 GPU busy 和验证耗时仍有明显改善空间，可以将验证改成有上限的跨 batch 在途队列：一个窗口收尾时提交下一窗口，避免等待最慢长回答才继续。实现要保持每题 16 条的 UID、答案对齐、失败计数、完整题目覆盖及 TQ 清理语义。此改动应先用 mocked sessions 测试，再用同一 checkpoint 对照验证总时长和指标；它比单纯调大 token budget 更直接针对当前的窗口尾部等待。

### 避免重复的 old-log-prob 前向

已有 rollout log-prob，而 actor 仍花约 5.75 秒重算训练后端概率；理论上值得研究复用。当前两个后端有可测的 $10^{-4}$ 量级 KL，旧 actor 概率还参与 PPO ratio 和一致性诊断，因此不能直接删除该阶段。需要明确选择 rollout policy 还是 training policy 作分母，并配套 IS/bypass 与 loss 等价性验证。该方向改变训练语义，优先级低于验证频率与 graph。

### Verifier 与专用 teacher 的资源

数学任务分数不参与当前 KD 梯度，关闭训练期间的 verifier 可能减少 CPU 成本，但会失去每步数学正确率与部分诊断。应先计时，再决定只在固定监控 batch 判分，且显式保留正式验证。Teacher 在验证期间完全空闲，长期可考虑独立评测作业或释放其资源；这需要调度层支持，当前固定资源池不会自动返还 GPU。

## 对照结果的记录标准

每次对照记录实际解析配置、代码来源、GPU 映射、同一评测 checkpoint、生成总 token、完整训练/验证墙钟、峰值整卡显存、GPU busy 采样覆盖与 GPU 小时。至少覆盖一次长验证，确认没有 OOM、失败样本或结果缺失。actor MFU 是辅助指标，最终按相同质量预算下的墙钟与 GPU 小时评估收益。
