# 固定验证设置下的 8 卡 OPD 效率优化

目标是保持数学验证设置和 sampled-token OPD 训练目标，提高实际吞吐：固定 570 题、每题 16 次采样、temperature=0.7、top-p=0.9、response≤31744、验证间隔 20、提交窗口 16；完整训练预算仍为 batch=64、n=1、mini-batch=64、每批更新一次。本文不再把降低验证频率、减少题目或缩短回答作为优化方案。

证据来自 `b38hw8v0` 的 [38 步训练快照](data/b38hw8v0-api-20261020/history.jsonl)、[系统采样](data/b38hw8v0-api-20261020/system-analysis.json)、两个新增的 [student](data/oneshot-student-6uorrk2k-api-20261020/config.json) / [teacher](data/oneshot-teacher-u87buult-api-20261020/config.json) 评测配置，以及 2026-10-20 查阅的 verl、ResOPD、One-Shot-OPD 源码。所有新配置均为待测方案，尚无对应 GPU 加速实测。

## 结论与优先级

**4+4 是资源浪费的主要原因之一，但每张 student 卡的低利用率还要单独处理。** 当前只有 4 张卡可以生成 student 回答，另外 4 张只能给已完成的轨迹打分；teacher 很轻，无法用足这些专用卡。把更多显存分给 teacher，或把 teacher TP 增大，都不能让这些卡帮助 student 解码。

推荐的完整 8 卡方向是借鉴本地 One-Shot-OPD：**student 生成/验证、冻结的 FSDP teacher 打分、student 更新复用同一组 8 卡，分阶段执行**。先保留全局 batch=64 与验证设置，测净墙钟收益；随后再决定是否增加训练 batch。当前主线 V1 只接入独立的 vLLM teacher pool，迁入共享 FSDP teacher 需要代码改动，不能直接复制另一个仓库的开关。[^oneshot-mixin] [^verl-v1]

同时先做容易归因的对照：student 开 CUDA Graph、记录推理统计，再比较 logits/entropy 融合和动态 token budget。这些措施改善实际执行，不减少验证工作量。减少专用 teacher 到 1–2 卡能降低占用，但不能满足“同一组 8 卡都帮助 student”的目标，因此不作为本轮主方案。

## 现有测量与主要瓶颈

### 训练阶段

Step 2–38 的平均值来自 [analysis.json](data/b38hw8v0-api-20261020/analysis.json)，剔除了首步预热。

| 阶段 | 秒 / step | 占比 | 计时范围 |
| --- | ---: | ---: | --- |
| `gen` | 124.176 | 85.66% | Student 生成、verifier、teacher 评分、TQ 和请求等待 |
| `old_log_prob` | 5.753 | 3.97% | Actor 重算 sampled token 概率 |
| `adv` | 0.106 | 0.07% | Advantage 与诊断 |
| `update_actor` | 12.802 | 8.83% | 外层参数更新，含部分切换成本 |
| `update_weights` | 2.092 | 1.44% | 向 rollout 同步参数 |
| 其余 | 0.039 | 0.03% | 计时残差 |
| 完整训练 step | 144.967 | 100% | 验证单独计时 |

首步耗时 216.867 秒，有约 55.1 秒尚未归入这些 timer，不能都归因于 JIT。稳定阶段约 26.49 题/分钟，累计 token / 累计 step 时间约 2691 token/s，包含 prompt 与 response。训练/验证分阶段记账仍然必要：一次完整验证为 21200.77 秒，但本轮优化固定其工作量。

即使完全消除 actor 更新，整步加速上限也只有：

$$
S_{\rm actor,ideal}=\frac{144.967}{144.967-12.802}\approx1.097.
$$

主收益应从 student 生成路径、资源复用和调度空档寻找。`gen` 内包含 teacher 与 CPU 逻辑，当前还不能把全部 124.176 秒视为纯 GPU decode。

### 整卡显存、busy 与进程显存

![系统 GPU 指标](figures/b38hw8v0-api-20261020/system-gpu.png)

系统 API 返回 3825 行，1912 行含 GPU 采样，采样间隔中位数 15.003 秒。下表使用样本均值，验证区间由 `_timestamp` 和 `timing_s/testing` 近似定位。

| 区间 | 物理 GPU 组 | Busy 均值 | 整卡显存均值 / 最大值 | 功率均值 |
| --- | --- | ---: | ---: | ---: |
| 训练，排除首步前与验证 | 0–3 | 39.58% | 37.04 / 40.98 GiB | 150.40 W |
| 同上 | 4–7 | 0.81% | 32.67 / 32.86 GiB | 99.25 W |
| 验证近似区间 | 0–3 | 35.92% | 40.89 / 40.98 GiB | 153.22 W |
| 同上 | 4–7 | 0.00% | 32.67 / 32.86 GiB | 95.53 W |

0–3 的行为与 student 一致，4–7 与专用 teacher 一致；实际 Ray rank→物理 GPU 映射仍应在试验启动时打印确认。15 秒采样可能漏掉 teacher 的短促 kernel，不能从 0.81% 倒算精确评分耗时。即便如此，验证时有整组卡不参与计算、训练中两组 busy 相差很大，这些事实足以支持重新设计资源分配。

$$
\mathrm{GPU\ busy}=100\frac{t_{\rm kernel\ active}}{t_{\rm sample\ window}},\qquad M_{\rm GiB}=\frac{M_{\rm allocated\ bytes}}{2^{30}}.
$$

Busy 衡量窗口内至少有一个 kernel 执行的时间比例，不代表所有 SM/Tensor Core 的平均满载度。`system.gpu.*.memoryAllocatedBytes` 是整卡字节数，`memoryAllocated` 是容量占比，而 `memory` 是内存读写忙碌率。[^nvidia]

Actor 的 PyTorch 高水位为 allocated=19.815 GiB、reserved=20.852 GiB，是另一个进程 allocator 的统计，不能拿它代替整卡占用。主机内存 74.39→110.01 GiB 是整机 `psutil.virtual_memory().used`，不足以证明 actor 泄漏。Actor 内部 MFU 稳态约 38.98%，分母只含 4 张 actor 卡和内部训练 timer，计算边界见 [MFU 文档](2026-10-20-MFU计算.md)。

## 显存还有余量，但增加预留不等于提高吞吐

模型实际约 1.777B 参数，BF16 全权重约 3.310 GiB。GQA 的每 token KV cache 为：

$$
M_{\rm KV/token}=2_{\rm K,V}\times28_{\rm layers}\times2_{\rm KVheads}\times128_{\rm headDim}\times2_{\rm bytes}
=28{,}672\ \mathrm{bytes}=28\ \mathrm{KiB}.
$$

| 每个 TP=1 副本的场景 | 理论 KV cache |
| --- | ---: |
| 16 条序列 × 6300 token，接近当前训练形态 | 2.692 GiB |
| 16 条序列 × 11265 token，训练 context 上界 | 4.813 GiB |
| 32 条序列 × 35841 token，验证 context 上界 | 30.626 GiB |

还要加权重、workspace、block rounding 和 graph；同时 vLLM 会按预算预分配 cache。当前 teacher 约 32.7 GiB/卡与 `gpu_memory_utilization=0.4` 一致，并不意味着有效 KV 占满这些空间。把它增加到 0.8 很可能只是留住更多空闲 cache。

当前训练 batch=64、student DP=4，平均每副本只有 16 个训练请求，而 `max_num_seqs=32` 已经高于这个数。把上限改成 64 或 128，不会凭空增加在途请求。大多数训练时间是短 prompt 后的长 decode；每轮 decode 约十几个 token，远低于 8192 的 batched-token 预算。提高这个预算主要影响 prefill/评分，不应自动期待训练 decode 加速。

简化为只读 BF16 权重的矩阵计算，每步解码 $b$ 条序列的算术强度约为：

$$
\mathrm{AI}_{\rm weights}\approx\frac{2Pb\ \mathrm{FLOPs}}{2P\ \mathrm{bytes}}=b\ \mathrm{FLOPs/byte}.
$$

当 $b\approx16$ 时，解码有带宽和小矩阵/launch 开销限制；这与可用显存容量是两件事。改成 8 个 student 副本且保持 batch=64 时，每副本只有约 8 条请求，单卡 busy 未必上升。复用 8 卡值得测试，是因为更多卡能服务 student、验证也能用 8 卡；不能据此承诺单卡满载或 2 倍加速。

训练状态的典型示意预算为 BF16 权重/梯度、FP32 master weight 和两个 moment，共约 16 bytes/parameter：全模型约 26.481 GiB，FSDP 4/8 rank 下理想分片分别约 6.620/3.310 GiB。真实布局还取决于参数 dtype、all-gather、激活和 offload，不能直接用这个理想分片值安排显存。

## verl、ResOPD、One-Shot-OPD 的做法

| 实现 / 配方 | 已核实的资源与执行方式 | 对本项目的启示 |
| --- | --- | --- |
| verl V1 OPD | `global_pool` 放 actor/rollout；另建 `teacher_pool`；teacher 对每条完成的轨迹立即评分，与其他轨迹生成重叠 | 当前就是这种模式；`distillation.n_gpus_per_node` 是额外资源，不是共享开关 |
| ResOPD 公开示例 | Student Qwen3.5-4B 用 4 卡；teacher Qwen3.5-27B 用 4 卡、TP=4；top-k=4、resopd loss | 4+4 服务的是大 teacher，不能把它当成 1.5B teacher 的性能最优配置 |
| 本地 One-Shot-OPD | `distillation.fsdp_teacher` 的冻结 teacher worker 注册进 actor 的同一 resource pool；FSDP CPU-offload；默认 student 资源为 8 卡 | 有现成的共享 8 卡部署实现可以参考，teacher 不再独占后四张卡 |
| verl Hybrid Engine | Actor 与 student rollout 复用 GPU，sleep/wake 与参数同步协调训练/生成 | 我们只在前四张卡上用了它，扩展 teacher 共池还需管理生命周期 |
| verl 异步配方 | 用异步生成/更新重叠减少 pipeline 空档，允许一定 staleness | 是后续方向，涉及采样策略版本与 IS，不能当作严格同步 OPD 的等价开关 |

ResOPD 检查到的 main 是 `3bdf019d`；verl main 是 `ddf70072`；本地 One-Shot-OPD 是干净的 `6b6b1782`。本文区分这些已实现代码与尚未合并的设计讨论。[^resopd] [^verl-v1] [^oneshot-mixin] [^oneshot-worker] [^async]

One-Shot-OPD 的 `register_opd_teacher()` 将 TeacherWorker 注册到 actor 共置 worker 集合；teacher `requires_grad=False`，forward-only，参数采用 CPU offload。其打分发生在 rollout 完成、student old-log-prob 已得到之后，参数更新之前。这里可以借用部署与打分方式；它还把 frozen token reward 交给自己的 advantage 分支，不能把整段 loss/advantage 逻辑一起复制到当前的 current-policy `k1 + PG` 实验。[^oneshot-mixin] [^oneshot-worker]

verl 的 `colocate_async` 指 actor 与 **student rollout** 共置，代码仍由基类建立独立 teacher pool。它不会自动将 student 改为 8 卡，也不会自动让 teacher 与 student 共池。TeacherModelManager 内的 `init_colocated(teacher_pool)` 只表示挂载到传入的 teacher pool，不能仅凭函数名判断为 actor/teacher 共卡。Issue #6705 的“single pool”讨论主要是多 teacher 之间切换权重、传递 hidden state，也不能读成已提供单机 student/teacher 共池开关。[^verl-colocate] [^rfc]

## 共享 8 卡的建议实现

推荐为现有 V1 trainer 增加一个可选的 forward-only FSDP teacher 后端；保留原独立 vLLM teacher 配方作为对照。共享方案按下列阶段运行，8 张卡的物理集合始终相同：

| 阶段 | 原 4+4 | 共享 8 卡目标 |
| --- | --- | --- |
| 训练生成 | 前 4 卡：4 个 student TP=1 副本；后 4 卡评分 | 8 卡：8 个 student TP=1 副本 |
| Teacher 评分 | 后 4 卡 vLLM，和生成部分重叠 | Student vLLM sleep 后，8 卡 frozen FSDP teacher 前向打分 |
| Old-log-prob / actor 更新 | 前 4 卡 FSDP2；teacher 等待 | 同一组 8 卡 FSDP2；teacher offload |
| 参数同步 | 更新 4 个 student 副本 | 更新 8 个 student 副本 |
| 验证 | 4 卡 student，teacher 4 卡闲置 | 8 卡 student；570 题、n=16、长度和频率保持原值 |

当前验证窗口 16 题展开为 256 请求；4 个副本 × 32 并发只能同时运行 128 请求，8 个副本则有 256 并发容量。这里没有改验证窗口、题数或采样次数，而是把原先闲置的卡用于相同工作。

需要迁移的边界如下；这些是设计位置，尚不是可执行配置接口：

1. 在 [distillation config](../../../verl/workers/config/distillation.py) 中明确选择专用 vLLM teacher 或共享 FSDP teacher，验证共享模式不再额外申请 teacher GPU。
2. 在 [V1 pool 初始化](../../../verl/trainer/ppo/v1/trainer_base.py) 将 forward-only teacher worker 注册到 `global_pool`，student world size 设为 8；按 actor/rollout 初始化完成后再加载 teacher。
3. 共享模式下，AgentLoop 先完成生成与 verifier，不等待独立 teacher client；在整个训练 batch 可用、student rollout 已 sleep 后，按现有 input IDs、position IDs 和 response mask 计算 teacher log-prob，写回当前 TensorDict/TQ 数据协议。
4. Teacher 只返回 sampled token 的概率，不搬运 $B\times S\times V$ 全词表张量；teacher 不训练、不添加 optimizer，温度固定为 1。保留当前 loss 中构造的 current-policy advantage，保持 `use_task_rewards=False`。
5. 将 teacher offload、actor 更新、rollout wake、验证切换串行化，显式记录 teacher 与切换 timer，避免两个大内存阶段同时唤醒。

不能仅设 `STUDENT_GPUS=8 TEACHER_GPUS=0`：当前脚本与 V1 pool 都会拒绝 0 卡 teacher；设为 8+4 又会申请 12 卡。共享模式还要同步修改 Hope 本地 worker 的固定 4+4 校验与资源声明，保留总量为 8；本轮没有更改运行中的 Hope 入口。

新路径的时间模型是：

$$
T_{\rm shared8}\approx G_8+Q_{\rm teacher,FSDP8}+O_8+U_8+W_8+S_{\rm switches}.
$$

$G,Q,O,U,W,S$ 分别是 student 生成、teacher 打分、old-log-prob、更新、权重同步和额外切换。原路径 teacher 与生成有重叠，新路径会增加显式 teacher 阶段；只有 $G_8$ 等阶段节省的时间超过打分与切换新增成本，净墙钟才改善。要实测完整 step 与相同验证，而不能简单把 124 秒除以 2。

### 新增参考 run 的执行差异

两个历史 val-only run 也使用 8 张 A800，采样 n=16、temperature=0.7、top-p=0.9、response≤31744 与当前一致。其 W&B run runtime 分别约 49.0 / 39.1 分钟，包含初始化；当前 353.35 分钟是独立 testing timer，不能直接报告精确加速倍数。它们使用旧 DataProto 路径、全部 8 卡生成、max_num_seqs=64、token budget=35840、memory utilization=0.75，且 val_batch_size=null，该版本默认整个验证集。数据和输入构造也需复核，不能将耗时差全归因于卡数。

这些配置差异为定位问题提供了现成对照：保持我们的验证设置，先用同一 checkpoint、同一服务容量对照 4 卡 / 8 卡推理，再逐项测 graph 与 pipeline。不要在改变卡数的同时把所有服务参数都改成历史值，否则无法区分收益来源。评测结果与配置对照见[实验记录](2026-10-20-sampled-token-OPD数学基线-b38hw8v0.md)。

## 现在可直接测试的执行优化

### Student CUDA Graph

当前 `enforce_eager=True`，每步 decode 可能有较大的 host launch 成本。先只关闭 student eager，并启用服务统计，保留所有验证和训练预算：

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 \
  EXPERIMENT_NAME=math-fixed-eval-student-graph \
  ROLLOUT_ENFORCE_EAGER=False \
  bash examples/mirroropd/run_math_deepseek_r1_1_5b_fsdp2.sh \
  'actor_rollout_ref.rollout.cudagraph_capture_sizes=[1,2,4,8,16,32]' \
  actor_rollout_ref.rollout.disable_log_stats=False
```

先看预热后的生成 token/s、TTFT/TPOT（后端若有记录）、running/pending requests、KV cache usage、preemption、完整步时与验证时长。Graph 显存不能通过 CPU offload 全部移走，必须测试 actor 更新与长验证的峰值。当前小模型 TP=1 已符合优先扩大副本数的做法，不建议仅为了多用卡而盲目加 TP。[^perf] [^vllm]

### 用额外显存容纳真实在途请求

有排队时，可以单独测试推理容量组合 `ROLLOUT_MAX_NUM_SEQS=48 ROLLOUT_GPU_MEMORY_UTILIZATION=0.7`，保持验证题数、n、response、频率与提交窗口不变。这是共享的服务容量参数，不减少任何评测请求。48 条最坏 35841-token context 的理论 KV 为约 45.94 GiB，加权重和 graph/workspace 后需检查 56 GiB 预算是否足够；不要直接将并发翻到 64 而不计算长验证 cache。

这个组合主要可能改善当前有 256 条排队请求的验证执行；训练平均每副本只有 16 条，容量增加本身不会改善训练 decode。先测 CUDA Graph，再独立测容量组合；graph 与 KV 的合计峰值、preemption 和请求延迟必须一起记录。

### Actor 的 token batching、offload 与输出头

这些只影响约 9% 的更新阶段，排在生成优化后；每次单独比较，验证设置保持默认。

| 候选 | 具体参数 | 验收重点 |
| --- | --- | --- |
| 更大动态 token budget | `PPO_MAX_TOKEN_LEN_PER_GPU=49152`，再比较 65536 | Micro-batch 数、外层 update_actor、峰值整卡显存 |
| 取消 optimizer / parameter offload | 依次 `OPTIMIZER_OFFLOAD=False`、`PARAM_OFFLOAD=False` | 传输与切换减少多少，是否挤占 vLLM/graph 空间 |
| 减少重计算 | `GRADIENT_CHECKPOINTING=False` | 步时与激活峰值；不是只看 MFU |
| 融合 logits/log-prob/entropy | `actor_rollout_ref.model.use_fused_kernels=True` | Sampled token log-prob、loss、entropy 和梯度数值对照 |
| 模型内部融合 | `actor_rollout_ref.model.use_liger=True` | 确认实际导入版本；与输出头融合分开归因 |

本模型词表 $V=151936$，未融合时一个 32768-token 的 BF16 logits 矩阵约为：

$$
32768\times151936\times2/2^{30}=9.2734\ \mathrm{GiB}.
$$

临时 FP32 softmax/entropy 还可能增加空间。融合输出头能够减少这类中间张量，比单纯增加显存预留更有实际意义；效果取决于 backend 和熵计算路径，需数值验收。源码已存在 fused / chunked entropy 分支；当前 `use_fused_kernels=False`，且 remove-padding 与动态 batching 已经开启，无需把它们当作新增优化。[^engine]

把 `max_num_seqs` 改得更大前，先证明 running/queued 请求受该上限限制；把 teacher token budget 增大前，先证明 teacher 有排队。训练 batch 提高到 128/256 可以增加有效 decode batch，但会改变每个 epoch 的更新次数和学习轨迹，应作为后续质量/吞吐联合实验，不能与 batch=64 配方直接按 epoch 耗时比较。

## 进一步的异步与调度方案

verl 的异步 / partial rollout / 独立训练-生成流水线能减少同步空档；收益依赖模型规模、节点数与采样长度。公开大规模加速数字不能套到当前 8 张 A800、1.8B 模型上。异步后轨迹可能来自旧策略，需要记录 trajectory staleness，并评估 IS/rollout correction；本轮严格同步基线不直接切换。[^async] [^async-kd]

验证中的 teacher 卡闲置可以通过共享资源结构解决；保留验证工作量还能用来检验 8 卡生成是否加速。先测试共享 FSDP teacher 与 CUDA Graph，随后才决定是否采用更复杂的异步调度。

## 对照与计时要求

每个实验记录解析配置、代码来源、同一 GPU 映射、原始采样 token 数、各阶段秒数、完整验证秒数、GPU 小时，以及分阶段的 busy 与整卡显存峰值。先用固定轨迹比较 vLLM / FSDP teacher sampled log-prob 的 mask、shift 和数值，再验证 current-policy `k1 + PG` 的 loss/梯度；不要求两个后端浮点逐位一致。

应新增 student submit/start/end、teacher enqueue/start/end、verifier 时间、TQ ready、sleep/wake、权重同步 timer，并报告计数与 p50/p95。不同请求有重叠，逐请求耗时之和不能当作整步墙钟。MFU 可记录 $T=\sum s_i$、$Q=\sum s_i^2$ 和内部 timer 以便复算。

共享 8 卡的验收是：总共只申请 8 卡；8 卡都运行 student 生成/验证与 actor 更新；teacher 在同组卡上打分；验证预算与训练 loss 保持本节开头的值；完整步时或相同质量预算的 GPU 小时改善。无需把空闲显存人为填满，也不承诺所有阶段的 SM busy 达到 100%。
