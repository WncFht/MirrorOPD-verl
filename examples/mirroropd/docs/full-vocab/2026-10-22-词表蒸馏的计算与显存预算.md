# 词表蒸馏的计算与显存预算

符号遵循[统一约定](../符号约定.md)；代码字段、论文原名与历史数据键保留原样。

本文是 OPD 各种学习信号共用的工程说明。算法与论文比较见[学习信号与梯度估计器对照](../opd-objective/2026-10-21-OPD学习信号与梯度估计器对照.md)，固定前缀与行为 IS 的数学边界见[优势估计文档](../theory/2026-10-22-固定前缀下的OPD目标与梯度.md)。数据与实现核对日期为 2026-10-21，本仓参照 `5bb952d8c`；2026-10-22 迁入 full-vocab 目录，历史测量口径保持不变。

**当前模型的词表是 151,936，hidden size 是 1,536。64 条满长训练回答的 BF16 teacher logits 约 129.83 GiB；对应 BF16 teacher hidden states 为 1.3125 GiB，另需一份约 0.435 GiB 的冻结 LM head。** 因而 full-vocab 的优先方向是保存 hidden states 并流式计算，而不是在 TQ 中缓存全词表 logits。

本文区分三类数字：张量大小是按形状计算的容量；已有 sampled-token 运行数据是实测；新方法的秒数是带显式参数的敏感性分析。没有将论文中其他模型、LoRA 或其他 backend 的倍数套到本配方。

## 2. 先分清三种成本

### 2.1 保留一个分数不等于只计算一个词表项

对 hidden state $h$，标准输出层与 sampled log-prob 是

$$
z=W h,\qquad \log p_a=z_a-\log\sum_{j=1}^{V}e^{z_j}.
$$

精确归一化仍扫描全部 $V$。即便 loss 最后只读取一个动作，梯度也是

$$
\frac{\partial\log p_a}{\partial z_j}=\mathbf1[j=a]-p_j.
$$

因此 sampled loss 的 LM-head 梯度通常仍是稠密的。Top-k 的 $O(K_{\rm head})$ 监督项减少的是 teacher 反馈、持久化状态和部分 loss 运算，不能由 $V/K_{\rm head}$ 推出整模型 FLOPs 或步时倍率。Full-vocab rKL 与 sampled-token 的 transformer backward 都可以只运行一次；差异集中在 head、softmax、loss 中间量及 teacher 信息通路。

仅支持内归一化的直接 top-k KL 可以对 selected logits 做 softmax，理论上不必计算全词表 normalizer；但它已改变目标。作者的某些 eager 实现仍先计算完整 logits/log-softmax，不能把这种潜在优化当作已测性能，也不能将其算作与 full-rKL 等价的省算。

Full-vocab 去除了固定前缀下 next-token Monte Carlo 噪声，却没有去掉 rollout、prefix、数据顺序和 optimizer 的随机性。

### 2.2 Payload、工作区与整卡峰值不是同一数字

- Payload 是跨 teacher/actor 边界保存的数据，可能驻留 CPU/TQ，也可能按 mini-batch 搬入 GPU。
- 工作区是当前 micro-batch 的 logits、log-softmax、概率、归一化统计和 backward 临时量。
- 整卡峰值还包括模型参数、梯度、优化器 shard、激活、FSDP all-gather、CUDA Graph、allocator 及同卡其他进程。

不能将全局 batch payload 直接称为每卡 VRAM，也不能将一个临时张量大小直接加到进程累计高水位后声称得到真实峰值。生命周期重叠必须由实现或 profiler 确认。

Hidden-state 路径的字节数比 BF16 logits 小 $V/d_{\rm hid,T}=98.9167$ 倍。另需 teacher head：

$$
M_{W_T}=Vd_{\rm hid,T}\times2=0.434692\ \mathrm{GiB}\quad(\mathrm{BF16}),
$$

按本机 Graph 运行的平均 response 长度 6,224.25 算，单批 response 位置约 398,352：dense BF16 为 **112.73 GiB**，hidden BF16 为 **1.140 GiB**。所以不是只有满长极端情况才需要处理 dense payload。

如果把完整序列所有位置的 dense BF16 都保存，最坏为约 **204.02 GiB/全局 batch**，hidden 为 **2.0625 GiB**。只保留 response 预测行不改变本文的局部目标，但必须保持 causal shift 与原始 response mask 对齐，不能删除 prompt 输入本身。

## 4. 当前 32K micro-batch 下的显存压力

### 4.1 Naive dense 路径

当 $B_{\rm tok}=32768$ 时：

| 单个数组                                        |        大小 |
| ----------------------------------------------- | ----------: |
| BF16 `[B_tok,V]` logits                         |  9.2734 GiB |
| FP32 `[B_tok,V]` logits/log-probs/probabilities | 18.5469 GiB |
| BF16 `[B_tok,d_hid_T]` teacher hidden           |      96 MiB |
| FP32 `[B_tok,16]` sparse scores                 |       2 MiB |

一个常见 naive full-KL 表达式可能同时持有两份 BF16 logits、两份 FP32 log-probs 和一份 FP32 student probabilities，这五个数组就有 **74.1875 GiB**，还未加入 transformer 激活、参数、梯度和 KL 乘积临时量。不同算子可释放或复用其中部分数组，故 74.19 GiB 是明确生命周期假设下的示例，不是所有实现的必需峰值。

如果整批 teacher payload 先进入 GPU，四卡时每 rank 的 BF16 缓存本身就有 32.46 GiB，八卡也有 16.23 GiB。再加当前 micro-batch 工作区，80GB 卡上的 naive dense 实现很容易受限。把 payload 放 CPU 能降低显存常驻，但会增加主机内存、搬运与序列化成本。

ResOPD 作者 kernel 的 `student_logits.to(float32).log_softmax()` 同样会带来 FP32 全词表工作区。它没有 dense teacher payload，但也不能仅凭 $O(K_{\rm head}+1)$ 的反馈就承诺与当前 sampled-token 完全相同的峰值。TA/Res 的 selected logits、mass 和 sampled score 可以复用一次 FP32 normalizer，避免重复 full `log_softmax`。[^res-code]

### 4.2 Token 分块

若每块只处理 $C_{\rm tok}=512$ 个预测位置，一份 FP32 `[C_tok,V]` 为 **0.2898 GiB**。假设 4–6 个此类工作数组同时存活，约为 1.16–1.74 GiB；加 teacher hidden/head 后，80GB 的 1.5B 配方具有实现流式 full-vocab 的合理空间。

这个判断成立的前提是块边界会真正释放中间量。普通 Python 循环把每块 loss 相加，再一次 `.backward()`，autograd 可能为所有块保留 logits 或 log-softmax，最终仍累积为 $O(B_{\rm tok} V)$。需要自定义 backward、checkpoint 重计算，或正确的梯度累积设计来保证内存上界。

现有 `_chunked_topk_log_probs()` 的输入已经是完整 `student_logits`；它按 token 分块处理 FP32 normalizer/gather，不会消除上游已经物化的 BF16 `[B_tok,V]`。其训练态 autograd 保存量也要单独核查，不能把代码中的 chunk 参数自动理解为整个 forward/backward 的常数显存。

### 4.3 词表分块与双维分块

Nitrobrew 直接从 hidden states 和 head 分块重建 logits，将词表方向工作集限制在 $O(B_{\rm tok} K_{\rm tile})$；其 custom autograd 保存 hidden/head/归一化统计，backward 重新计算词表块。它不需要缓存完整词表 logits。[^nitro]

进一步采用 $C_{\rm tok}=512$ 个位置、$K_{\rm tile}=4096$ 个词表项的双维 tile，一份 FP32 tile 仅 **8 MiB**。这不是总显存：仍有多个 tile、GEMM workspace、student 激活、teacher head 和 head 梯度；小 tile 也可能降低 GEMM 效率。正式实现应对位置块和词表块分别做速度/峰值扫参。

SVD 或低秩 head 压缩会改变重建分布，应独立作为近似实验。完整 hidden states 加原始 LM head 在相同归一化、temperature 和 logits 变换下才是精确重建；将原本 FP32 hidden 降为 BF16 仍会引入数值误差，表中的 BF16 预算不构成任意精度下的无损保证；必须取得 final norm 后、LM head 前的正确 hidden state，并复现可能存在的 bias、softcap 或缩放。本项目 Qwen2 配方较直接，不能据此推广到所有模型。NeMo RL 明确拒绝其 hidden-state 路径不能复现的 post-head 变换。[^nemo]

## 5. 精确 KL 的流式算法

KL 用于数值、baseline 和梯度代理时的 detach 位置及验算见[数值与梯度实现](../theory/2026-10-22-Full-vocab计算图与四种更新.md#graphs)。本节集中维护共用的流式计算公式。

令一行 student/teacher logits 为 $z^p,z^T$，温度已统一为 1。维护

$$
Z_p=\sum_v e^{z^p_v},\qquad Z_T=\sum_v e^{z^T_v},\qquad
\mathsf U=\sum_v e^{z^p_v}(z^p_v-z^T_v).
$$

则

$$
K=\frac{\mathsf U}{Z_p}-\log Z_p+\log Z_T.
$$

实际计算使用 running maximum 避免溢出。假设已有 $\zeta_p,S_p,\mathsf U_p$，新词表块的最大值为 $\zeta_c$，取 $\zeta'_p=\max(\zeta_p,\zeta_c)$，并更新

$$
\begin{aligned}
S'_p&=e^{\zeta_p-\zeta'_p}S_p+\sum_{v\in c}e^{z^p_v-\zeta'_p},\\
\mathsf U'_p&=e^{\zeta_p-\zeta'_p}\mathsf U_p+\sum_{v\in c}e^{z^p_v-\zeta'_p}(z^p_v-z^T_v).
\end{aligned}
$$

Teacher 的 $S_T$ 做相同的 online log-sum-exp，得到 $\log Z_p=\zeta_p+\log S_p$、$\log Z_T=\zeta_T+\log S_T$。所有 vocabulary tile 丢弃后，每个位置只保留 $K,\log Z_p,\log Z_T$ 等少量标量。

**Full baseline** 到这里即可：在 `no_grad` 下得到 $K$，再将 $r^{\rm cur}_a+K$ 作为 detached advantage，反向走原 sampled-token 路径。若 student logits 已在普通 forward 中物化，可以直接复用；进一步融合 LM head 时，可同时收集 sampled score，避免为了 baseline 额外做一遍 student 模型。

**Full-vocab loss** 需要第二遍重建块，计算

$$
\delta_v=p_v\bigl(\log p_v-\log T_v-K\bigr),\qquad
\nabla_{h_S}K=\sum_v\delta_v W_{S,v},\quad
\nabla_{W_{S,v}}K=\delta_v h_S^\top.
$$

Teacher hidden/head 不参与 backward；student head 和 hidden 梯度再接回原 transformer 图。这是精确分块求和与内存换计算，不是只对 top-k backward。CPU [验算脚本](../opd-objective/scripts/verify_reward_estimators.py)独立验证了该两遍公式与 dense autograd 一致。

一次 teacher head 投影的成本为 $2\mathsf T_{\rm resp}d_{\rm hid,T}V$，满长 batch 约 **214.12 TFLOPs**。流式重计算仍需这些乘加，不能把 hidden-state 通信优化误解为取消词表投影。若 teacher 端直接导出 hidden 而不再计算未使用的 full logits，可将原来的投影移到 actor 侧；只在 teacher 已经完整投影后又重复重建，会付出额外成本。多 epoch 可以复用 teacher hidden，但每轮 current full-KL 仍需与当前 student 匹配。

## 6. KL baseline 的高效实现选择

### 6.1 Teacher-top-k baseline：最容易复用稀疏反馈

Teacher 在一次 forward 中输出 top-k 的真实 log-probs 与 sampled score，student 从当前 logits gather 相同 IDs；baseline 选集、归一化和求和全放在 `no_grad` 下。最后只将一个 FP32 scalar 接到 sampled loss 的 advantage。

在同一 teacher-top-16 payload 上，可以分别得到：支持内归一化 KL baseline、TA 粗粒度 KL baseline、TA loss、HETS、ResOPD、SC-TA。Baseline 的两个版本不要混名；直接 TA loss 必须对 student mass 求导，不能将 baseline 的全套 `no_grad` 路径直接当作 TA loss。

这条路线不需要额外 teacher forward，但需要扩展本仓 shared teacher 的输出。Teacher 排序/gather 有成本；若为诊断重复计算 student top-k 或保留 $K_{\rm head}\times K_{\rm head}$ overlap，则又有额外费用，应与方法必需项区分。

### 6.2 Student-top-k baseline：原论文路线需要调整生产顺序

当前顺序为 rollout → teacher score → FSDP old-log-prob → actor update。原版 vOPD 需要 student 的 top-k IDs 在 teacher 查询前可用，可选：

1. 将已有 student old-log-prob 阶段移到 teacher 前，并在同次 forward 取得 top-k，再让 teacher 对每个位置的指定 IDs 打分。固定这一支持集后，多轮更新仍可使用它作为 action-independent baseline，但不再是每轮重选的原版 current top-k。
2. 在 rollout 导出 student top-k，再让 teacher 对指定 IDs 打分。必须区分 vLLM 的行为分布与 FSDP current 分布，也要验证 backend 的 per-position 指定 token 评分能力。
3. 保存 teacher hidden states，在 actor 当前 forward 内选择 student top-k；从冻结 teacher head 中只取这些行重建 teacher selected logits。对于支持内归一化 baseline，无需为该 baseline 单独重建全词表 teacher normalizer；sampled reward 所需的 $T_a$ 仍要另行提供。

上游 #7806 的请求级 union 会把不同位置的候选并起来，返回量可能大于理想的 $Nk$，也依赖指定 vLLM API。因此不能仅看 `topk=16` 就认定其通信与 teacher-top-16 相同。我们已有 FSDP teacher，可以直接做逐位置 gather，无需为该功能先升级 vLLM。[^pr-rkl]

### 6.3 Full baseline：比较三种生命周期

| 路线 | 持久数据 | 每次更新的额外工作 | 取舍 |
| --- | --- | --- | --- |
| Teacher/student 同时前向 | 无跨阶段全词表缓存 | 可直接复用两份 logits 做 KL | 最简单，但双模型/双 logits 同时驻留，与当前分时 offload 不同 |
| Teacher 导出 hidden + head | $O(Nd_{\rm hid,T})$ + 冻结 head | teacher head 重建、KL reduction | 通信和显存可控，最适合共享池演进 |
| 一次算完并缓存 baseline scalar | $O(N)$ | 后续只读取 scalar | 旧 baseline 仍可作为控制变量，但不再是每轮精确 current KL；生成该 scalar 时仍需双方分布 |

在一次更新的配方中，还可以将 teacher hidden 交给已有的 old-log-prob 前向：同一次无梯度 student forward 计算 baseline，写入每位置 scalar，随后释放 teacher hidden/head，再进入 actor backward。这避免为 baseline 新增 student 前向，也避免在 actor backward 期间保留 teacher 工作区；所得是 old-policy baseline，多轮复用时应按该名称记录。

原版 vOPD 的“baseline 不增加 critic/inference”不能推出我们无需数据通路修改。若不改变现有顺序、不保存 teacher 信息，又要求每轮精确 current full baseline，就必须重新运行 teacher 或保留双模型，成本会发生变化。

| 原版 student-top-20 baseline | 理想 sparse payload 73.5 MiB，或 1.31 GiB hidden | 支持集产生与 teacher 查询重排 | 容量通常可控，接口与额外前向比 top-k 数值更关键 |
| Full baseline，hidden + no-grad streaming | 1.31 GiB hidden + 每 rank 0.435 GiB head | teacher head 重建与 streaming KL，sampled backward | 原理上可行，需 kernel/生命周期实测 |
| Full-vocab rKL，hidden + custom backward | 同上 | 两遍或更多次 head 重建、dense 梯度 tile | 原理上可行；需避免普通 autograd 跨块保留全部中间量 |
| Full baseline / full loss，naive dense 缓存 | BF16 129.83 GiB 或 FP32 259.66 GiB | 多个全词表矩阵与搬运 | 不建议作为当前默认 32K 预算的首个实现 |

这里的“原理上可行”只意味着大词表临时量可被限制到较小工作区，不保证整卡总峰值或吞吐。新方法还需同批次测量 GPU allocated/reserved、NVML 整卡显存和 CPU/TQ 驻留，尤其不能把 vLLM 生成期 KV 的约 42 GiB 与训练期已经 sleep 的工作区简单相加。

## 8. 用现有实测约束速度估算

### 8.1 可直接使用的锚点

本机 H800×4、Graph、batch64、epochs1、训练 response≤7168，step2–5 的实测均值为：

| 阶段                            | 秒/step |
| ------------------------------- | ------: |
| Student 生成及既有收尾          |  24.197 |
| Teacher 搬入/搬出               |   0.877 |
| Teacher forward                 |   1.303 |
| Student old-log-prob            |   2.702 |
| Actor update                    |   5.801 |
| Advantage、权重同步与未分解余量 |   1.046 |
| 总计                            |  35.926 |

实测 FSDP 全 rank 累计 allocated 高水位的观测最大为约 18.57 GiB，actor 阶段整卡采样峰值约 23.04 GiB，生成阶段约 42.25 GiB。它们分别是累计 allocator 计数和约 1 秒采样的整卡指标，不是同一口径。原始条件和限制引用[本机测量](../infra/2026-10-22-训练与验证性能实测.md#3-本机编译与训练优化)。

默认脚本使用八卡，但当前没有同条件 **H800×8 + Graph** 的新估计器测量，不能直接把上述秒数除以二。已有 A800×8 shared/eager 历史均值约 148.54 秒，其中 teacher forward 2.74、actor update 9.01 秒；其生成阶段慢得多，详见[历史对照](../infra/2026-10-22-训练与验证性能实测.md#4-八卡历史与one-shot对照)。两套数据分别列出，不混成一台机器的预测。

### 8.2 方法阶段的敏感性分析

在固定轨迹长度、相同 GPU 数、相同调度下，以下带阶段下标的 $t_{\rm new},t_{E=4}$ 均为墙钟秒数，与核心稿梯度流时间 $t$ 分开。设新 teacher forward 和 actor update 分别为原来的 $f_T,f_A$ 倍，额外传输/同步时间为 $\Delta t_{\mathrm{payload}}$，则四卡的一次更新场景为

$$
t_{\mathrm{new}}\approx35.9259+
1.3032(f_T-1)+5.8010(f_A-1)+\Delta t_{\mathrm{payload}}.
$$

| 假设 $f_T=f_A$，额外 payload 时间暂取 0 | 条件步时 | 相对旧锚点 |
| --------------------------------------- | -------: | ---------: |
| 1.0                                     |  35.93 s |       不变 |
| 1.1                                     |  36.64 s |     +1.98% |
| 1.5                                     |  39.48 s |     +9.89% |
| 2.0                                     |  43.03 s |    +19.77% |

这些因子是待测参数，表格不是 ResOPD/TA/full-vocab 的已知倍率。它给出可审查的预算：如果 sparse loss 使 teacher/actor 合计只多 10%，整步约多 2%；如果流式 full-vocab 使相关阶段翻倍，整步约多 20%，再加 payload 时间。**不能据此声称 full-vocab 必然只有 20% 开销**，低效 kernel、OOM 后缩小 micro-batch、额外模型 forward 都可能超出该假设。

各方法优先测量的未知量如下：

| 方法 | 决定速度的增量 | 如何代入 |
| --- | --- | --- |
| Teacher-top-k baseline | teacher top-k + student gather/no-grad baseline | 测 $f_T$，以及 baseline 对 $f_A$ 的影响 |
| TA / HETS / Res / SC-TA | 同 payload，不同可微 reduction 与 tail correction | 共享同一 normalized logits 的实现下，比较各自 $f_A$；不要另加一遍 transformer |
| Student-top-k baseline | 支持集生产与 teacher 指定 ID 评分 | 若不能复用 old-log-prob 而额外增加等成本 student scoring，则还要加约 2.70 秒，约 +7.5% |
| Full baseline | no-grad streaming head/KL + 数据搬运 | 测 $f_A$ 与 payload；不加 critic，仍可能加 head 计算 |
| Full loss | head 重建与自定义 backward、可省去冗余 sampled loss | 测实际 $f_A$；不能用逐词表项数预测 |
| Naive dense | dense payload + 巨型中间量 | 先验证是否能容纳；OOM 时没有有意义的秒数估计 |

在历史 A800×8/eager 锚点上，相同敏感性式约为 $148.54+2.74(f_T-1)+9.01(f_A-1)$。相关阶段翻倍约 160.29 秒、增加 7.91%，原因是原生成阶段占比大；这不是 Graph 默认配方的速度。

### 8.3 四次更新的外推

若每批复用四次、teacher 评分一次，先保持每次 actor update 等成本，则四卡基准外推为

$$
t_{E=4}\approx35.9259+3\times5.8010=53.3290\ \mathrm{s}.
$$

此处 53.33 秒本身也是外推，不是已有 E4 运行的实测。带新 loss 的式子为

$$
t_{E=4,\mathrm{new}}\approx53.3290+
1.3032(f_T-1)+23.2042(f_A-1)+\Delta t_{\mathrm{payload}}.
$$

| $f_T=f_A$ | 条件步时 | 相对四轮基准外推 |
| --------- | -------: | ---------------: |
| 1.1       |  55.78 s |           +4.60% |
| 1.5       |  65.58 s |          +22.98% |
| 2.0       |  77.84 s |          +45.96% |

Teacher hidden/top-k 可以缓存一次，但 current full-KL、当前 baseline 或当前 tail masses 要在各次更新重新计算。重复更新会放大 actor-side kernel 的成本，也更需要正确的 residual IS。还应核查 worker 是否在每个 epoch 重新从 CPU 搬入同一 payload；“数据只生产一次”不等于“只传输一次”。

## 9. 搬运时间下界与计算预算

满长 response-only payload、假设整个作业的有效聚合带宽为 25 GiB/s 时：

| 数据                          | 单向纯字节传输下界 | 两次同等搬运的下界 |
| ----------------------------- | -----------------: | -----------------: |
| BF16 dense logits，129.83 GiB |            5.193 s |           10.386 s |
| BF16 hidden，1.3125 GiB       |           0.0525 s |           0.1050 s |
| Top-16 + sampled，59.5 MiB    |          0.00232 s |          0.00465 s |

25 GiB/s 是示例输入，不是本机已测 PCIe/NVLink/Ray 带宽。假设 50 或 100 GiB/s 时，这些纯搬运值分别除以 2 或 4。这里使用**全局有效聚合带宽**，不把单卡链路带宽与全局 payload 混算；真实路径还包括同步、CPU copy、序列化、TQ 和多个 rank 并发。

对 naive dense 路径，仅两次 payload 搬运就可能是数秒到十秒级，而稀疏与 hidden 路径的原始字节量通常不主导整个生成步。框架开销可能大于小 payload 的字节下界，不能用表中毫秒数替代实际 teacher transfer timer。

计时模型不含启动/编译、验证、保存和重试，也假定不同算法的生成长度不变。实际算法改变回答长度后，rollout 成本也会变化，不能将全部步时差归因于 loss。报告完整实验成本时应使用

$$
T_{\mathrm{run}}=T_{\mathrm{startup}}+\sum_s T_s+
\sum_j T_{\mathrm{validation},j}+T_{\mathrm{checkpoint/cleanup}}.
$$

GPU 小时还要乘以实际占用的卡数。现有验证设置每题采样 16 次、response 上限 31,744，验证成本可能很大；这些长度不能代入训练 teacher payload 表。本文不重新估计验证速度，复用 infra 的独立测量。

## 10. 实现路线与验收点

建议先扩展一条 shared FSDP teacher 稀疏输出通路，统一产出 teacher top-k 的 FP32 log-probs、INT32 IDs 和 actual sampled log-prob。用它支持 teacher-top-k baseline、TA、HETS、Res、SC-TA，避免给每个方法单独加一次 teacher forward。Loss 层保留明确的数学定义，不能仅通过不断增加 PG 布尔开关表达直接散度与随机残差。

Full-vocab 的下一步采用 teacher final hidden states + frozen head。先在小 batch/短 response 上实现 FP32 dense reference，再做 no-grad streaming baseline，然后做 custom-backward full KL。正式性能对照关闭 SVD、量化和额外 token 筛选；若研究这些近似，单独命名。

验收至少覆盖：causal shift、EOS/padding、不等长序列、全局 token-mean、teacher detachment、student head 梯度、tail mass 数值边界、teacher=self 时 KL 接近零、独立 dense oracle 对齐，以及峰值随 micro-token/chunk 大小的变化。只验证 KL=CE−entropy 不能发现两条路径共同使用了错误 teacher logits；NeMo 的实现说明也明确区分该代数自检与 payload 正确性。[^nemo]

容量和时间表由[脚本](../opd-objective/scripts/estimate_reward_costs.py)生成，完整未四舍五入结果见 [cost-estimate.json](../opd-objective/data/reward-research-20261021/cost-estimate.json)。可修改 batch、response 长度和 micro-token 预算重新计算容量；时间锚点仍是已测四卡 batch64，不会随这些参数自动缩放，JSON 会标明配置是否匹配：

```bash
python examples/mirroropd/docs/opd-objective/scripts/estimate_reward_costs.py \
  --batch 64 --response-length 7168 --prompt-length 4096 --micro-tokens 32768 \
  --output /tmp/opd-cost-estimate.json
```
